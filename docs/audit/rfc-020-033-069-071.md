## RFC-020 Versioned bot configuration - Partial

Acceptance criteria and evidence:
1. Team default; private owner-only across list/read/use/edit. Partial. Default is `team` for specialists (CS:98), chief forced private by SCH check; `visibleBot` filter (CS:76) used in list (CS:95), conversation start (CS:79), mentions (CS:73); edit/archive/move are owner-only (CS:102-115, 137-141). Test: chat.integration.test.ts "team specialists are visible but only editable by the owner" (private-bot probing by user B only partly covered).
2. Stale-version detection. Met. `updateBot` uses `where version = expected` and increments (CS:102-108); proposals go stale (CS:145-152); tested in tools.integration.test.ts.
3. Run configuration reproducible by version; archive blocks new work without erasing history; onboarding A cannot ready B; no model flag bypasses admission. Partial. Messages record `botVersion` (SCH message.botVersion; CS:218) but the bot row is overwritten in place, so a past version's personality/instructions/harness cannot be reconstructed (no `bot_version`/history table). Archive: `archiveBot` sets flag (CS:110); `loadVisibleBot` rejects archived (CS:79) and history stays. `onboarded` is a single boolean on the bot (SCH bot.onboarded), only the owner can set it (CS:118), so B using a team bot is neither gated nor "not ready" in any recorded way: ordinary chat in `converse` (CS:181-229) never checks `onboarded` for anyone. Workflow prompt nodes (FS:16-17,125) and `mentions` for non-owner bots also bypass it (mentions require `onboarded` at CS:73, which for a team bot is the owner's flag, not B's). No model-supplied flag exists, so forgery is moot.
Other contract gaps: no integration requirements / skill references / required capability validation; no actor+bot+binding fingerprint; harness enum in zod is the only validation (chat/routes.ts:12); no bot_version/archive-revocation tests; "cosmetic vs meaningful" is the field list at CS:104 (name/description change does not reset readiness: OK).

Remaining gaps and smallest implementation:
- Add `bot_version` snapshot table (bot_id, version, config jsonb) written inside `updateBot`; add `GET /bots/:id/versions/:v`. Store `botVersion` already on message so replay is possible.
- Replace `bot.onboarded` boolean by `bot_readiness(user_id, bot_id, config_fingerprint, confirmed_at)`; admission check `isReady(actor, bot)` used in `converse` (unless message flagged as onboarding turn by server, i.e. conversation.purpose='setup'), mentions, routines, workflows. This is the only way "A ready, B not ready" becomes true.
- Add `configuration.test.ts` DB integration cases listed in RFC.
- BLOCKED-EXTERNAL: none. Integration requirement resolution depends on RFC-007 (connections store exists in `modules/connections` but is not wired to bots).

## RFC-021 Bot onboarding and settings - Partial

1. Configure, account setup, return without losing progress, real response. Partial. Settings form in CP:144-153 (harness, model, personality, instructions) and a real reply requirement (CS:122-124 needs a complete assistant message at the current `botVersion`). No account/provider setup flow (RFC-019 absent), no persisted draft (settings submit directly; reload keeps saved values only). A `fixture` harness reply satisfies the gate (CS:122 does not exclude `harness='fixture'`), which the RFC explicitly forbids as evidence.
2. Explicit positive satisfaction only; No/silence/stale/model-authored cannot bypass; B unready. Partial. `answerOnboarding` is a dedicated authenticated endpoint (chat/routes.ts:85) requiring `satisfied=true` and matching `expectedVersion` (CS:117-126); version bump on reconfiguration resets (CS:104-105). Missing: the "bot asks are you satisfied" question is not a persisted message the confirmation is tied to; the evidence message is any assistant message of that version, not one from an onboarding-marked conversation; no fingerprint of connection bindings; B-unready not modelled (see 020). Test: chat.integration.test.ts "onboarding needs a real reply and explicit satisfaction, and reconfiguration resets it".
3. Refine/retest/confirm accessible after reload; ordinary execution gated. Partial. After reload the "setup" banner/buttons recompute from messages (CP:74,137-142; labelled group, buttons). Ordinary chat is not gated (CS:181+); routines and mentions are (FS:29,78; CS:73); workflows are not. No RFC-071 outstanding-question item.
Remaining: (a) reject `harness='fixture'` as evidence unless an env flag is set in tests; (b) add `conversation.purpose` ("chat"|"setup") set only by server when bot unready and gate `converse` on `purpose==='setup' || ready`; (c) persist the satisfaction question as an assistant message (`kind='satisfaction_prompt'`) and require its id in `answerOnboarding`; (d) emit attention item for outstanding setup; (e) draft: client localStorage or `bot_draft` table; (f) tests `onboarding.test.ts`, `form-state.test.ts`.
BLOCKED-EXTERNAL: the RFC's required approved real-harness conversation + user confirmation (claude-code/haiku was exercised once per the checkpoint; other harnesses and RFC-019 account setup UI need real accounts).

Add `chief.test.ts` with `Promise.all` ensureChief. Not hooked into enrollment (ensureChief is lazily called from GET /bots at chat/routes.ts:82): acceptable per "existing and newly enrolled users".

## RFC-025 Persist private conversations and messages - Partial

1. Shared bot has separate A/B conversations; no cross-owner probing. Met. `conversation.ownerUserId` + `loadConversation` filters by owner (CS:83-86), messages queried with owner (CS:165); test "chief provisioned once; chat round-trips; other users are denied".
2. Repeated send creates one user message and one logical run; history paging has no gaps/duplicates. Unmet. No client request key (grep: no idempotency in chat module); `converse` always inserts a new user message (CS:203). History returns the full list unpaginated (CS:163-168). Seq uniqueness exists (SCH `message_conversation_seq_unique`) but `nextSeq` is computed from a read (CS:202) so concurrent sends collide on the unique constraint and surface as 500 (no retry).
3. Rejected/failed distinguishable from accepted-but-running with stable IDs. Partial. `message.status` has `complete|failed` (SCH) with no `running/pending`; user message exists before the run (SSE `user` event then `message`). Failures of authz happen before insert (CS:185-194). No run association (message has no run id).
Remaining: add `message.clientRequestId text` + unique (conversation_id, client_request_id) and make `converse` return the existing user message/replies on repeat; allocate seq with `insert ... select coalesce(max(seq),0)+1` or advisory lock; add `GET messages?before=<seq>&limit=` cursor; add `status` value 'running' (assistant placeholder) if RFC-069 is taken on. Tests: `messages.test.ts`.

## RFC-026 Connect composer to runs - Partial

1. Sending creates one persisted message/run with correct attribution. Partial. Persisted user+assistant messages with `botId`/`botVersion` attribution (CS:203,218); UI shows author for delegated bots (CP:117). "Run" is not a persisted entity in this path.
2. Double submit/reconnect no duplicate; rejected sends keep text. Partial. `busy` flag blocks local double submit (CP:51-52); server has no idempotency (see 025). On failure draft is retained because `setDraft("")` only after success (CP:64) - Met for that part. Reconnect creates duplicates.
3. Keyboard/empty/unavailable bot states; other user cannot open route by ID. Partial. Enter sends, Shift+Enter newline (CP:169), empty-state text (CP:113); ownership enforced server-side (404). Unavailable (archived) bot state not shown explicitly. Cancel/status not wired: SSE `cancel()` aborts generator on disconnect (chat/routes.ts:66) which treats disconnect as cancellation, which the RFC forbids. No `composer-state.test.ts`.
Remaining: idempotency key (025), explicit cancel endpoint (AbortController keyed by conversation) and decouple generation from the HTTP stream, archived-bot message, extract composer to `composer.tsx` with pure state tested.

## RFC-027 Streaming history and reconnect - Unmet (basic streaming only)

1. Split/replayed/late events produce same content as history. Unmet. Client concatenates deltas per botId and replaces by the final `message` event (CP:56-60); no sequence ids, dedupe or reducer. Server events carry no seq (service.ts ChatEvent type at line 18).
2. Disconnect/reconnect preserves partial output and origin; repair-and-return; no auto replay. Unmet. If the stream drops, the generator is returned and partial text is lost (chat/routes.ts:66; CS:215-216 only persists after the loop). There is no interrupted/cancelled status. Repair link exists only as `resultLink` strings on attention items (FS:43) and Studio; no return-to-chat flow.
3. Scroll stability upward during streaming/pagination; disposed chats get no updates. Unmet. `scrollIntoView` on every messages/streaming change (CP:46) yanks the reader down; no pagination; unmount aborts nothing (fetch has no AbortController).
Remaining (smallest viable): persist partial assistant text periodically (status 'interrupted' on stream cancel in a `finally` in `converse`), add `seq` numbers to SSE events, a pure `event-reducer.ts` (dedupe by seq, reconcile with `GET messages`), AbortController on unmount, only auto-scroll when the user is within ~80px of the bottom. Repair-return is a larger piece; defer or limit to a link back to `/chat?c=` (the attention link already uses that shape, FS:43, but `chat.tsx` route does not read `c`: verify).

## RFC-028 Markdown - Partial

1. Lists, emphasis, links, fences, multiline round-trip without altering source. Partial. Renderer is read-only over `message.content` (stored source untouched; CP:119). Supports fenced code, `#` headings, `-`/`*` lists, bold/italic/code/links (markdown.tsx:4-38). Not supported: ordered lists, blockquotes, tables, images, nested lists, hard line breaks within paragraph; fenced code inside lists; unterminated fence handling OK. User messages render as plain text, not Markdown (CP:119).
2. Script URLs/raw HTML/malicious images can't execute. Met for what exists: React text nodes, links restricted by regex to `https?://` with `rel=noopener noreferrer nofollow` (markdown.tsx:13); images are not rendered. No sanitizer test file (`markdown-policy.test.ts` absent), no browser XSS probe recorded.
3. Composer preview and final message consistent. Unmet. Composer is a plain `Textarea` (CP:168) with no preview or formatting affordances.
Remaining: add `Preview` toggle reusing `<Markdown>` in the composer; unit tests for the `inline`/block renderer (feed `javascript:`, `<img onerror>`, `[x](javascript:...)`); note the RFC requires approval before a parser dependency, so the hand-rolled subset is a policy deviation to be accepted explicitly (research/decision item, not external). Render user messages through Markdown too.

## RFC-029 Attach owned files - Partial

1. A cannot attach/read B files; MIME/name tricks, oversize, traversal rejected. Partial. Attachments are DB rows (`attachment` table in FSCH) with owner check and `isNull(messageId)` single use (CS:188-189); test "attachments are owner-only, single-use and reach the bot". There is no filesystem path so traversal is moot; opaque UUID ids. Size is limited to 256KB by zod `max(262144)` (chat/routes.ts:18) and re-checked by bytes (CS:172), but this is a JSON body, not a streaming limit; NUL bytes reject binary; MIME is client-supplied and never validated (CS:173).
2. Run sees only accepted bounded content with provenance; unsupported formats error actionably. Partial. Content is included in the prompt as fenced blocks with the file name (CS:201); no provenance (hash, owner, upload id) in the prompt; error message "Only text files up to 256 KB" is actionable (chat/routes.ts:38). Only 5 attachments per message (zod).
3. Abandoned uploads cleaned; removal before send prevents inclusion. Unmet/Partial. Removal is client-side only (the id is simply not sent; row remains); no retention/cleanup job; no DELETE endpoint; no progress UI (CP:166 reads file as text).
Remaining: `DELETE /attachments/:id` (owner, unattached only) + a periodic purge (e.g. in the 30s scheduler: delete unattached rows older than 24h); store sha256 in the row and include it in the prompt header; reject non-text MIME allowlist; tests `uploads.test.ts` as listed. Binary/PDF parsing deferred (research-only: needs parser dependency approval).

## RFC-030 Server file references - Partial

1. Traversal/encodings/symlink escape/unauthorized roots fail before content enters context. Met for covered cases. `createFileStore.area` resolves root as `me/<userId>` or `shared` only from the actor (files.ts:13-23), `realpath` both base and target and checks prefix (files.ts:20-21); size cap and NUL check (files.ts:34-36); fileRefs are authorized before anything is written (CS:187-194). Test: experience.integration.test.ts "server file references stay inside the user's area and the shared area" (includes symlink escape per checkpoint). Not covered: .env/credential-name denylist (RFC non-goal says no access to .env files; only root containment protects), TOCTOU between realpath and readFile (files.ts:20 vs 35; fd-based open not used).
2. File changes between selection and execution follow explicit version policy; context tied to a recorded hash. Unmet. Content is read at send time (CS:192), no hash/mtime recorded anywhere, no selection-time snapshot.
3. Conversation snapshot contains only copied content, never a live capability. Met by accident. `publishSnapshot` copies only `{role, content, seq, status}` (FS:139); fileRefs are not stored on messages at all (only the user's typed `content`), so no capability leaks; but the file content that the bot saw is not preserved either.
Remaining: record `{path, sha256, bytes}` for each fileRef on the message (new `message_context` jsonb column or table) and include sha in prompt; use `open` + `fstat` to avoid TOCTOU; skip dotfiles/`.env*`; add `server-references.test.ts` for pure path policy (extract `resolveRef`). Server-file picker exists in CP:165 (minimal).

## RFC-031 Message threads - Partial

1. Root from another conversation/user can't be a parent. Met. `converse` requires `parentMessageId` to exist in this conversation's history (CS:185), conversation is owner-scoped; test in features.integration.test.ts "threads and reactions are owner-scoped". One-level restriction (parent must itself be a root) is not enforced: a reply can parent a reply.
2. Threaded run receives root/replies and explicit attachments only; siblings excluded. Unmet. `hist` is the entire conversation history (CS:184, 212) and pipeline includes the last 10 of it (pipeline.ts:48); no thread filtering. Replies by the assistant inherit `parentMessageId` (CS:218) which is good.
3. Reload/reconnect preserves ordering/counts; closing panel releases subscriptions. Partial. Ordering by seq persists; UI shows "in thread" label only (CP:116) with a "Reply in thread" button (CP:122); no panel, counts, deep links, so nothing to release.
Remaining: in `converse`, when `parentMessageId` set, build `hist` as `[root, ...replies where parent=root]`; enforce parent.parentMessageId is null; add counts to listMessages (group by parent). `threads.test.ts` DB integration.

## RFC-032 Mentions - Partial

1. Autocomplete/forged IDs cannot expose/invoke another user's private bot. Partial/Met server-side. Resolution is by name token among `visibleBot` and onboarded, non-archived bots (CS:70-75) so private bots of others cannot be invoked; there is no autocomplete UI and no mention ID in the request, so forgery is not a vector.
2. Rename/stale access cannot redirect a stored mention. Unmet. Mentions are not stored as structured data; each send re-resolves `@name` text against current names, and two bots with the same name would both match (no uniqueness on visible names across owners; `workspace`/`bot` unique only on workspace name). A renamed bot silently changes target on re-run only; stored history has no mention record.
3. Valid mention yields one target run with same user connections; ambiguous multi-target rejected. Unmet. Up to 3 mentioned bots all run sequentially (CS:74,210) as fan-out, plus the chat's own bot always runs first (CS:210), so a mention gives 2+ runs, contrary to "one explicit target per send".
Remaining: add `message.mentions jsonb` of `{botId, label}` stored at send; accept `mentions` ids from client picker (validate through `loadVisibleBot` + ready); if >1 distinct target return 400 `AMBIGUOUS_MENTION` (or product decision to keep bounded delegation of 3 - this deviates from RFC and needs sign-off); autocomplete endpoint `GET /bots?q=` already filtered by visibility. Tests `mentions.test.ts`. Note the experience test currently asserts the fan-out behaviour, so it would change.
Also: readiness check uses owner's flag (see 020).

## RFC-033 Reactions - Partial

1. Duplicate add/remove converge to one state. Partial. Add: `unique(messageId, ownerUserId, emoji)` with `onConflictDoNothing` (FS:149; FSCH:66). Remove: no operation exists (routes.ts:69 only POST).
2. A cannot react to B's message or snapshot. Met. Message lookup requires `ownerUserId = actor` (FS:147); snapshots are a separate table with no reaction path. Reaction rows list for a message returns all reactions on it (FS:150; only owner can reach).
3. Rejected updates restore UI; emoji not raw HTML. Partial. Emoji is only `min(1).max(8)` (routes.ts:21) so any text up to 8 chars (including `<b>`) is stored; React escapes on render, and the UI hardcodes only 👍 and no rendering of reactions at all (CP:121 shows a notice, no persisted state shown after refresh). No optimistic update/rollback, no aria state.
Remaining: `DELETE /messages/:id/reactions/:emoji`, validate emoji with a small allowlist or `\p{Extended_Pictographic}` regex, return reaction counts in `listMessages`, render pressed state with `aria-pressed` and a label, tests `reactions.test.ts` (race via Promise.all, invalid emoji, cross-owner). Keyboard check is browser-approval item.

## RFC-069 Persist assistant and tool output - Partial (architecturally different)

The simplified path has no run-event stream; the assistant message is written once, after generation (CS:218). Consequently:
1. After stream completion/cleanup, reload returns same visible assistant/tool content with stable IDs and attribution. Met in the simple sense: message ids stable, `botId`/`botVersion` stored, tool notes appended as text lines to the content (CS:61-64, e.g. "Remembered: ..."), tool blocks stripped (tools.ts:43). Tool results/status are not structured parts; browser results are only fed back to the model, not stored.
2. Duplicate chunks/terminal events, out-of-order replay and crash between event persistence and projection don't lose/duplicate; cursor. Unmet. There are no events to project and no cursor. Crash mid-generation loses the whole assistant message (nothing persisted until completion) and leaves a user message with no reply.
3. Failed/cancelled/interrupted runs retain visible partial output with honest status. Partial. Failed replies are persisted with `status='failed'` (CS:216,218) but the content is a generic error string unless some chunks were streamed (`reply || ...`); cancel/disconnect persists nothing (chat/routes.ts:66, CS:215).
Smallest implementation that satisfies the intent on this architecture (no event table): (a) in `converse`, insert the assistant message row up front with status `running` and update `content` periodically/at end (stable id, survives crash); extend status enum with `running|interrupted|cancelled`; (b) wrap the loop in try/finally to mark `interrupted` when the generator is returned; (c) on server boot mark stale `running` rows as `interrupted`; (d) store tool results as `message.parts jsonb` (type, name, status, redacted result) rather than text lines. This replaces RFC-069's events/cursor machinery; document it as an accepted deviation (the RFC dependency RFC-011 events module does not exist on this path). Test: `output-projection.test.ts` becomes a DB test for interrupted/restart.
BLOCKED-EXTERNAL: "disposable PostgreSQL transaction/restart check" needs approval (compose Postgres is available locally).

## RFC-070 Private multi-turn run context - Partial

1. Second turn sees first exchange and new prompt once; other conversation/user gets none. Met in behaviour. `history` loaded by conversationId (CS:184), where conversation is owner-scoped (CS:83-86); pipeline passes the last 10 messages (pipeline.ts:48) and the current prompt as `User: ...`; history already contains the user message when `run.stream` is called with `hist` (CS:212,215) and the prompt is appended as well, so for non-fixture harnesses the current user message appears twice (once as the last "Conversation so far" line and once as `User:`): a defect against "current message exactly once". Check pipeline.ts:48-49 with CS:212.
2. Restart / config change / unsupported resume follow documented policy. Partial. Always replays persisted history (no native resume), so restart is safe; no documentation of the policy; config change just changes system parts; redaction hooks also applied to history (pipeline.ts:31-33).
3. Limits, concurrent turns, tool pairing deterministic; cutoff/version recorded; truncation visible. Unmet. Hard `slice(-10)` with no byte limit (a few very large messages can exceed context), no visible truncation notice, tool-call/result pairing not preserved (tool blocks stripped from stored content), no cutoff/applied-version record on the run, no turn serialization: two concurrent POSTs interleave and collide on `seq` (CS:202).
Remaining: build `turn-context.ts` (pure): takes messages with seq <= cutoff, excludes the current user message from history, applies a character budget, prefixes "[earlier messages omitted]" when truncated; record `contextCutoffSeq` and `botVersion` on the assistant message; serialize per conversation with an in-process mutex map or `pg_advisory_xact_lock(hashtext(conversation_id))` and reject overlapping sends with 409; unit tests `turn-context.test.ts` (pure, no DB needed).
BLOCKED-EXTERNAL: the single approved Pi two-turn smoke (needs Pi installed/account).

## RFC-071 Common in-app attention state - Partial

Schema `attention_item` (FSCH:43-48): owner, bot, title, detail, nextAction, resultLink, source (routine|workflow|manual|bot), status (open|acknowledged|resolved), timestamps. Routes: list/add/status (features/routes.ts:59-61). Producers: routines (FS:32,43), workflows (FS:130), background hooks (pipeline.ts:56-57), handoff and delegated failure (CS:38,222).
1. Same source issue has one stable identity across replay/restart; consistent labels/counts across consumers. Unmet. No source key / generation; every producer event inserts a new row (FS:21-23), so a failing routine every 30 min creates unbounded duplicates. Consumers: only Studio kanban; no sidebar/activity consumer.
2. Two users of same bot can't see/mutate each other's items; nested links authorized on access. Met for list/mutate (owner filters FS:104,111). Links are raw strings (`/chat?c=<id>`, FS:43) never re-authorized; revoked/expired targets are not handled.
3. Acknowledge, resolve, cancel, approve distinct; reading can't mark success. Partial. Status change endpoint is one generic `status` setter allowing open→resolved directly (FS:110-111; routes.ts:17): "resolve requires the underlying repair/answer/approval event" is not enforced, and there is no `cancel`. Acknowledge doesn't alter runs (Met), no `unread` / read-state, no precedence (blocked vs unread).
Remaining (smallest): add columns `sourceKey text`, `generation int`, `reason enum(input|repair|review|result)`, `readAt timestamptz`; unique (owner, sourceKey, generation) with upsert in a single `raiseAttention()` producer function used by all current producers; split endpoints `/attention/:id/read` and `/attention/:id/resolve` (resolve only from server-side producers or after the repair event, e.g. routine succeeds); expose `GET /attention/summary` (counts by bot, blocked precedes unread) for the nav shell. Tests `attention/state.test.ts` as DB integration tests. PostgreSQL checks need approval (compose Postgres local).
