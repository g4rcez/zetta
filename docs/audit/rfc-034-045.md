## RFC-034 Capture immutable conversation snapshots - PARTIAL (low)
Existing: `snapshot` table (features.ts:~59, jsonb copy of role/content/seq/status); `publishSnapshot` (service.ts:~125) owner-only, 404 for other users; test features.integration.test.ts:123-133 (later message not in snapshot, B cannot publish A's chat).
1. Contains every eligible message through cutoff, no later content - PARTIAL. Single un-paginated select, no explicit cutoff, no transaction/snapshot isolation; excludes thread linkage (parentMessageId), reactions, attachments (service.ts publishSnapshot selects only role/content/seq/status). Later content excluded only because copy is by value (Met for that part).
2. No credential/live file URL/tool handle/memory; unsafe content blocks publication - UNMET. No safety scan or DTO; assistant text may contain `zetta:*` tool blocks, redaction-hook secrets already sent, or file contents from `fileRefs`; nothing blocks or previews ("show exact representation before confirmation" missing).
3. Concurrent mutation/failed capture leave no partial - PARTIAL. Single INSERT is atomic and content is immutable by value; no DB-level immutability (no UPDATE/DELETE trigger or privilege), no idempotency key (double publish creates duplicates), no revocation/retention (RFC-001 policy), no confirmation step.
Gaps -> smallest implementation: (a) `publishSnapshot` in one `db.transaction` (repeatable read) reading messages + attachments + reactions with a recorded `cutoffSeq`; (b) a pure `toSafeDto()` that includes parentMessageId, reactions counts, attachment name+text copied inline; strips ```zetta:*``` blocks; fails with FeatureError("UNSAFE") (+reason) if an attachment/part cannot be represented; (c) `preview` endpoint returning the DTO, publish requires `confirm: true` + `idempotencyKey` (unique on owner+key+conversation+cutoff); (d) `revokedAt` column + BEFORE UPDATE/DELETE trigger (content immutable); (e) add `snapshots.test.ts` (>page-size conversation, thread, attachment freeze, unsafe part, retry idempotency). Needs only local Postgres. Not external.

## RFC-035 Team read-only snapshot viewer - PARTIAL (low)
Existing: `GET /api/snapshots` + `/api/snapshots/:id` (routes.ts, `access.requireActive`); Studio "Team snapshots" tab renders read-only (studio-page.tsx:183-192).
1. Team readers see frozen content, no mutation via snapshot ids - Met in practice (no mutating snapshot endpoints; chat endpoints key on conversation owner), but no test that proves it.
2. Non-members/removed members cannot fetch pages/bytes - PARTIAL. Authorization is `requireActive` (any active installation user) = team membership; removed/suspended members are blocked by identity layer; no snapshot-specific test, no attachment bytes route (none exist), no revoke/expire state (404 only).
3. Original chat continuing never changes viewer; no source link authority - Met (jsonb copy; test line 127-131). Viewer shows no timestamp/owner label (list returns ownerUserId only as id) and no thread rendering; no dedicated route (no `routes/_auth/snapshot.*`, only a Studio tab).
Smallest: add `snapshot-view` test file covering removed-member 403/404 and mutation absence; return owner display name + createdAt in viewer; render parentMessageId nesting; add revoked/unavailable empty state; optional route `_auth/snapshot.$id.tsx`. Depends on 034 DTO.

## RFC-036 Dispatch an owned specialist subtask - PARTIAL (low-medium)
Existing: `@mention` delegation in `converse` (chat/service.ts:70-76 resolveMentions: visible = own or team, not archived, `onboarded`, max 3; :209-222 loop; failure -> attention item). Test experience.integration.test.ts:94-105 (unready excluded, B sees team bot, B-private not reachable).
1. Chief invokes team/A-private specialists, not B-private bots or B connections - Met for bots (visibleBot filter); connections N/A (no bindings exist). Caveat: `onboarded` is checked on the specialist for any owner, including team bots owned by others, where the RFC wants initiator-based readiness; acceptable.
2. Child run records preserve initiator/parent/target version/context provenance - UNMET. Replies are plain `message` rows (botId, botVersion only); no parent/child run link, no `delegation` table, no provenance of which context was passed (the full prompt, history, files go to every mentioned bot).
3. Invalid target / missing connection / unsupported bridge gives visible result to chief without unauthorized launch - PARTIAL. Unknown/unready mentions are silently dropped (no visible result). No cycle detection (mentions in replies are not re-dispatched, so no recursion, effectively depth 1). No payload size limit specific to delegation. No host-tool bridge (RFC-006/013 not used; harness is CLI text only), the chief cannot choose to delegate; only the human types @Name.
Smallest: new `delegations` table (id, ownerUserId, parentMessageId, parentBotId, childBotId, childBotVersion, status, contextSummary, createdAt) written inside the mention loop; emit a system note message listing skipped mentions with reason ("not ready: open setup"); add a `zetta:delegate {botId, task}` fenced tool in `chat/tools.ts` (same text protocol, depth capped at 1, size cap) so the chief can delegate; tests for A/B visibility, oversize, unready setup-link. "Approved real harness bridge smoke" is BLOCKED-EXTERNAL (spends harness quota) - claude haiku smoke already exists in real-harness.integration.test.ts and could be reused.

## RFC-037 Aggregate bounded specialist work - UNMET (small partial)
Existing only: max-3 mention cap, failed delegated reply -> one attention item attributed to bot with resultLink to the chat (chat/service.ts:222).
1. Fanout/depth budgets hold; parent cancel cancels children - PARTIAL (fanout 3 hardcoded, depth 1 implicit); no cancellation propagation (no cancel endpoint for turns at all; SSE abort not wired to the child loop).
2. Mixed-success attribution, completed vs missing/uncertain, durable links - UNMET. No consolidated answer, no per-child summary, no delegation-status UI (`delegation-status.tsx` absent). Attention item has only a chat link, no child id.
3. Restart/replay without duplicate consolidation; repair and return - UNMET. Mentions run sequentially inside the request; a crash loses state; no replay idempotency.
Smallest: build on 036 table: add status per child, a final "consolidation" assistant message generated deterministically (list of bot name + complete/failed/uncertain + link `/chat?c=...#m=<id>`), an AbortSignal passed through `run.stream` that stops remaining children on client disconnect, attention dedupe key `(owner, delegationId)`; tests with fake runner. "Approved repair-and-return walkthrough" requires connection bindings (RFC-044) first and a human/browser pass: BLOCKED-EXTERNAL for the walkthrough.

## RFC-038 Owned schedules and routine actions - PARTIAL
Existing: `routine` table (features.ts), `createRoutine`/`setRoutinePaused` (service.ts), routes.ts `routine` zod (IANA tz validated via Intl, `dailyAt` HH:MM, `everyMinutes` 5..10080), owner scoping, bot visibility on create, activation requires onboarded bot (409 NOT_READY), test features.integration.test.ts:79-102.
1. A cannot create/edit/run B routine or inaccessible bot - Met for create/run/pause/delete (owner filter + `usableBot`); there is no edit endpoint at all. Conversation targeting does not exist (always a new conversation).
2. Invalid timezone/recurrence/missing bindings rejected with actionable errors - PARTIAL. Timezone and recurrence validated but error is generic "Check the details"; no bindings (RFC-044). `everyMinutes`+`dailyAt` both allowed (dailyAt wins silently); no one-time kind.
3. Pause/edit/archive semantics, missed/overlap policies documented and versioned; queued occurrences retain captured definition - UNMET. No `version`, no edit/archive, no documented policy (code behavior: claim-before-run advances to next from `now`, so missed occurrences are skipped, overlap = serial within a tick), no draft-with-missing-prerequisites list, no conversation-mode choice recorded, no `nextRun` definition snapshot.
Smallest: add `version`, `status` (draft|active|paused|archived), `kind` (once|daily|interval), `conversationMode` (new|continue) + `targetConversationId`, `missedPolicy='skip'`, `overlapPolicy='skip'` columns; `PATCH /api/routines/:id` with optimistic version; `missingPrerequisites()` returned on save; document policies in `docs/decisions/routines.md`; tests in `routines/definitions.test.ts` (or extend features.integration.test.ts). Pure local work.

## RFC-039 Timezone-aware scheduled occurrences - PARTIAL
Existing: `nextDailyRun` scans real minutes in tz (schedule.ts:1-14) -> DST aware; `runDue` claim = conditional UPDATE `nextRunAt = r.nextRunAt` (service.ts runDue) so two workers/ticks cannot both claim; readiness rechecked in `execute` (pauses routine + attention); 30s in-process tick (index.ts:24-25). Test: daily/DST at features.integration.test.ts:18, run-due at :89-97.
1. Two workers + restart at enqueue boundaries cannot duplicate - PARTIAL. Claim is atomic (good), but there is no `occurrence` row with unique (routine, version, occurrence_instant): if the process dies after claim and before `execute`, that occurrence is silently lost, and `runRoutineNow` has no idempotency. No multi-worker test.
2. DST gaps/folds/timezone changes/clock advance documented - PARTIAL. Scan of 48h finds wall time; in a spring-forward gap the nonexistent time yields no match that day (skipped, scan returns next day's) - undocumented, and fold (ambiguous time) picks the first. Existing test covers some DST case only.
3. Paused/deleted/unauthorized do not execute; no unbounded burst - Met largely: paused filtered in query, owner/bot check in `execute`; catch-up is one run (next computed from `now`). Deleted routine: runs deleted; membership removal is not rechecked (only bot visibility), and connection validity N/A.
Smallest: `routine_occurrence` table (routineId, routineVersion, scheduledFor, status queued|running|succeeded|failed|skipped|blocked|interrupted, unique(routineId,scheduledFor), runId/conversationId); `runDue` inserts occurrence `ON CONFLICT DO NOTHING` then executes; startup sweep marks `running` older than lease as `interrupted`; check membership active; add fake-clock tests for gap (02:30 America/New_York 2026-03-08) and fold (2026-11-01 01:30) plus Promise.all of two `runDue`. Postgres is local compose (no external needs).

## RFC-041 Routine run history and outcomes - PARTIAL (low)
Existing: `routine_run` (status succeeded|failed, output, conversationId, started/finished), `GET /api/routines/:id/runs` limit 20 owner scoped (service.ts routineRuns); failure -> attention item with resultLink `/chat?c=`; run-now button.
1. Occurrence identifies responsible bot and partial outcome; deliverable reopens after reload - PARTIAL. Each run creates a conversation (reopenable) but runs have no bot id (via routine), no partial outcome/supporting results, no pagination cursor (hard limit 20). Reads are owner-scoped (Met).
2. Skipped/blocked/interrupted not shown as success - UNMET. Status enum is only succeeded|failed; blocked (unready bot) just pauses routine + attention and creates no run row; skipped/interrupted/upcoming/queued/running states do not exist.
3. Run-now double submit creates one logical action; one source-linked attention item per blocked occurrence; repair returns without executing - UNMET. `runRoutineNow` has no idempotency key (double submit = two runs and two conversations); every blocked tick can raise a new attention item (the routine pauses so likely once, but no dedupe); attention has no link to occurrence.
Smallest: depends on 039's occurrence table: extend enum, add `occurrenceId` to attention (`source_ref`), `Idempotency-Key` on run-now (unique(routineId, key)), paginated `GET /api/routines/:id/occurrences?cursor=`, History panel in Studio; test for double run-now and state mapping.

## Cross-cutting findings
- All twelve RFCs are "Proposed/Not started" in tasks/*.md and TASKS.md; none has a Completion record. Existing code satisfies only fragments via the simplified path (checkpoint docs say so).
- No tests carry the RFC-named files; evidence is the 14 DB integration tests (features.integration.test.ts, experience.integration.test.ts). I did not run tests (read-only audit).
- Security-relevant gaps: snapshot content is unfiltered (tool fences, file contents may be republished to the whole team); routine/run-now have no idempotency; routine execution does not recheck owner membership status; delegated bots receive the full prompt incl. attachments (no explicit context selection).
