# Audit: RFC-064..068 and RFC-072..082 (2026-10-22)

Read-only audit against the simplified v1 path (see docs/release/v1-verdict.md, docs/checkpoints/chat-slice.md). Paths relative to repo root. Verdicts: Met / Partial / Unmet. Tag BLOCKED-EXTERNAL = needs external accounts, paid calls, installs or infra approval. RESEARCH = research/decision only.

## Cross-cutting facts used as evidence
- Attention: table `attention_item` (packages/db/src/schema/features.ts, status open|acknowledged|resolved, source routine|workflow|manual|bot; NO dedup key, NO parent/run/step ids, NO partial-work fields). Service: apps/server/src/modules/features/service.ts:104-111 (list/add/setStatus, owner-scoped). Producers: routine pause/fail (service.ts:32,43), workflow fail (service.ts:130), delegated fail (chat/service.ts:~222), handoff (chat/service.ts:36-38). Chat config proposals do NOT create attention items.
- Workflow: single `workflow` row with jsonb graph + integer version, overwritten in place (service.ts:114-119); `workflow_run` stores final status + trace (features.ts). Graph schema apps/server/src/modules/features/workflow.ts:3-24 (prompt/condition/decision/browse/end, <=20 nodes, dangling-edge check only; cycles bounded at runtime by MAX_STEPS=30, workflow.ts:28). Execution is synchronous in-request (service.ts:120-132).
- Computer: apps/server/src/modules/computer/service.ts, Playwright-core persistent Chromium per (user, profile string), in-memory sessions, `control: agent|human` flag (L15, L92). Routes computer/routes.ts. Tests computer/computer.test.ts (SSRF unit test; real Chromium only when ZETTA_COMPUTER_TEST=1, else skipped).
- No audit module, no recovery doc, no isolation-matrix test, no v1-workflows test, no release-readiness doc exist (verified by find). docs/decisions/browser-computer.md exists (research only, "RFC-074 remains incomplete").
- Old RFC machinery (apps/server/src/modules/runtime/*, journals/dispatch) is present but unused by the product path.

## RFC-064 Privacy-safe execution audit views -- UNMET
Criteria:
1. Partial incidental coverage: routineRuns (service.ts:86).

3. Cross-user activity isolation + admin policy: Unmet (no activity endpoints; per-row owner scoping exists elsewhere).
Gaps: audit module, schema/table or evlog wide-event wrapper, activity route/UI.
Smallest implementation: table `audit_event(id, owner_user_id, kind, actor_bot_id, run_ref, parent_ref, status, reason_code, duration_ms, created_at)` with a closed enum of reason codes and NO free text; helper `recordAudit()` called from routine execute, delegated failure, workflow run, hook stop/background, memory/instruction write, config proposal decide, computer takeover; `GET /api/activity` owner-scoped (admin gets only counts/metadata); test in apps/server/src/modules/audit/events.test.ts with synthetic-secret canary asserting DTO + captured console output contain no canary. ~1 session.

## RFC-078 Secure takeover and hand-back -- PARTIAL
Criteria:
1. Only owner can view/control; stolen/expired links, revoked sessions, two-controller races fail safely: Partial. Owner-only by userId-keyed sessions behind cookie auth + origin check (computer/routes.ts); no tokens/links so none to steal, no expiry, no race handling on the control flag (takeover() just flips it, service.ts:92; no check of who holds it; user and agent actions are not mutually serialized apart from the flag check at act time).
2. Passwords/MFA never in retained frames/events/chat/memory/snapshots; bot input suspended: Partial. Agent actions are refused while human has control (service.ts:68, test L26-37 env-gated). But screenshots endpoint is available during takeover to the owner only (acceptable), and nothing prevents the bot from reading page text (`text()`, innerText) of a login page or the typed value; typed credentials by `type` action from user path are not logged (no logging), but the bot's own `type` action text is stored in message tool blocks (chat messages contain the typed text) -> bot-typed secrets would be retained in chat history. No explicit secret-suppression layer.
3. Complete human step and return to same task; honest recoverable state: Partial. handoff tool creates attention item (chat/service.ts:36-38) pointing to /studio; Studio>Computer tab takeover/hand-back (studio-page.tsx:229+); hand-back does not resume the bot task nor verify page state; attention not auto-resolved (good), no "same task" link.
Smallest: on hand-back (takeover human=false) verify session alive and add a `hand_back` event that resolves the linked attention item only if the page URL is no longer the login URL (store attention.source_ref=profile); store the originating conversation id so the card can link to /chat?c=...; add `redact` of `type` action text in persisted tool blocks (replace with "[typed N chars]"); add single-controller compare-and-set; tests with fake page. Secret-suppression for frames/logs = needs real browser: partially BLOCKED-EXTERNAL.

## RFC-080 Durable workflow execution -- UNMET/Partial
Criteria:
1. Manual and scheduled follow same published graph/actor, no duplicate steps on repeated request/occurrence ids: Partial. Manual run exists (service.ts:120-132) with actor identity and readiness not rechecked (usableBot only checks visibility, not onboarded; contrast routine execute which checks onboarded, service.ts:29). 3. Crash/cancel/lease preserve results, never replay uncertain: Unmet. No per-step persistence, no cancel, no recovery; a crash loses the run entirely (no row). The old runtime journal machinery is unused.
Smallest: (a) add onboarded check in runWorkflow's bot callback (same rule as routine execute); (b) add `requestKey` unique(owner, workflow, key) to workflow_run and return existing run on repeat; (c) persist the run row at start (status running) and update trace after each node, with status enum extended to running|failed|succeeded|cancelled|interrupted, and on boot mark stale `running` rows interrupted (never replayed); (d) add `workflowId` nullable on routine + execute path calling runWorkflow with occurrence key = routine id + nextRunAt; (e) record skipped nodes (unvisited targets of taken condition).
