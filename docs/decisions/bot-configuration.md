# Versioned bot configuration and actor readiness

Status: design accepted by coordinator after [independent CLEAR review](../reviews/bot-configuration-020a-review.md),2026-10-22. Design only. Pure020b implementation may be separately assigned; schema, service, route, browser, native harness and database gates remain explicit. RFC-020 remains incomplete. Only this acceptance status was added after the reviewed content freeze.

## Reused policy and boundaries

Sources: [confirmed intent](../intent/zetta-v1.md), [ownership](ownership.md), [connections](connection-secrets.md), [durable runs](durable-runs.md), [dispatch](durable-dispatch.md), [harness research](harness-compatibility.md), [020](../../tasks/020-implement-versioned-bot-configuration.md) and [021](../../tasks/021-build-bot-onboarding-and-settings.md). The issued-actor and fresh-membership boundary from RFC-005 and closed capability contract from RFC-006 remain mandatory.

A specialist defaults to team visibility. Its owner alone edits, changes visibility or archives it. Active B may use a team bot with B's own accounts and B's readiness. Admin has exactly the same private-content restrictions. A chief is private and unique per owner, including archived chiefs; creating another chief cannot evade that identity. No editor lists, organization model, ownership transfer or new RBAC system.

Bot identity, immutable execution configuration and execution actor are separate identities. A bot never supplies an execution user. Removed owners suspend use of their team bots; removed actors cannot read or run them. Archive blocks new work and preserves private historical runs. Neither archive nor visibility changes erase a run's accepted snapshot.

No harness is made operational by this proposal. Accepted research establishes candidate transports and unresolved protocol/isolation requirements, not a working native adapter. RFC-007 native-profile storage, private credential issuance, RFC-008 containment, RFC-010 admission, per-harness compatibility and the RFC-020 public-producer resource queries remain explicit gates. Fixture success and a caller's `native` or `ready` flag cannot satisfy them.

## Minimal records and bounds

These are proposed logical records, not existing tables. Schema assignments must name their actual columns and constraints before generation. Use UUID server-generated identities, positive PostgreSQL int32 revisions/versions, UTC timestamps and restrictive deletes. No foreign key to a future resource table.

| Record | Minimal fields and ownership |
| --- | --- |
| Bot | id, immutable owner user, kind chief/specialist, visibility private/team, lifecycle active/archived, current configuration version, lifecycle/configuration revision, presentation revision, name, description, created/updated/archive timestamps. Chief must be private; unique owner chief identity. |
| Configuration version | bot id + sequential version, immutable canonical share-safe execution definition, schema version 1, creation time. Configuration identity exposed to RFC-009 is bot id plus this version; no second independent configuration counter. |
| Actor binding version | actor user + bot id + sequential version, immutable canonical private binding snapshot and creation time. No shared default account. Latest version is selected under bot/member locks; absence means unconfigured. |
| Setup session | id, actor/bot/configuration/binding identities, exact canonical readiness descriptor and digest, bounded state, trusted native response evidence reference, confirmation challenge and times. Private to actor. |
| Mutation receipt | actor + operation UUID unique, method and exact bounded canonical arguments, original safe result. Private, retained for same-operation repair; never a credential or instruction log. |

Only existing membership/user identities, existing connection identities, and records introduced in the same accepted feature may have FKs. Connection binding ownership/version needs the accepted composite connection identity, not merely a globally valid connection UUID. Instruction, skill, hook, memory and native-profile reference backends require their own accepted ownership/version contracts before enabling those slots; initially reject nonempty unsupported slots, rather than treating opaque strings as validated resources.

Proposed limits are UTF-8 byte limits measured before storage: name 1–80 Unicode scalar values and at most320 bytes; description at most2048 bytes; personality at most4096; explicit inline instructions at most16384. No NUL. Definition canonical text at most32768 bytes; binding text at most16384. At most16 instruction/skill/hook references in total and16 integration requirements. Identifier values use the accepted006 canonical ASCII grammar and maximum128 bytes; provider slugs use lowercase ASCII letters/digits/hyphens,1–64 bytes. Unique sorted requirement keys; no duplicate resource references. Schema parsers reject unknown keys, unsafe numbers and oversized collections before DB work.

Definition v1 contains harness enum (the six intended native harnesses; fixture excluded), optional model provider/id, personality, explicitly authored shared instructions, versioned public-catalog references, required006 capabilities, and integration slots `{key, provider, kind, required}`. A model id is a bounded opaque provider selector, not a resource ID:1–128 ASCII characters, leading alphanumeric followed by alphanumeric/dot/underscore/colon/slash/hyphen. Reject URL syntax `://`, control characters and slash-delimited `.`/`..` path segments. Dotted or provider-qualified selectors are permitted structurally; actual catalog availability/ownership/entitlement remains setup work. This clarification follows the coordinator's reproduced020b rejection of a dotted selector and changes no resource identity grammar. Null model means the harness's selected default must be resolved and pinned during setup; changes to that resolved default invalidate readiness. Capability names come only from006; unsupported requirements fail, never silently downgrade. No arbitrary URL, command, environment, executable path, account display name, credential or native filesystem selector.

A binding maps requirement keys to actor-owned pinned connection/version identities and, when supported, opaque native-profile revision or private resource revision. Model selection that depends on an actor's account resolves privately here. Private instruction/memory sources never become definition fields by copying the actor's resolved prompt. Definition text is intentional audience-visible content: the service cannot reliably recognize a secret pasted into prose. Publication therefore needs explicit audience preview and deliberate human submission; no automatic promotion from a conversation or private resource.

Assembly must also satisfy009's prompt and canonical-input byte caps. Accepted individual fields do not guarantee their concatenation fits. Reject an oversized resolved snapshot with a bounded repair reason; never truncate instructions or replace versions implicitly.

## Lifecycle, edits and visible results

Create specialist produces active bot/version1 and default team visibility after an explicit audience-visible submission. Ensure-chief is idempotent for the actor and returns the unique chief; it never returns another user's chief. An archived chief remains that chief. An explicit owner restore may reactivate an archived bot, but creates a new semantic configuration version and requires new readiness; archive history remains immutable.

Every execution-affecting edit appends a version and CAS-updates the current pointer in one transaction. Expected configuration version is mandatory. Harness/model/personality/instructions/resources/requirements and publication audience changes are semantic. Name/description use an independent expected presentation revision and do not invalidate readiness. A no-op normalized edit returns the existing version. Counters never wrap; exhaustion rejects the edit. Archive and restore also require expected current version and a separate lifecycle CAS token (the bot's updated revision); the schema slice should implement one monotonic bot revision for all non-presentation changes.

Private-to-team publication creates a newly approved share-safe version. It does not expose old private versions, their diffs or bindings. Team-to-private immediately removes B's access to definition/use. B's historical run remains B's private snapshot, independently authorized by009; it does not grant continued access to the bot. Shared readers receive only the current published version while the bot is currently visible. Full configuration history is owner-only. Archive metadata may be shown to an authorized historical owner, but does not permit use.

Visible list/read DTO: bot id, kind, name, description, current version, lifecycle, visibility and `canEdit`; current definition may be fetched separately under the same visibility check. Do not return owner account names, binding IDs, profile paths, private reference IDs, another actor's setup status or readiness digest. Unknown/private IDs both return fixed `not_found`. An accessible bot owned by an inactive member returns fixed `owner_unavailable` on use without disclosing membership details. Lists use bounded pages (default20, maximum50) and actor-bound authenticated cursors tied to filters; recheck membership and visibility on every page.

Private binding DTOs expose only the actor's opaque selections and revision. Private readiness DTOs use closed states `needs_configuration`, `technical_blocked`, `needs_test`, `awaiting_confirmation`, `ready`, `stale`, plus fixed repair codes and a return target. Never return raw adapter errors, credential material or another actor's account availability. Technical failure and human dissatisfaction are different reasons.

## Authorized service contract and mutation repair

Proposed operations: create specialist/ensure chief, get/list visible, get owner version history, edit presentation, append definition, change visibility, archive/restore, get/update my bindings, get my readiness, start/continue setup, confirm/reject setup. Forms and any-bot chat call these same services. Chat may propose an exact diff with expected revisions and audience; applying that proposal requires the same authorized human approval as forms. A model/tool invocation cannot supply that approval or confirm satisfaction.

All methods require a005-issued actor and fresh active membership; owner writes additionally compare the locked bot owner. B/admin substitutions, structural actors and forged setup evidence fail. For own-binding writes, actor identity comes exclusively from the issued actor, never a body user ID. Validate syntax before receipt lookup; lock and authorize before returning any receipt. Exact canonical same-operation replay precedes stale-version rejection and returns its original safe result, not a newly fabricated success. Different method/target/semantic argument under the same operation UUID yields `operation_conflict`. No receipt replay restores archived state or bypasses current read authorization.

Persist mutation and receipt atomically. A failed commit acknowledgment yields fixed `outcome_unknown`; the caller retries the identical operation UUID/arguments for readback repair. Never generate a new operation automatically after an unknown outcome. Stale edit returns fixed `version_conflict` plus an authorized current revision for reload/diff; preserve unsaved client work. No request can submit executable configuration by referencing an unvalidated UUID.

## Readiness and real human confirmation

Readiness is derived from three independent facts: current technical prerequisites, an actual successful native setup response for this exact descriptor, and explicit positive human confirmation of that response. Technical checks alone cannot mark ready. The descriptor includes actor id and enrollment epoch, bot id and owner enrollment epoch, configuration version/digest, actor binding version, all pinned resource/credential/profile revisions, resolved model, adapter compatibility/protocol revision and readiness-policy revision. Store bounded canonical descriptor plus SHA-256 digest; compare exact descriptor as well as digest. Digests are private and not bearer capabilities.

The accepted dispatch ADR already identifies the missing non-reusable membership activation epoch. Re-enrollment cannot restore an old confirmation. The smallest proposed005 extension is a server-generated, non-reused UUID activation epoch on membership: create one on initial activation and replace it on every inactive-to-active transition under the membership lock. Repeated activation of an already-active member preserves it. Backfill existing active memberships once in a reviewed migration; absence fails closed. Readiness evidence and producer provenance pin both actor and bot-owner epochs. Removal first marks inactive and persists010 cancellation intent under its accepted transaction order; subsequent checks deny immediately. Reactivation assigns a new epoch, so retained confirmations and queued provenance cannot become valid again. Historical records remain readable under their separate owner policy and never rewrite their pinned epoch.005 activation/removal and010 provenance changes require separate bounded source and actual race/restart proofs before readiness is enabled. Current membership timestamps are not assumed to provide this property. This is an integration blocker, not an invented existing column.

Setup starts only from an explicit human request for this actor and bot. A trusted setup producer resolves the exact current descriptor and creates a bounded setup run through reviewed009/010 integration. Proposed session budget: at most8 human turns within30minutes, each subject to the stricter accepted attempt duration/output limits. A setup run permits only conversation/testing and inert configuration proposals; it cannot delegate, schedule, execute workflows, run arbitrary host tools or obtain general ordinary-run authority. Enforce that restriction transitively at producer/action admission, not through a UI flag or prompt instruction.

Setup states: `testing → awaiting_confirmation → confirmed|rejected`; any meaningful descriptor/access change makes it `stale`, and deadline expiry makes it `expired`. Failed/uncertain/cancelled/fixture runs cannot advance to awaiting confirmation. Trusted response evidence must bind the actor, bot, descriptor, run, attempt, selected adapter/model and a nonempty successful response. The native provenance is issued by the accepted adapter/admission path, not accepted from caller JSON. Until that path exists, setup is technically blocked.

After the actual response, the UI presents a fresh server-issued challenge and asks whether this setup is satisfactory. Yes or an explicitly correlated positive human reply confirms; Keep adjusting rejects and preserves the draft. Silence, reactions, ambiguous text, model-generated consent and an old challenge cannot confirm. Human-authenticated confirmation must match the still-current descriptor and unexpired question (30minute setup deadline). Confirmation consumes the challenge once, with operation replay supported. Another actor cannot answer it. Further meaningful adjustment requires another real response and confirmation. Confirmed readiness has no arbitrary periodic consent TTL; it remains conditional on every descriptor/access prerequisite remaining current.

Readiness of A never affects B. Connection replacement/revocation, changed private resources/model/profile, configuration change, owner/actor removal, restore, or adapter-policy incompatibility fail the next readiness comparison. Do not substitute a newer connection or model automatically. Public consumers cannot accept a stored `ready=true` without these checks.

## Transaction order and public producer gate

Proposed order, conditional on the005 normalization below; it is NOT compatible with every current identity writer: **capacity gate when applicable → all relevant memberships sorted by user id → connections sorted → key-check singleton when needed → bots sorted → actor-binding rows sorted → setup/readiness rows sorted → runs → attempts → claims → grants**. Every operation uses a forward subsequence and rereads predicates after locking. Existing007 and009 paths retain their order. New020 public paths lock both actor and bot-owner membership before connections/bot; do not discover and lock another member after bot/run locks. Read candidate identities without locks, then lock/revalidate immutable ownership. No lock spans human, browser, harness or network interaction.

**Blocking identity-order audit:** current `apps/server/src/modules/identity/enrollment.ts:61–72` locks installation → active-admin membership → actor auth account; invitation acceptance then locks subject membership at138–140. `admin-lifecycle.ts:116–121` instead locks installation → sorted auth accounts → sorted memberships. If B sorts before admin A and uses A's team bot,020 can hold B and wait for A while the existing admin-first enrollment path holds A and waits for B. A removal path using that prelude has the same cycle. Sorted020 members alone therefore do not establish a unified graph, including for team reads.

Selected smallest proposed prerequisite: normalize005 identity writers to **installation (identity writers only) → all required auth accounts sorted → all required memberships sorted → invitations/session mutations/audit**, collecting the admin/actor/subject IDs from the locked installation and validated request before taking member locks, then rechecking active-admin and subject predicates after locks. Preserve bootstrap/replacement authorization; do not move an authorization decision outside the transaction.020 and dispatch take only the sorted-membership-and-later subsequence and never acquire installation or auth-account row locks afterward. Existing single-member007/009 transactions remain subsequences, but their complete FK/trigger/session interactions must be audited in that bounded integration. This uses the existing short identity singleton transaction only for identity writers; it does not add a global bot mutex. The normalization is a separate reviewed005 change, not authorization to edit accepted identity code here. Actual lock-observed enrollment, replacement and removal against cross-owner bot read/use in both orders, including A/B lexical reversal, are required before enabling020 team services. If normalization is not accepted, keep team operations blocked and return to design; do not substitute unlocked snapshots or claim deadlock safety.

Bot mutation serializes through its row; own-binding insertion additionally uses that bot row to serialize absence and latest-version selection. This deliberately serializes bindings for a single shared bot, avoiding a new mutex framework. Confirmation locks connections before bot/binding/session and recomputes the descriptor. Owner removal can deny subsequent use through its membership row without scanning or locking every B binding while holding B resources. Re-enrollment non-resurrection remains epoch-gated. Removing access after admission invokes010 cancellation/reconciliation rules; it cannot undo an already delivered effect.

Ordinary submission must atomically query visible active bot/current version, fresh actor and owner membership, actor-owned binding provenance, current technical prerequisites and matching confirmation before inserting009 run/current attempt. Conversation ownership is also checked once025 supplies that real resource. The public request cannot choose another actor, bypass via setup origin or supply an arbitrary configuration/version. Stale versions fail rather than silently following latest. Claim and each action admission recheck eligibility and pinned resources; a semantic change blocks pending old work and requests cancellation of admitted work through010's existing coordination, without rewriting historical snapshots.

This requires a reviewed transaction-bound009 producer entry point, not calling the current store in a separate transaction after releasing020 locks. The implementation must also extend010 admission queries before enabling native/public work. No grant path may acquire bot/membership after run/grant locks. These integration changes are separate assignments and actual race proofs, not implied by accepting this design. Future schedules/delegation/workflows must present their own stored owner/version provenance and the same readiness gate; none is enabled by020.

## Bounded child slices and proof gates

1. **020b closed definition/binding contracts:** pure schemas, normalized canonical arguments, safe DTOs and focused tests. Keep unsupported resource/native slots closed. No database or public producer.
2. **020c bot/version schema:** one schema owner, feature generator/config and reviewed constraints, then separately authorized disposable PostgreSQL proof. Immutable versions, chief uniqueness, current-pointer integrity, bounds, publication history and restrictive retention. No future-resource FKs.
3. **020d authorized configuration store:** at most five product files per assignment; issued actors, owner writes, visibility reads, CAS, receipts and actor bindings. Split bindings/receipts into a child if necessary. Actual PostgreSQL A/B/admin, forged actor, removal, duplicate operation, stale edit and unknown-commit proof before routes.
4. **020e readiness storage/services:** only after membership epoch, unified identity lock order, native-profile/resource provenance and trusted adapter evidence contracts are accepted. Separate technical evaluation, setup evidence and explicit-human confirmation. Actual DB concurrency and true-process readback; fixtures are negative readiness controls only.
5. **020f public producer/admission:** narrow009 transaction integration and010 rechecks assigned serially to their owners. Actual lock-observed submit/edit, confirm/revoke, removal/claim and visibility/dispatch races in both orders. No native enablement until containment, credential issuance and real harness gates pass.
6. **021 UI and073 chat consumers:** forms/drafts, audience preview, exact-version proposed edits, account repair/return, actual response and Yes/Keep adjusting. Share service contracts, not duplicated authorization. Separate real-browser proof and a separately approved real-harness/account proof.

Each child gets exact source ownership, focused tests, strict diagnostics, source hashes and independent review. Schema/code scopes are not approved by this proposal. Root retains020/021 status and assigns slices individually.

Actual PostgreSQL proof must exercise valid controls and constraint-specific failures; independent connections plus observed `pg_blocking_pids` establish both race orders. Cover chief-create races, immutable version/pointer constraints, A/B same operation independence, receipt conflict/commit-loss repair, private-to-team old-history denial, B/admin private substitution, binding ownership/version mismatch, A-ready/B-not-ready, re-enrollment non-resurrection, archive/restore, expiry at the locked DB clock, and descriptor change against confirmation/submission/admission. Assert retained history and no extra run/attempt/grant, rather than merely observing an exception.

Real-browser proof uses separate authenticated A/B/admin sessions: list privacy, empty/loading/error states, stale edits with retained drafts, keyboard/focus and mobile layout, publication preview, repair-and-return, refresh/reconnect during setup, explicit confirmation and any-bot-chat proposal parity. Rendering a button is not authority evidence. Private values must not appear in B network responses, page state or error text.

Real-harness proof records pinned verified binary/protocol, isolated actor-owned account/profile, selected/resolved model, admitted setup run and actual response, followed by a real human's explicit correlated confirmation. Then prove an ordinary request succeeds only for that actor/descriptor and that a meaningful account/configuration change denies it until retested. Never automate or synthesize human satisfaction. Neither a fixture nor CLI discovery replaces this gate. HTTP, deployed SQL least privilege and native containment claims require their own actual evidence.
