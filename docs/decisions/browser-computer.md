# Isolated browser and computer backends

Status: source-supported candidate accepted for bounded provisioning planning after [independent CLEAR/APPROVE review](../verification/reviews/browser-074a-review.md), 2026-10-22. This is the bounded [RFC-074a](../../tasks/074a-research-isolated-browser-computer-backends.md) handoff. **RFC-074 remains operationally incomplete.** No backend, viewer, account, model, container or VM was started. The user's authorization to continue v1 permits this early research; it does not turn the pending six-harness proofs into completed prerequisites. Component installation/distribution, the exact reproducible image and actual Xvnc/native-image/takeover proofs remain separate gates.

## Recommended paths

Use two independently testable capabilities behind the accepted [execution boundary](execution-isolation.md): **agent-browser for web**, and **standalone Cua Driver on a private Linux X11 desktop for full computer use**. For human desktop viewing/input, evaluate **TigerVNC Xvnc + noVNC + websockify**, separately from the driver. Do not require Cua Spaces, a paid service, macOS host control, or the user's existing browser/profile. These are viable source-supported integration candidates, not a verified working image or dependency approval.

Keep the harness/code-execution sandbox separate from the GUI sandbox. The trusted broker alone connects to browser/CDP/driver/X11/VNC channels. The harness receives only actor/run/attempt-bound host tools, never those raw channels, display sockets, profile mounts or viewer credentials. Otherwise arbitrary code in the harness could bypass a paused tool gate and capture passwords or inject input. Only the trusted launcher has Docker authority; neither application server nor attempts receive its socket. Per-actor isolation still needs exclusive per-profile/per-desktop leases so simultaneous runs by the same actor cannot race.

### Browser boundary

The [session contract](https://github.com/vercel-labs/agent-browser/blob/468c0526c884722afd9c10bcc0d5b09ed4c0c5d1/docs/content/docs/sessions.mdx) supports a custom `--profile <path>` and separate session/namespace. Persist only a launcher-selected actor-owned profile; never use a browser profile name, host auto-connect, imported cookies, or model-supplied paths. Session names are process routing, not user authorization. Saved-state encryption covers saved cookie/localStorage state, not an entire Chromium profile. The [secrets ADR](connection-secrets.md) expressly leaves native-profile storage unsupported until its own proof; do not put profile archives in API-key blobs.

The [stream contract](https://github.com/vercel-labs/agent-browser/blob/468c0526c884722afd9c10bcc0d5b09ed4c0c5d1/docs/content/docs/streaming.mdx) supplies JPEG/base64 `frame` messages, URL/status updates, and `input_mouse`, `input_keyboard`, `input_touch` over a local WebSocket. It starts automatically and is bidirectional; origin restrictions are not Zetta actor authentication. Keep it internal and proxy only the selected owner's stream. Suppress URL, console and tab metadata during secret entry; URLs may contain OAuth codes. Do not use the page's old TypeScript `BrowserManager` example as proof of an exported SDK: the pinned package ships a native CLI. Browser viewport streaming does not capture native file pickers or prove full desktop use.

The [security contract](https://github.com/vercel-labs/agent-browser/blob/468c0526c884722afd9c10bcc0d5b09ed4c0c5d1/docs/content/docs/security.mdx) adds domain/action guards, but excludes persistent/existing-profile/CDP and restore combinations from equivalent domain containment. Enforce egress below the browser: DNS, redirects, subresources, WebSocket, IPv4/IPv6, private/control networks, host gateway, metadata and direct/proxy bypass. Never substitute flags or a proxy environment variable for that proof.

### Standalone full desktop boundary

[MCP documentation](https://github.com/trycua/cua/blob/688c5fd62a9f13dddc309970c948df494e7de33f/libs/cua-driver/docs/mcp-protocol-and-skills.md) defines stdio JSON-RPC 2.0 with legacy MCP `2025-06-18` initialization or modern `2026-07-28` per-request metadata/discovery. Select legacy initially where the harness bridge supports it; pin negotiation rather than calling it “MCP 2.” Modern HTTP is explicitly not equivalent. Start the standalone driver inside the GUI sandbox, with private HOME/runtime directories and no inherited host-daemon attachment. The broker owns stdio and proxies only approved tools.

The [portable desktop registry](https://github.com/trycua/cua/blob/688c5fd62a9f13dddc309970c948df494e7de33f/libs/cua-driver/rust/crates/cua-driver-contract/src/desktop.rs) exposes `list_windows`, `get_window_state`, `get_desktop_state`, click/drag/scroll, text/key/hotkey, window geometry and `clipboard_read`/`clipboard_write` across Linux/macOS/Windows. [Linux clipboard implementation](https://github.com/trycua/cua/blob/688c5fd62a9f13dddc309970c948df494e7de33f/libs/cua-driver/rust/crates/platform-linux/src/clipboard.rs) uses a native clipboard backend. These operations do not require spacesd. Their existence is source evidence, not a successful Zetta desktop action.

[Linux guidance](https://github.com/trycua/cua/blob/688c5fd62a9f13dddc309970c948df494e7de33f/libs/cua-driver/rust/Skills/cua-driver/LINUX.md) and [action support](https://github.com/trycua/cua/blob/688c5fd62a9f13dddc309970c948df494e7de33f/libs/cua-driver/docs/action-support.md) distinguish X11 foreground XTest/AT-SPI from refused background actions. Provision one private X11 server, WM and D-Bus/AT-SPI session per desktop; do not mount host `/tmp/.X11-unix`, session bus or devices. Foreground automation is confined to that virtual desktop and exclusive automation lease. Capture refusal, stale target, `background_unavailable` and unverifiable effects remain explicit failures; no host-display fallback. Xvfb evidence does not establish real Xorg/uinput, Wayland, arbitrary toolkits or the proposed Xvnc combination.

Human takeover uses noVNC through a same-origin authenticated broker and fixed private websockify target. [Xvnc options](https://github.com/TigerVNC/tigervnc/blob/081403d0e3088377c233f170d5a667dc39c8f0dc/unix/xserver/hw/vnc/Xvnc.man) include localhost binding, key/pointer admission and clipboard direction controls. Disable clipboard synchronization in both directions at the server, not merely hide UI buttons. Do not expose VNC/websockify directly or let a request select an arbitrary destination. The gateway owns membership, owner, CSRF/origin checks, lease expiry and connection closure; stock VNC passwords and noVNC `viewOnly` do not implement these rules.

## Ownership, takeover and recovery requirements

These are proposed downstream contracts, not implemented APIs. Reuse [ownership](ownership.md), RFC-006 actor/run/attempt identity, and RFC-008/010 lifecycle authority.

- Bind desktop, profile, downloads, clipboard and observations to the initiating actor; schedules use routine owner, delegation preserves actor, shared bots/workspaces grant nothing. Explicit same-user profile sharing still takes an exclusive lease. A second run queues or gets an attention item; it never opens the same profile concurrently.
- Use launcher-owned profile storage with encryption-at-rest, key custody, exclusive mounts, atomic clean checkpoints and restore proof before enabling persistence. Ephemeral scratch, downloads and clipboard are separate. Downloads have size/time quotas, safe names, symlink/traversal protection and owner-checked export; never expose raw guest paths. Disable clipboard managers/history, browser tracing/HAR/video and driver recording. Clear guest clipboard before/after takeover and teardown; no host clipboard sync.
- State transitions: automation → quiescing → human-secret → hand-back → automation, plus revoked/failed. Close automation admission first; cancel/drain pending work and attest no input/observation remains before enabling human input. If quiescence is uncertain, do not show a login-ready screen. The harness cannot directly reach GUI processes/files/channels. Stop model calls, screenshots, DOM/AX reads, clipboard reads, logging, learning and queued observer results throughout secret entry. All other viewers close; only the authenticated owner sees ephemeral frames.
- The owner explicitly hands back after leaving credential screens. Clear clipboard, discard buffered frames/input/URL events, invalidate snapshot IDs and mint a new lease epoch before fresh observations. Do not infer hand-back from inactivity, password masking, or a classifier. Screenshot redaction is insufficient because DOM/AX/clipboard/network traces can retain secrets. Enforce the same barrier on error/reconnect paths and analytics/session replay.
- Use authenticated same-origin WebSockets with server-side owner/session/epoch checks, secure session cookies and origin validation; no URL bearer tokens, VNC passwords in URLs, raw screenshots, typed text, URL query strings or stream payloads in access/app logs. Reauthorize initial attach and active leases; membership removal, logout/revoke, connection replacement or deadline closes active sockets and denies further input/observations. A viewer disconnect does not automatically resume automation.
- On crash, revoke control first, terminate owned GUI/driver/browser descendants, reconcile launcher receipts and release leases only after confirmed stop. Quarantine a dirty profile/checkpoint. Restart creates a new attempt/epoch and requires safe owner repair where login state is uncertain. Never replay uncertain clicks/submissions; preserve partial results and link an owner-only attention action back to the source run. Token expiry or a successful driver `end_session` is not proof that OS children stopped.

## Amendment 2026-10-23 (2): desktop through Cua Spaces (RFC-077)

Desktop (whole-screen) computer use is **available** when `ZETTA_DESKTOP_RUNTIME=cua` and the `cua` CLI (>= 0.6) is installed. `apps/server/src/modules/computer/desktop.ts` talks to `cua mcp` (stdio MCP) and, per (user, profile), creates its **own local Linux container Space** (`create_space on=local kind=container`, name `zetta-<hash>`). Every action targets only `local:zetta-<hash>`: the host Mac or any `relay:`/`direct:` computer is never addressed, and a pre-existing Space is adopted only if it is exactly a local container with the expected name. Actions: click, type, key, scroll, launch (plain app names only), screenshot (PNG), and a text read (the Space's accessibility tree) for bots; control/takeover with epoch and compare-and-swap as for browser sessions; limits (1 desktop per user, 3 total), idle reaper, Space deleted on close. Bots use it with the `zetta:desktop` tool (needs onboarding, counts against the per-turn action budget). Studio > Computer shows the live screen with click/type/take-over/hand-back.

Evidence: unit tests with a fake Cua (`desktop.test.ts`), a real-Cua test (`ZETTA_DESKTOP_TEST=1`: two users get two container Spaces, real PNG screenshot, accessibility text, Space deleted), and a browser walkthrough of the Studio panel. Limits: the Space image has no browser pre-installed guarantee (use `launch`), Cua's local runtime must be present on the server host, and audio/clipboard/teleport features of Cua are not used.

## Amendment 2026-10-26: persistent per-user VMs (cua-spacesd)

`ZETTA_DESKTOP_RUNTIME=docker` replaces the Cua Spaces CLI path for desktop use. The changes:

- `apps/server/src/modules/computer/vm.ts`
- `docker/desktop`
- the `computer_vm` table
- a `create_vm` proposal kind

**The image.** Each VM is a container from our own image: `debian:trixie-slim`, Xvfb, Openbox, Chromium, and AT-SPI with `ACCESSIBILITY_ENABLED=1`. It runs the pinned glibc **cua-spacesd 0.8.0** release, sha256-checked. The static release build ships without the driver registry: `/mcp` returns 501.

**Control.**

- The broker is the server. It talks MCP over Streamable HTTP to spacesd on a loopback-published port.
- The bearer token is minted per start and never leaves the server.
- No Cua relay, cloud or host computer is involved.

**cua-driver on Xvfb, as verified against 0.8.0:**

- Background input is refused, because it needs uinput, which a virtual X server cannot add. All input is therefore `delivery_mode: "foreground"`, confined to that VM's private display.
- Coordinate clicks and scrolls use `scope: "desktop"`.
- Bot text reads walk Chromium's AT-SPI tree with `get_window_state`.
- The driver's `browser_*` tools need an existing-profile consent grant, so they are not used. Navigation is address bar, then type, then Enter, after the usual public-address check.

**Persistence and state.**

- `/home/agent` is the named volume `zetta-vm-<id>`, so sign-ins persist across idle stops.
- On boot, the image clears Chromium's singleton lock and the stale X lock left by the previous run.
- Each VM has one exclusive control lease, as before: human takeover, an epoch, and compare-and-swap.

**Licences.** spacesd is FSL-1.1-MIT; cua-driver is MIT. The licence and third-party notices are copied into `/usr/share/doc/cua-spacesd` in the image.

**Still open:**

- host-level egress filtering (see runtime-modes)
- a WebSocket media stream: the live view currently polls screenshots
- gVisor has not been exercised

**Evidence:**

- `vm.test.ts`: fake CLI and fake spacesd.
- `tools.integration.test.ts`: the `create_vm` proposal against Postgres.
- `vm-docker.test.ts` (`ZETTA_VM_TEST=1`, run with podman 6.1 on arm64): two users get two VMs, real PNG, navigate to example.com, AT-SPI read contains the page, a home file survives stop and start, and delete removes the volume.

### Amendment 2026-10-26 (later): VNC for people

People now see and control VMs over VNC instead of polled screenshots and per-click API calls. TigerVNC's X server (Xtigervnc) replaces Xvfb and serves VNC itself, so bots (cua-driver, XTEST) and people share one screen; XFCE replaces Openbox so a person gets a usable desktop (panel, menu, terminal, files). No root is granted: software is installed per user on the home volume. The server bridges noVNC's WebSocket to x11vnc. It authenticates with the per-start VNC password itself and gives the browser a no-auth RFB session after a one-time ticket, so the VNC port and password stay on the server. VNC authentication is weak (DES, 8-character password); it is acceptable only because the port is loopback-published and every connection comes through the authenticated bridge. Earlier draft: x11vnc on Xvfb. Bots keep using spacesd's MCP.

## Amendment 2026-11-04: Cua and agent-desktop, VM and local (phase 0 findings)

Each computer row now has a `target` (`vm`, `local`) and a `driver` (`cua`, `agent-desktop`). Findings from running the real tools:

**agent-desktop (vercel-labs, Apache-2.0).** The image pins release v1.1.0 (sha256 per architecture, in `docker/desktop/Dockerfile`).

- Released builds have **no `mcp` command**. It was added to `main` on 2026-11-03, after v1.1.0. The driver therefore reads the JSON envelope each CLI command prints, and does not use stdio MCP. Refs are `@<snapshot>:eN` and are valid for one snapshot.
- On the VM display (Xtigervnc, XFCE, Chromium): with `DISPLAY` and `DBUS_SESSION_BUS_ADDRESS` set, accessibility is granted and Chromium's tree is readable. `exec` has no D-Bus address by default, so the image must hand it over (the address is random per start).
- `type <ref> <text>` needs `--headed` for Chromium's address bar (the field offers no semantic action). It then verifies the field value. Semantic `click <ref>`, `mouse-click --xy x,y --headed`, `snapshot`, `list-windows` and `clipboard-set/get` work.
- **`press <key>` makes Chromium segfault** on this display, for every key tried (return, escape, tab, space, ctrl+a). `xdotool key` in the same container does not. Keys therefore go through `xdotool` in the container, not through agent-desktop.
- `screenshot --screen` is refused under XFCE's compositing window manager (`PLATFORM_NOT_SUPPORTED`). `screenshot --window-id` works.
- A password input is role `textfield` with state `secure`; a plain input is `textfield`. `pickInput` expects cua-style roles (`entry`, `password text`), so the driver must translate.

**Cua on the local machine.** On macOS `cua-driver` 0.36.0 has a different tool contract from the Linux `cua-spacesd` 0.8.0 the VM uses: `click`, `type_text` and `press_key` target a `pid`/`window_id`/`element_token` and run in the background. The VM driver's `scope: "desktop"` and foreground calls do not apply. A local Cua driver is a separate implementation.

**Host (macOS).** `agent-desktop` 1.0.2 lists windows and has Accessibility; Screen Recording is not granted to the terminal, so host screenshots need that grant.

**Implemented 2026-11-04.**

- `computer_vm.target` and `.driver` exist (migration `20261104001234_computer_target_driver`), with `GET /api/computer/capabilities` reporting `targets`, `POST /api/computer/vms` and `PATCH /api/computer/vms/:id`. `ZETTA_VM_DRIVERS` (default `cua`) sets which drivers are offered.
- `drivers/cua.ts` and `drivers/agent-desktop.ts` implement one `DesktopDriver`; `vm.ts` keeps leases, limits, VNC and the container lifecycle. The agent-desktop driver reads CLI envelopes through `docker exec ... zetta-agent-desktop`, sends keys with `xdotool`, and translates its `textfield`/`secure` roles for `pickInput`. Fixtures in `drivers/fixtures/` are real output.
- The image sets the session environment for `exec` (`/tmp/runtime-agent/session.env`) and turns xfwm4 compositing off.
- `src/scripts/vm-demo.ts <cua|agent-desktop>` runs the same walkthrough on a real VM with either driver: navigate, read, scroll, click, sign-in fill with a dummy credential, takeover and hand-back. Both passed on the rebuilt image.
- **Not built:** the `local` target (the server's own desktop). Creating one returns `UNSUPPORTED`. macOS `cua-driver` and agent-desktop on a host need their own drivers (see above), and a decision on what "read" means for a host desktop with many apps.

**Systems, 2026-11-04.** `computer_vm.os` (`debian` | `ubuntu`, migration `20261104011405_computer_os`) picks the image per computer; `ZETTA_VM_OS` (default `debian`) is what the operator offers and `ZETTA_VM_IMAGE_UBUNTU` names the Ubuntu image. One Dockerfile builds both (`BASE_IMAGE`, `BROWSER`). Findings and choices:

- Ubuntu 24.04 has no Chromium in apt (`chromium` has no candidate; `chromium-browser` installs a snap, which does not run in a container). The Ubuntu image therefore has no browser rather than a third-party package source; the service refuses `navigate` and credential fills on it, and its drivers do not wait for a browser window at start.
- Both drivers work on Ubuntu 24.04: spacesd (glibc build) answers its health check, agent-desktop reports accessibility granted, and a bot opened a terminal and ran `uname -a` on a Debian computer (Cua) and an Ubuntu one (agent-desktop) in one run (`vm-demo.ts machines`).
- `uname -a` prints the host's kernel in every container, so the two computers show the same kernel line; `/etc/os-release` is what tells them apart.
- Windows and macOS are in the list the UI shows (`GET /api/computer/capabilities` -> `os`) with `available: false` and a reason. Neither can run in a Linux container. macOS is only possible as the server's own desktop (the local target).

## Amendment 2026-11-04: machines (SSH, SFTP, FTP) and remote Cua computers

Two more ways for a bot to reach a machine. In both, the secret stays on the server: the browser seals it to the server's transport key (`connections/transport.ts`), the connections store encrypts it at rest (`connection`, provider `machine`, per-user key), and no API, list, log, audit row or prompt carries it back. Migration `20261104045356_machine_access`.

**Machines (Studio > Computer > Machines).** Table `machine` holds name, kind (`ssh` | `sftp` | `ftp`), host, port, user, the pinned host key and the id of the sealed secret. A bot names a machine in a `zetta:machine` block (`run`, `list`, `get`, `put`); Zetta runs the call, so the bot never holds the key.

- **Per bot, not for everyone:** a machine is used only by the bots its owner shares it with (table `machine_bot`, migration `20261104054046_machine_bots`; `PUT /machines/:id/bots`, or `botIds` when adding). A machine shared with no bot is used by none. A bot only sees the machines shared with it in its prompt, and a call for any other name gets "not found" (audited as `denied`), so a bot cannot tell which machines exist. Owners can share with their own bots and with team bots they can use.
- **ssh / sftp:** the private key (unencrypted) goes to a per-call `ssh-agent` on stdin, never argv and never disk, then `ssh` or `sftp` runs with `StrictHostKeyChecking=yes` against the pinned key, no forwarding, no user config and a clean environment. The agent is killed and its folder removed when the call ends. The host key is pinned at creation from a fresh `ssh-keyscan` the person confirms (`POST /machines/scan`); a different key later fails the call with `HOST_KEY_CHANGED`. A key with a passphrase is refused when it is saved.
- **ftp:** `curl` reads the user and password from a config on stdin. FTP (plain) and SFTP are both accepted. TLS is used when the server offers it (`--ssl`); otherwise the password crosses the network in clear text, and the form says so.
- **Where:** one lookup per call; the address that passes the private-network check is the one the connection uses (`ZETTA_ALLOW_PRIVATE_NETWORK=1` lifts the check, as for the browser).
- **What a bot may do:** like its own shell, deletes (`rm`, `rmdir`, `shred`, `unlink`), `sudo` and mail wait for the user: a `run` that names one is refused unless the bot's approved allow list has that exact `Bash(<word>:*)` rule. This is best effort (a command can be obfuscated). The real limit is what the remote account may do, so give a bot a restricted account. `get` and `put` move files only inside the user's code workspace (`codeDir`), never `.ssh`, keys or `.env`. Outside people never reach machines (`inboundAllowed`).
- **Output:** the secret, and each line of a key, is replaced with `[redacted]` in output, errors and the command shown to the user. Output is capped at 64 KiB. Each call writes an `audit_event` (`machine:<action>`, outcome) without the output.
- The server image needs `ssh`, `ssh-agent`, `sftp` and `curl` (added to `apps/server/Dockerfile`).
- Checked against a real `sshd` on loopback (run, exit code, key redaction, wrong key, changed host key, dead port, sftp put/list/get) and against `curl` with a small FTP server (PASV answer pointing at an unroutable address, no TLS). Not checked: FTP over TLS with a real server, and the Docker image build.

**Remote Cua computer (`computer_vm.target = "cua"`).** A machine that already runs `cua-spacesd` is added by https address and bearer token (`POST /vms` with `target: "cua"`, `endpoint`, sealed `token`). Row columns `endpoint` and `connection_id`. It uses the same `cua` driver and the same act/read/screenshot path as a container computer; nothing runs in a container.

- Only `https` (`http` when private networks are allowed), no credentials, path or query in the address; checked again at every start.
- No browser is assumed on someone else's machine: `navigate` and sign-in fill are off. Keyboard layout, paste and the VNC viewer are not offered. Deleting the computer revokes the token and touches no container.
- Needs the VM service, so `ZETTA_DESKTOP_RUNTIME=docker` must be set on the server even if only remote computers are used.
- Not built: replacing a token (delete and add again), a bot proposing a remote computer, FTP/SSH hosts behind a proxy.

## Amendment 2026-11-04: `navigate` goes through DevTools and says where it landed

A bot that asked a VM to open a page could read `about:blank` and give up. `navigate` typed in the address bar (Ctrl+L, the address, Return) and reported "ok" without checking anything: the keys went to whatever window had focus, or to a Chromium that was still starting, and the next `read` ran before the page changed. Checked on a real VM: after a cold start the first navigate and the read that follows it now show the page.

- **Navigate:** `navigatePage` (`computer/cdp.ts`) opens the address in the active tab over the published DevTools port (`9222`), waits for the load event (15 s at most) and answers the address the tab ended on. It attaches to the tab only: no request interception and no viewport override, because the window is the one the user sees. Right after a cold start it waits (10 s) for the first tab. The scheme and public-address checks run first, as before.
- **Refused pages:** Chromium's own error (`net::ERR_*`) becomes `NAVIGATION_FAILED` and goes to the bot. A host that does not resolve is still `BLOCKED_URL`, from the server's address check, before Chromium is asked.
- **Fallback:** a VM from an older image publishes no port, and a port that does not answer is not an error: the address bar is used, now after activating the Chromium window (`bring_to_front` for Cua, `xdotool search --onlyvisible --class chromium windowactivate` for agent-desktop).
- **What the bot is told:** a `navigate` in the middle of a reply answers `navigate ok: now at <address>`; a read of a blank tab starts with "The browser shows an empty tab (about:blank): navigate again."
- **Instructions (`chat/tools.ts`):** `zetta:browser` is a separate browser on the Zetta server, with none of the user's sign-ins; `zetta:desktop` is the browser inside the user's own computer (VM). The desktop text says when to use it (the user names it, a site needs their sign-in, WebFetch/curl/`zetta:browser` are blocked), to send `navigate` and `read` together, to read again before reporting `about:blank`, to treat a sign-in or CAPTCHA wall as a working computer (say what is seen, try another address of the same source once, then `zetta:handoff`), and never to start, stop or control a computer with shell tools.
- **Image:** `zetta-desktop:latest` must be rebuilt when `docker/desktop` changes. The server recreates a running container whose image is not the current one at its next start (the home volume stays; open tabs close).
- **Not checked:** the credential-fill test in `vm-docker.test.ts` fails on a real VM with or without this change (its last step clicks a fixed position on github.com's sign-in page).

## Amendment 2026-11-10: placement, this computer, tools inside the run

- **Placement** (`computer/placement.ts`): a server open to the network never runs a bot's browser on itself (the browser container runtime is required) and never offers its own desktop. A local install may also use its own desktop and the person's default browser.
- **This computer** (target `local`, `drivers/host-agent-desktop.ts`): agent-desktop on the host. Read is the focused window; navigate opens the address with the system (`open` / `xdg-open`); passwords are never typed. Without macOS Accessibility every window reads as not accessible and the driver says how to allow it. Only the permission path was checked for real (agent-desktop 1.0.2); act and read need a granted machine.
- **Tools inside the run** (`computer/run-tools.ts`, `POST /api/run-tools/mcp`): Claude Code bots with desktop access get `computer_read`, `computer_act` and `computer_screenshot` (an image) as MCP tools, authorized by a random token that lives only for the turn. Same VM service, so takeover, address checks and limits are unchanged. In the Docker runtime set `ZETTA_INTERNAL_URL` to an address the container reaches. Other harnesses keep the fenced blocks.
- **Verified on real systems (2026-11-10):** macOS (read the focused window, screenshot, with Accessibility and Screen Recording granted) and Linux (XFCE desktop image: read, screenshot, keys through xdotool, typing, navigation). **Windows is not verified:** agent-desktop supports it and addresses open with `start`, but no Windows machine was reachable (Cua offers no Windows VM on a Mac or in the linked clouds). Check it on a real Windows PC before relying on it.
