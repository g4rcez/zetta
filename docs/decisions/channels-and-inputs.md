# Channels and inputs

Decided and built on 2026-11-15: documents, voice, Slack and e-mail.

## Documents

- PDF, Word (`docx`), PowerPoint (`pptx`), Excel (`xlsx`), CSV and TSV, up to 20 MB, on `POST /api/attachments` (`dataBase64`, like pictures). `chat/extract.ts` reads the text: PDF with `unpdf` (first 200 pages), Office files with `fflate` and their XML (at most 400 parts and 50 MB unpacked), tables as text. The text (at most 256 KB) is the attachment's content, the original is kept on disk like a picture, so the text reaches the turn as any attached file does: framed as untrusted data, and the turn counts as having seen outside content.
- A scan (no text), a damaged or password-protected file and a file that is not the type its name says are refused with a sentence.
- Out of scope: reading pictures inside documents, legacy `doc`, `xls` and `ppt`, OpenDocument.

## Voice

- `modules/transcribe/`: Whisper (`Xenova/whisper-small`, multilingual; `base` was unusable on Portuguese in a real run, and without a language Whisper assumes English, so the language is passed: the browser's for the microphone, the language field of Studio > Voice > Speech to text for voice notes) runs **in the server** through `@huggingface/transformers`, like the embedding model: the audio never leaves the machine. The model downloads once into `ZETTA_TRANSCRIBE_MODEL_DIR` (default `~/.cache/zetta/models`); the model is the `transcribe_model` of the installation settings, and the provider `off` turns it off. (The variables `ZETTA_TRANSCRIBE_MODEL`, `ZETTA_TRANSCRIBE_LANGUAGE` and `ZETTA_TRANSCRIBE=off` were removed on 2026-11-23: see `docs/operations/server-settings.md`, "Upgrading".) One recording at a time, five minutes at most, 120 seconds to finish.
- Web: a microphone button in the message box. The browser records, decodes and resamples to 16 kHz mono itself (`features/chat/audio.ts`), so the server needs no decoder for it; `POST /api/transcribe` returns the words, which go into the message for the person to read and change. At most 6 recordings a minute per person.
- Voice notes of outside people (Telegram, WhatsApp): the plugin's `poll` marks the event (`audio.ref`) and `fetchAudio` hands over the bytes (at most 10 MB, 5 minutes); `inbound/service.ts` transcribes up to five per poll with **ffmpeg** (added to the server image) and replaces "(voice note)" with the words, marked as transcribed automatically and maybe wrong. Without ffmpeg, or on any failure, the event arrives as "(voice note)".
- **Provider choice (2026-11-15, after the first run):** `installation_settings.transcribe_provider` is `off`, `local`, `openai` or `compatible` (`off` added 2026-11-23: it replaced `ZETTA_TRANSCRIBE=off`; the column is a TypeScript enum with no database CHECK, so no migration) (any `/audio/transcriptions` server; `transcribe/remote.ts`), read on every recording by `transcribe/configured.ts`. Installation-wide because voice notes are transcribed with a background actor who is never an administrator. The key is a sealed connection of provider `transcribe` owned by the administrator who saved it (`PUT /api/connections/transcribe-key`, purpose `installation.transcribe-key`; hidden from the Accounts tab); the settings only record which one, and the API never returns it. If that administrator leaves the key reads as "unavailable" and nothing falls back silently to another provider. There was an operator fallback `ZETTA_TRANSCRIBE_API_KEY`; it was removed on 2026-11-23, so the sealed connection is the only home of the key. The address goes through the private-network rule (`assertPublicUrl`); redirects are refused; the provider's words are never passed on; the key buffer is zeroed after each call. The audio now leaves the machine with a provider: the Studio card and the Save button say so. Language: the call's (the browser's) wins over the installation's, which serves voice notes.

### Speech out and the voice core (2026-11-22)

Live spoken conversation with a bot, then phone calls, were built in steps (all built by 2026-11-23: see `voice-and-phone.md`). The answer stays the bot's own (its memory, instructions, tools, permissions), so the design is: speech to text per finished utterance, the bot's normal turn, text to speech sentence by sentence, with interruption. Everything is saved as normal chat messages. Steps 0 and 1 need no network transport:

- **Voice core** (`apps/server/src/modules/voice/core/`, pure, no I/O): 16 kHz mono PCM16 frames of 20 ms, a resampler for 8/24/48 kHz, G.711 mu-law (for phone); a `Vad` interface with an energy-plus-hangover detector; end of turn (700 ms of silence, 1,200 ms when the transcript reads as unfinished; English, Portuguese, Spanish); a speakable-text filter and sentence splitter (`SpeakableStream`); and `VoiceSession`, a state machine (`listening | thinking | speaking | interrupted | ended`) with injected `Vad`, transcriber, `Synthesizer`, `TurnFollower` and clock. Barge-in flushes the audio at once, the new utterance goes to the running turn as a late message (the old reply's text is dropped until it arrives), a stop phrase (`chat/stop-intent.ts`) stops the turn. One filler ("One moment" / "Um momento" / "Un momento") after 1.5 s without text, one more after 8 s of silent tool work. The `reply` event reports `spokenChars`: how much of the reply was heard (the transport can say with `reportPlayed`).
- **Speech out** (`modules/speech/`): `Synthesizer` returns 16 kHz PCM16 and can stream chunks; adapters for OpenAI-style `/audio/speech` (`openai`, `compatible`; asked for `pcm`, 24 kHz, brought to 16 kHz) and ElevenLabs (`/text-to-speech/{voice}/stream?output_format=pcm_16000`). `browser` means the page speaks the text itself. Settings are the `speech_*` columns that already existed (no migration), read on every call like speech to text; the key is a sealed connection of provider `speech` (`/api/connections/speech-key`), never returned, buffer zeroed; the address goes through the private-network rule; redirects are refused; the provider's words are never passed on. `POST /api/speech` (20 a minute per person) serves the Listen button: WAV for a provider, `{mode: "browser", text}` for the browser, 409 when off.
- **Decisions.** The voice of a bot was first kept on the device (`localStorage`), because the bot table had no settings column. Phone calls then needed the server to know it, so it moved to `bot.voice` and `bot.voice_language` (a device voice still stays on the device; see `voice-and-phone.md`). Text to speech is installation-wide like speech to text, for the same reason (a background actor is never an administrator). The Listen button speaks the first 1,500 characters; longer replies are for the voice session, which speaks them as they stream.
- **Outside that step** (the browser socket and the phone transport were built the next day: `voice-and-phone.md`): echo cancellation (the transport's job: the detector cannot tell the bot's voice coming back from the person's); a model-based detector (the interface is there); `ZETTA_SPEECH_API_KEY` was read at that step as a fallback (removed on 2026-11-23: the sealed connection is the only home of the key).

## Slack

- Plugin `slack`: the person creates a Slack app (scopes `app_mentions:read`, `im:history`, `chat:write`; events `app_mention`, `message.im`), pastes the bot token and the signing secret, and sets the app's Request URL to `/api/inbound/slack/hook/<user id>`. The server must be reachable from the internet.
- Slack **pushes** the messages, so `PluginInbound` gained `ingest(ctx, headers, raw, {filter})`: it verifies the signing secret (HMAC-SHA256 of `v0:timestamp:body`, five minutes of tolerance, timing-safe), answers Slack's one-time challenge, and returns the message. The inbound service stores it like a polled one (once per key, the same caps and framing) and starts the turn. A request that is not signed with this person's secret gets the same 401 as any other refusal. Without an enabled route the setup check still passes and nothing is kept.
- A direct message is its own chat; an @mention is a chat per thread. The same trust as Telegram: everybody who writes is an outside person, code off, only the reply tool and the read tool, for the chat the message came from.
- Replies: `send_message` (off until "Allow replies" is yes, rate limited, plain text with Slack's control characters escaped so a reply cannot ping `@channel`), `read_thread` (read, untrusted data).
- Decided: **no approve-in-Slack buttons** (an outside person's turn drops every write, so no card ever comes from one) and **one bot per workspace** (the route key stays one bot per plugin).

## E-mail

- Plugin `mail`: IMAP read-only (nothing marked, moved or deleted) and SMTP, any host. Cursor `{uidValidity, lastUid}`: the first poll remembers where the mailbox is, a rebuilt mailbox starts again from now, a poll cut short stops the cursor before the unread mail.
- Trust: delivered only when the sender is on the person's list (addresses or `@domains`) and, unless "Check the sender" is off, the topmost `Authentication-Results` line with the configured receiving server's name says `dmarc=pass`, or `dkim=pass`, for the From domain (`plugins/authres.ts`). With no list nothing is delivered. Automatic mail (`Auto-Submitted`, bulk) and the bot's own address are ignored; the quoted thread is cut; attachments are named, never opened.
- Replies: `send_email` only to the chat's own address, only if it is on the list, off until "Allow replies", at most 5 a minute and 20 an hour, plain text, no header injection. Hosts go through the same private-address policy as WhatsApp and MCP servers.
- Verified against a real IMAP and SMTP server: GreenMail (`docker.io/greenmail/standalone`) in a local container, not a commercial provider. `plugins/mail.real.integration.test.ts` runs the plugin's own code against it: install and status, the first poll, delivery and the trust checks, a cut-short page, a file attachment, `send_email`, a rebuilt mailbox (server restart, new `UIDVALIDITY`), a wrong password, an unreachable server. GreenMail adds no `Authentication-Results` (the test writes it into the messages) and has no STARTTLS, so TLS and STARTTLS stay covered by the fakes only. Rerun: `ZETTA_TEST_GREENMAIL=1 ZETTA_DOCKER_BIN=<engine binary> bun --no-env-file test src/modules/integrations/plugins/mail.real.integration.test.ts` from `apps/server` (see `docs/operations/email.md`). No defect in the plugin came out of the first run.

## Mail inbox and bots that send

Decided 2026-11-22. The inbox (`modules/mail`, the `mailbox` plugin, the chat panel of the Mail page) stays read-only; a bot may send in the person's name, and "bots can send email if they asked" is read this way: **the person's own request in the turn is the approval, everything else gets a card.**

- Two tools of effect `send`, `mail_reply` (the server takes the recipient from the answered message, builds the `Re:` subject and the threading headers) and `mail_send` (at most 5 recipients). Plain text, To only. Per mailbox `sending` on or off; off refuses with a sentence that only the person can turn it on.
- The gate is `mailSendMode` in `chat/mail-policy.ts`, reached through a gate the chat service builds from facts it holds (the tool asks it once it has worked out the recipients): where the turn runs, the person's own words, the conversation open beside the chat, and what the turn read. Send at once needs all four: own chat turn, an ask in their words, recipients they pointed at, no outside content read other than the open conversation. Otherwise a card (the pending call is signed and expires; a changed or replayed call is refused) or a refusal (no access, sending off, limits). A card is never remembered. Nothing about the rule is in a prompt.
- A copy of every sent mail is filed in the sent folder by the IMAP driver, behind the driver interface (a later Gmail driver does nothing). That is the one write to a mailbox.
- The activity trail takes closed tokens and ids only (no database change was made), so it records the mailbox and the number of recipients, not the address, subject or text; the person sees the whole mail in the chat or on the card.
- Decided against: letting a bot with code access or MCP servers force a card (it would make every default bot ask each time; same trade-off as `writeMode`); a Reply-To that differs from the sender sends without a card (it is a card).
- Verified against GreenMail (reply threaded to its author with a copy in the sent folder, a card-approved send, the hostile mail that sends nothing) and the real engine in a real browser; see `docs/security/plan.md` row C7 and `docs/operations/email.md`.

## Gmail as a mailbox

Decided 2026-11-22. Any provider is visible in Zetta, each mailbox is its own read-only view (never merged), and a connected Google account shows up as a mailbox with no extra step.

- Kind `google` of `zetta.mailbox`, driver `mail/drivers/google.ts` over the Gmail API. No database change: the existing kind, the unique index on owner, kind and lower(address), and the `retired` state were enough.
- **Tokens are borrowed, not copied.** The driver gets a `GmailTransport` per request from `integrations/plugins/google/mail-access.ts`, which uses the person's own Google installation (`plugins.ownContextFor`, never the team's), the account's own context, the plugin's refresh with single-flight and its safe errors. The mailbox row has no connection id and no secret.
- **Made on first need.** `mail.list` (also behind the bots' plugin and the MCP server through `mail.rows`) adds a row for each connected account with `gmail.readonly`, with `insert ... on conflict do nothing` on the unique index, so parallel lists cannot make two. Sending starts off for such a row. A row whose account is gone or lost the read permission is set to `needs_auth` at list time; it becomes active again when the account works.
- **Remove means hide.** It sets `retired` (the row stays, so it is not recreated), leaves the Google account connected, and a retired row is dropped when its account disappears from the plugin, so reconnecting shows it again. `POST /api/mailboxes/google` brings back a hidden one. Decided against deleting the row (it would come back on the next list) and against disconnecting the Google account (that is the plugin's job and would break the bots' Gmail tools).
- **Errors.** Missing read permission, a revoked token and a disconnected account are code `AUTH` (state `needs_auth`) with a sentence that points to Studio > Plugins > Google. A missing send permission is `SEND_SCOPE`, mapped to the same `MAIL_AUTH` for a bot but **not** recorded on the mailbox: it would otherwise block reading. A deviation from "maps to needs_auth", on purpose.
- **Read-only by construction.** The driver allows GET of profile, thread, message and attachment and POST of `messages/send`; labels, modify, trash, delete, drafts and batch calls are refused before the transport.
- Found while doing it: the Google plugin's per-account context did not carry `clientType`, so a token refresh for a Desktop-type client without a server URL set failed as "not configured"; fixed in `oauth.ts`.

## Outlook and Microsoft 365 as a mailbox

Decided 2026-11-22. Microsoft turned off password sign-in for IMAP and SMTP in Exchange Online and Outlook.com, so these addresses need OAuth. Same shape as Gmail: a plugin holds the sign-in, an account becomes a mailbox by itself, the driver is read-only by construction.

- **The person's own app registration**, like the Google plugin's own OAuth client (`integrations/plugins/microsoft/`): client ID (and secret for a web client), tenant (`common` by default, optional tenant), authorization code with PKCE and `state`, tokens sealed per person, up to ten accounts, refresh with single-flight (Microsoft rotates the refresh token, the plugin stores the new one). Settings live in the plugin config, never in environment variables. Delegated scopes `offline_access`, `User.Read`, `Mail.Read`, `Mail.Send`; the person ticks Mail.Read and Mail.Send.
- **Two client types.** A public client (default): redirect `http://localhost`, no secret, the address the browser ends on is pasted back (`POST /api/plugins/microsoft/complete`). A web client: secret and `/api/plugins/microsoft/callback`. The Google loopback listener was not generalised: paste-only for Microsoft is one fewer moving part. Microsoft matches a localhost redirect without its port, and the portal cannot register `http://127.0.0.1`, so `localhost` is used.
- **Database.** `MAILBOX_KINDS` and `mailbox_kind_check` gained `microsoft` (migration `20261123014700_microsoft_mailbox`: drop the check, add it again with the four kinds; no data touched; tested with a mailbox of every kind present, `packages/db/src/embedded/microsoft-mailbox.migration.test.ts`).
- **Generalised, Google unchanged.** `MailboxStore.ensureAccount(kind, ...)` replaces `ensureGoogle`; the service looks the words and the access of each account kind up in one table (`ACCOUNT_WORDS`), so list reconcile, hide on remove and "show again" are one code path for both kinds. `POST /api/mailboxes/microsoft` brings back a hidden one (`NO_MICROSOFT` when the account cannot be shown). A Google and a Microsoft mailbox of one address are two mailboxes.
- **Graph shapes.** List: one request per page on `/me/mailFolders/inbox/messages` (`$select` without bodies, `$orderby=receivedDateTime desc`, or `$search` in place of the order: Graph sorts a search itself and returns at most 1000 results), grouped by `conversationId` on the page. Chosen over one request per conversation because Graph allows four concurrent requests per mailbox and a page of 30 would breach it; the cost is that a row's count covers only its messages on the page. The cursor wraps `@odata.nextLink`, and only the allow-listed query keys are read back, never its address. Conversation: `/me/messages?$filter=conversationId eq '...'` (all folders, so the person's own replies in Sent Items are in it; Graph refuses `$orderby` on a property the filter does not name, so the order is made here), plus the ids of Sent Items, Deleted Items and Junk to tell sent from received and to drop deleted and junk; drafts dropped; a copy in both Inbox and Sent Items (mail to oneself) is shown once. Immutable ids are requested so a move does not change an id.
- **Send.** `POST /me/messages/{id}/reply` for an answer, `POST /me/sendMail` for a new message, plain text, saved to Sent Items by Exchange (`copy: "provider"`). **Deviation from "createReply + send"**: `createReply` needs `Mail.ReadWrite` (Microsoft's documentation), which would let Zetta change the mailbox; `reply` needs `Mail.Send` only. Costs: no Message-ID of the sent message, and the subject of an answer is Outlook's.
- **Read-only by construction.** The transport accepts a list of method and path pairs (`isAllowedGraphCall`); a test proves every request the fake Graph saw is on it.
- **Errors.** Same codes as Gmail: a missing `Mail.Read`, an expired or revoked refresh token (`invalid_grant`, `interaction_required`) and a disconnected account are `AUTH` (`needs_auth`) pointing to Studio > Plugins > Microsoft; a missing `Mail.Send` is `SEND_SCOPE` and is not recorded on the mailbox.
- **Revoke.** The Microsoft v2 protocol has no token revocation endpoint, so disconnecting forgets the tokens and the guide tells the person to remove the app's consent in their Microsoft account. Not hidden behind a call that does not exist.
- **Detection.** `GET /api/mail/detect` for a Microsoft-hosted address (by name or MX) answers `next`: the mailbox when the account is connected, otherwise the plugin. The connect page and the chat card no longer say "not supported" and offer no password form.

## A mail address for every bot

Decided 2026-11-22. "Bots have their own email, only if possible and if it doesn't require external work from the user." The owner of a bot types nothing: the address is made when the bot is created. What cannot be removed (a mail domain and a mail service account) is set once by the administrator in the installation settings (`mail_provider` `off | resend`, `mail_domain`, the API key as a sealed connection of provider `mailprovider`, `mail_cursor`). Where it is off, nothing is offered and the IMAP mailbox and the `mail` plugin stay.

- **Provider: Resend**, plain receiving (not its paid Inboxes), behind `mail/providers/provider.ts` (`domainStatus`, `poll`, `fetchRaw`, `send`; a fake serves the tests). Receiving is polled, so an installation the internet cannot reach works. Sending goes by SMTP (`smtp.resend.com`) with `nodemailer`, so the threading headers are the ones Zetta writes and the stored copy is the very bytes sent. Every call goes through the mail module's private-address policy, with timeouts and a size cap.
- **Mail is stored in Postgres** (`zetta.mailbox_message`, kind `provisioned`), because Resend keeps received mail only for its plan's retention (30 days on every plan listed). Removing the mailbox purges its messages and its route; the row stays hidden (`removed_at`) so the address is never reused.
- **The address**: `<bot slug>-<last 4 characters of a UUID v7>@<domain>`; on a collision 6, then 8 characters. Made after the bot exists, outside its transaction, never in a trigger; a failure never blocks creating a bot. Renaming keeps the address (the display name follows the bot). Archiving retires it: mail to it is dropped and counted, stored mail stays readable. Existing bots get "Give this bot an address" (bot settings, or the Chief). No backfill.
- **One route per mailbox.** `inbound_route` gained a nullable `mailbox_id`; its old unique key on (person, plugin) became a partial unique index that applies only to routes without a mailbox, and each mailbox has its own (the new indexes were created before the old key was dropped, in one migration). The mailbox poller stores events through `inbound.ingestMailbox`, which reuses the inbound service's storage, caps and turn start; the platform never polls a mailbox route through a plugin.
- **Trust, the `mail` plugin's rules.** A turn starts only for a sender on the mailbox's `allowed_senders` whose authentication results (from Resend, not from a header in the message) say `dmarc=pass` (SPF speaks of the envelope address and Resend does not name the DKIM domain, so neither alone is enough), and never for automatic mail (`Auto-Submitted`, bulk or list precedence, `List-Id`, `List-Unsubscribe`, an empty `Return-Path`) or the bot's own address. Mail from anyone else is stored and shown, and starts no turn. The turn is an inbound one (outside people, code off). Its one tool is `send_email` of the built-in `botmail` plugin, offered only in an inbound turn to the bot that owns the address: the chat service's inbound policy already refuses any address but the chat's, and the tool refuses an address that is not on the list or has not written, writes the `Re:` subject and the threading itself, and is limited to 5 a minute and 20 an hour. The `mailbox` plugin's read tools stay closed to outside people.
- **Decided against**: Resend webhooks (they need a public address); Resend's Inboxes product (paid, and ties mail to the provider); an environment variable for the key (the settings live in the installation, like speech to text, where the variable is only an operator fallback and this one has none); a column for the sender's name per message beyond the address (the raw source is kept).
- **Deviations**: `mailbox_message.attachments` (`none | some`) and `mailbox.removed_at` were added so the list can show a paperclip without parsing every source and so a removed address stays reserved. The mail counters are kept in memory and written to the server log, not in a table.

## Video transcription (2026-11-24)

The `video-transcription` plugin (`integrations/plugins/video-transcribe.ts`) turns a video into text for a bot: from a public link (any site yt-dlp reads) or from a file inside the person's code folder.

- **Captions first.** For a link, the video's details are read first (yt-dlp writes them to a file: a talk with automatic translations lists about 160 caption languages, more than the runner keeps of its output). `pickTrack` then chooses **one** track: a person's captions in the language, else the automatic ones in the speaker's own language (`xx-orig`), else the automatic ones of that language; the language is the one asked for, else the one the video says it is in. Asking yt-dlp for tracks by pattern (`.*-orig`) fetched about 25 of them on a real talk and YouTube answered 429. A caption download that fails is not an error: the sound is transcribed instead. Captions are WebVTT. YouTube's rolling automatic captions repeat each line, so `captions.ts` drops a line the cue before already showed. No captions, or `force: true`, means speech to text. A file always goes to speech.
- **Speech goes through the server's own recognizer** (`transcriber` in `services.ts`, Studio > Voice: local Whisper, OpenAI or compatible). The plugin has no key of its own. With Voice `off`, only videos with captions work, and the plugin's status says so.
- **Windows of 30 seconds.** ffmpeg decodes to 16 kHz mono on a pipe (`streamPcmWindows` in `transcribe/decode.ts`) and each full window is transcribed as it fills, so a long video never sits in memory and every call stays inside the 5-minute cap of the recognizer. Each window becomes one cue (the `.srt` and `.vtt` have 30-second cues, not sentences).
- **Output.** `.txt`, `.srt` and `.vtt` under `outputs/transcripts/` in the code folder. The tool returns the first 8,000 characters; `read` pages through the rest by job id (the text is kept in memory for the 20 latest jobs, the files stay).
- **Background jobs** like the YouTube downloader (the platform cuts a plugin call at 60 s): `transcribe` waits about 40 s, then answers with a job id for `job`, `read` and `cancel`. At most 2 run at once per person.
- **Safety.** A link goes through the downloader's public-address check (`ytdlpKit.publicUrl`). A file is resolved with `realpath` and refused when absolute or outside the code folder, so `..` and symbolic links out of it fail. The language is checked against a short pattern before it reaches yt-dlp's `--sub-langs`.
- **Settings** (both optional, empty means no limit): the longest video in minutes (a link longer than this is refused before any download, a file is cut), and a default language.
- **Deviations**: the job store is a small copy in the plugin, not shared with `ytdlp.ts` (that file has other changes in flight; `ytdlpKit` at its end exports the pieces that were reused). Windows are 30 s, not 60 s, because the local model has a 120 s deadline per call. A file's length is not probed, so its progress is "seconds transcribed", with no percent.
- **Verified for real** (2026-11-24): a 17-minute English talk on YouTube. Captions: 7 s, 15,678 characters. `force` (speech): download, ffmpeg and the local Whisper model, 1,051 s of sound in 105 s, 14,324 characters, with the language of the video passed on (the recognizer assumes English when told nothing). A 75 s mp4 file in the code folder also went through. The speech version mishears a name or two ("pull requests" came out "employee requests"); captions are the better source when they exist.

### Progress of a long plugin call in the chat (2026-11-24)

A bot's `zetta:plugin` call that runs long (a download, a video transcription) now shows how far it is in the chat's "Working" card: a line ("Downloading video · 45% · 1.20MiB/s · ETA 00:05", "Transcribing · 62% · 10:48 of 17:31") and a thin bar under the running step, and the card's header line says it too.

- **Plugin side**: `PluginContext.progress?({ text, percent? })` (`integrations/plugins/registry.ts`). The chat service hands it to any plugin through `ToolExtra.progress` (`plugins/service.ts`, `toolCtx`). The YouTube downloader and `video-transcription` keep it on their job and report from the yt-dlp progress parser and the transcription windows; `plugins/progress.ts` writes the text.
- **Server**: `runTools` gives the call a sink (`chat/plugin-progress.ts`): at most one report a second (the first at once, the latest of a burst a moment later), never the same text twice, text cut to 160 characters, percent clamped; `close()` runs when the call returns, so a background job that keeps reporting never reaches a step that is over. The turn emits a `progress` event (`data-progress` in `ui-stream.ts`, one part id per message so each reading replaces the last). It is **not** a step and not history: nothing goes into `timeline`/`meta.timeline`; `saveLive` keeps the latest "label · text" as the activity so a page opened mid-turn reads something.
- **Web**: `chat-rows.ts` keeps the latest reading on the row; `currentProgress` shows it only while it is newer than the latest real step (`activityAt`, ignoring the "Still working" heartbeat). It decides by time, not by place, because the part is replaced in place and can sit before a later step. `work-timeline.tsx` shows the line and `Progress` on the running step.
- **Polling**: a call is cut at 60 s, so a long job answers with a job id after about 40 s and the bot polls `job`. With a chat watching, a `job` poll now waits up to that long for the job and reports while it waits (without a chat it still answers at once). In the quiet moment between a poll and the next one (the bot's own model round) nothing moves.

## Built-in plugins are activated, not on by default (2026-11-24)

A **built-in** plugin ships with Zetta and needs no configuration, but it is no longer on for every bot. The person **activates** it (an install with nothing to fill in) and chooses the bots that may use it, exactly like any other plugin. Decided with the user: it applies to every built-in plugin, the three phone plugins included, and the bots are picked at activation.

- **Built in**: Apps, Mailbox, Bot e-mail address, Phone call, Phone calls, Phone call line, YouTube downloader, Video transcription.
- **Registry** (`integrations/plugins/registry.ts`): `builtin: true` (native; every field optional and not secret; `registerPlugin` refuses anything else) replaces the old `always`. The `always` object became `gate` (`available`, `refusal`, `prompt`): extra conditions checked on every call and prompt **after** the binding (mail switched on, a phone call in progress, an app given to the bot). A `gate` needs `builtin`. The catalog says `builtin`, no longer `always`.
- **Service** (`plugins/service.ts`): no more special path. A call needs the person's binding for the bot; a built-in plugin without one answers `NOT_BOUND` with "<name> is not turned on for this bot" and the fix "Activate <name> in Studio > Plugins and choose this bot". The context of a built-in plugin still gets `turn` and the server's decision points (mail, phone), now assigned onto the context, not copied: `config` is a getter that `setConfig` keeps current (a copy froze it; that also affected the progress callback of the previous change). The prompt lists a built-in plugin only for a bot it is bound to and whose gate lets it in; otherwise it is among the plugins offered as a setup card. `install`, `uninstall`, `setupInfo`, `botSettings` and the `zetta:setup` block work for it like for any plugin.
- **Web**: a card says "Built in", and "Active" once activated; the button is **Activate** (a built-in plugin) or Install. The plugin page shows no configuration fields for a built-in plugin: the only choice is the bots. Optional settings (the limits of the YouTube downloader and of video transcription) are on its page after activation. An administrator can still open the server settings of Bot e-mail address before activating it.
- **Not migrated**: nothing activates the built-in plugins for people who used them before. After this change a bot that read mail, answered a phone call or called an app needs the plugin activated; until then its calls answer "not turned on". This follows the request ("must require to install them"); an automatic activation for existing bots would be a data migration to decide.
- **Watch**: the **phone** plugins only exist during a call. A bot that was never given them can neither take a message for its owner nor hang up on a live call; this was accepted when chosen. Bot e-mail: a bot with its own address needs the plugin activated to reply to an incoming mail.
- **Tests**: `plugins/builtin.test.ts` (rules, activation, gate, prompt, context); the suites of mail, phone, apps and pause activate the plugins they use (`test-world.ts` has `activate`, and `world({ db })`).

## Plugin list filters (2026-11-24)

The Studio > Plugins list has a **Built in** status next to Installed, Available and All: it lists the built-in plugins, activated or not. Installed holds only what the person installed or activated; Available holds everything not installed, built-in ones included. The filters (words, status, category) live in the address (`/studio/plugins?status=builtin&category=messaging&q=mail`, defaults left out), parsed in `features/studio/plugins-filters.ts`; the setup flow (onboarding) keeps its own state because it is a step, not a page.
