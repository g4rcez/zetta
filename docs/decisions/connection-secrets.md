# Connection secret storage

Status: accepted design selection under delegated architecture authority after [independent WATCH review](../verification/reviews/connection-secrets-review.md), with the request encoding clarified below. Research/ADR only. This does not complete [RFC-007](../../tasks/007-store-user-owned-connection-references.md) or approve a production deployment. Decision date: 2026-10-22. Earlier phrase-marker checks are housekeeping history, not semantic acceptance evidence; direct review and later behavioral proofs are required.

## Decision and observed baseline

Use application-side AES-256-GCM through `node:crypto` and the existing PostgreSQL/Drizzle stack for bounded API-key blobs. One deployment-owned 32-byte random key is supplied to the trusted secret service at startup. Store authenticated ciphertext in PostgreSQL; expose only safe metadata and opaque, owner-checked references. No new dependency, vault platform, provider call, global credential fallback or plaintext persistence is needed.

Observed source anchors: [database factory](../../packages/db/src/index.ts), [database manifest](../../packages/db/package.json), [identity schema](../../packages/db/src/schema/identity.ts), [access checks](../../apps/server/src/modules/identity/access.ts), and [root manifest](../../package.json). These declare Drizzle 1.0.0-rc.4, pg ^8.23.0 and Bun 1.3.14 as package manager. No connection schema/service was found at these planned RFC-007 paths. The actual database server version and deployed crypto runtime remain implementation verification inputs.

Follow [ownership](ownership.md), [execution isolation](execution-isolation.md), [task rules](../../tasks/README.md), [plan](../../tasks/plan.md), and [confirmed intent](../intent/zetta-v1.md). Admin status never bypasses owner access. Shared bot definitions carry requirements; actor-private bindings select the actor's connection references. Workspace placement grants no authority.

## Two distinct credential kinds

- `api-key`: a bounded opaque UTF-8 byte sequence, encrypted by this store. No trimming, normalization, arbitrary JSON object or provider-dependent refresh protocol. Empty input, invalid UTF-8 and input above 16,384 bytes are rejected. A provider adapter may impose a smaller limit. A provider-specific OAuth token protocol needs a separate typed contract before joining this kind.
- `native-profile`: an opaque reference to private actor+harness state managed by the isolated launcher. It is not an API-key blob, exported token, host path, profile archive or browser cookie DTO. Its storage-at-rest, mount, login relocation, exclusive lease and refresh behavior require the corresponding harness/profile proof. This ADR permits the discriminated reference contract only; it does not approve host-profile migration or mark native profile resolution implemented.

Only API-key writes are selected for the first implementation slice. Native profile references must report unsupported until their independent state backend is accepted. A caller cannot choose a filesystem path or make an API-key envelope masquerade as a native profile.

## Key and authenticated envelope

Proposed trusted configuration: `CONNECTION_SECRET_KEY` (canonical base64 encoding of exactly 32 random bytes) and `CONNECTION_SECRET_KEY_ID` (non-secret `[a-z0-9_-]{1,32}`). Validate canonical round-trip base64, not permissive decoder success alone. Reject missing, malformed or wrong-length values; never derive this key from passwords, auth signing secrets or database URLs. Configuration belongs only to the trusted secret-service process; a trusted launcher receives the key only if it actually hosts that service. Prefer keeping the key in the server and delivering only dispatch-scoped plaintext to the launcher. Never inherit the key into attempts, web bundles, build jobs, DTOs or logs. Environment schema/codegen changes are a later scoped task.

Envelope v1 has exactly: `envelopeVersion: 1`, `algorithm: "aes-256-gcm"`, `keyId`, `nonce` (12 bytes), `tag` (16 bytes), and `ciphertext` (1–16,384 bytes). Store byte fields as binary columns, not unbounded JSON/base64. The binary payload ceiling is 16,412 bytes including nonce and tag; metadata is separately bounded. Reject unknown versions/algorithms/key IDs and incorrect lengths before decryption. Envelope serialization is internal only.

For every encryption, including replacement/rekey, generate a fresh `randomBytes(12)` nonce. Enforce uniqueness of `(keyId, nonce)` across all retained API-key envelopes; do not reuse a key ID for different key bytes. Keep nonce tombstones when ciphertext is removed, so collisions with revoked/replaced versions remain detectable. A uniqueness conflict retries encryption with a fresh nonce inside a bounded local transaction retry (maximum three); exhaustion fails closed. Retain this ledger for that key's lifetime. Set a conservative v1 ceiling of 1,000,000 encryptions per key and refuse further writes until an approved rekey; this is an operational safety limit, not a claimed cryptographic bound.

AAD is the UTF-8 encoding of the exact JSON array `["zetta.connection",1,keyId,ownerUserId,connectionId,kind,credentialVersion]`. Construct it from trusted row identity and the requested pinned version, never from caller-provided AAD. Owner/connection/kind are immutable; credentialVersion is a positive integer, not a floating-point string. Fixed-position JSON avoids concatenation ambiguity. The algorithm is fixed by envelope version, not dynamically selected from untrusted input.

Call `setAAD` before encryption/decryption updates. Set `authTagLength: 16` explicitly on both cipher and decipher. Store `getAuthTag()` only after encryption `final()`. Do not release any decrypted bytes from `update()` until `final()` authenticates successfully. Authentication failure becomes a fixed unavailable error; discard temporary buffers without printing the exception payload. Best-effort buffer clearing reduces residency but is not a JavaScript secure-erasure guarantee.

A singleton authenticated key-check record stores an encrypted fixed public sentinel with a distinct AAD domain `zetta.connection-key-check`, version and key ID. Its nonce participates in the same nonce ledger. Bootstrap it atomically only in an explicitly initialized empty connection store. If ciphertext exists but the sentinel is missing, fail closed; do not silently create a new key/check record. Startup verifies the configured key against it before enabling secret reads/writes. Wrong bytes with the same key ID therefore fail startup, including when no user secret is being read. This check does not protect against an attacker controlling the running trusted service.

## Logical storage and service contract

This is a logical schema proposal, not SQL or a migration. All constraints must be enforced in service validation and corresponding database constraints where possible.

| Record | Fields and constraints |
| --- | --- |
| Connection | Server-generated UUID `id`; immutable `ownerUserId` FK to existing user ID; immutable kind; allowlisted provider/harness identifier of 1–64 ASCII characters; user label 1–100 Unicode characters/400 UTF-8 bytes; state `active` or `revoked`; revision integer 1–2,147,483,647; currentCredentialVersion same range; created/updated/revoked timestamps; optional expiry timestamp. Owner ID is existing auth text, bounded at service boundary to 256 UTF-8 bytes. Overflow requires repair, never wraps. |
| Credential version | Composite identity `(connectionId, credentialVersion)`; immutable owner/kind match connection; versioned envelope above for API keys only. Exactly one current version; old versions cannot resolve. Retain encrypted old versions inaccessible until retention is decided; no plaintext history. |
| Nonce ledger | `(keyId, nonce)` unique; envelope/key-check identity; no plaintext. Persists across replacement/revocation and ciphertext cleanup. |
| Mutation receipt | Owner-scoped operation UUID and operation type; target ID, expected revision, request MAC, safe result/revision. Unique `(ownerUserId, operationId)`. Store no raw request. Retain with connection for v1. |
| Dispatch grant | Durable owner/run/attempt/action identity, connection ID, pinned credentialVersion, lease ID, expiry, state `pending`, `issued`, `cancelled`, `expired` or `uncertain`; no ciphertext/plaintext. Implement with RFC-008/010 durable dispatch rather than a second independent lease engine. |

API design is service-level only; no public URL is selected here. `createApiKey(actor, operationId, provider, label, secret, expiresAt?)`, `listOwned(actor, cursor?, limit)`, `replaceApiKey(actor, id, expectedRevision, operationId, secret, expiresAt?)`, and `revoke(actor, id, expectedRevision, operationId)` return allowlisted metadata. List limit is 1–100 (default 50), with opaque owner-bound pagination. IDs/operation IDs must be canonical UUIDs. Provider is selected from the installed adapter allowlist, never an endpoint URL. Expiry, when present, must be future on write; it is checked using database time at grant issuance.

The DTO is `{id, kind, provider, label, state, revision, credentialVersion, createdAt, updatedAt, expiresAt, revokedAt}` only. No account token suffix, ciphertext, key ID, native path, secret length or raw driver errors. Labels are user text, never logged and never auto-derived from a credential. A reference is `{connectionId, credentialVersion}`; it is not a bearer capability. Shared definitions must not expose another actor's binding references.

Initial revision/version is 1. Replacement atomically increments both and invalidates readiness and pending grants for older versions; revocation increments revision and never reactivates. A new connection is required after revoke. Updates require exact expectedRevision. Requests cannot change owner/kind or silently substitute the latest credential version for a stale reference. Metadata-only edits, if later needed, increment revision without changing credentialVersion and require their own bounded service method.

Idempotency is first committed operation semantics with exact request matching. Derive a separate32-byte request-MAC key using HKDF-SHA256 with the deployment key as input key material, empty salt and UTF-8 info `zetta.connection.request-mac.v1`. Use HMAC-SHA256 over the UTF-8 JSON encoding of exactly one operation-specific fixed-position array:

- Create: `["zetta.connection.request",1,ownerUserId,operationId,"create-api-key",provider,label,secretBase64,expiresAtMsOrNull]`.
- Replace: `["zetta.connection.request",1,ownerUserId,operationId,"replace-api-key",connectionId,expectedRevision,secretBase64,expiresAtMsOrNull]`.
- Revoke: `["zetta.connection.request",1,ownerUserId,operationId,"revoke",connectionId,expectedRevision]`.

Every semantically effective input is included; no additional fields are accepted. A generated create connection ID is absent because it does not exist before the first commit; replays compare the request then return the original stored ID. IDs/provider are canonical validated strings, labels preserve exact accepted Unicode without normalization, secretBase64 is canonical encoding of the original validated UTF-8 bytes with no trim, and expiry is normalized once at the boundary to a safe integer UTC epoch millisecond or explicit null. Absent expiry means null, not undefined/omission. Reject ill-formed Unicode instead of replacing bytes. No arbitrary object ordering or locale-dependent formatting enters the MAC.

Store only the MAC, compare in constant time, and never expose it. Same owner+operation ID and matching request returns the original safe receipt without another write; different content/type is conflict, including changed provider/label/expiry. Authorize fresh membership before replay lookup/return; compare the receipt before enforcing the now-stale expected revision on a valid replay. Cross-owner operation IDs grant nothing. MACs remain private and count as key-dependent state during rekey.

A transaction commits connection, encrypted version, nonce ledger and receipt together. Lost acknowledgment is `outcome-unknown`; query/retry only with the identical operation ID, never generate another ID automatically. A receipt absent during an in-flight transaction is not proof of rollback; uniqueness and transaction completion settle the retry. No external provider action occurs inside these mutations. Database unavailability denies access rather than consulting an in-memory success cache.

## Resolution, revocation and lease ordering

No HTTP/model API returns plaintext. A trusted dispatch-only callback consumes authenticated bytes for one authorized run/attempt/action; the store never returns a reusable credential resolver to caller code. Dispatch authority is obtained from server-owned run identity and a fresh membership lookup. The current `requireActive(headers)`/`requireOwned` contract is for HTTP callers; scheduled dispatch needs a separately issued internal actor derived from the stored owner plus fresh membership, not a forged `ActiveActor` cast or cached admin/session.

Use a single lock order for grant issuance, replacement and revoke: membership row first, then connection rows sorted by ID, then dispatch grant. Lock membership and connection rows with PostgreSQL `FOR UPDATE` while checking active membership, owner-scoped reference, run/attempt authorization, current version, state, expiry and grant freshness. Membership removal must update the same membership row, so the database orders it against grant issuance. Re-read values after lock acquisition; membership lookup outside the transaction alone is insufficient. Unknown/foreign IDs return the same not-found result, including for admin.

Decrypt only within that bounded authorized issuance operation. Commit the durable `issued` grant before delivering bytes; if commit outcome is unknown, discard plaintext and mark/reconcile uncertainty without dispatch. No locks are held across network calls or harness execution. A pending grant is not permission to decrypt later: promotion to issued repeats all checks. Grants are single-use and expire after 30 seconds or the attempt deadline, whichever is earlier; expiry means no new delivery, not revocation of bytes already copied. Restart never reuses an issued/pending grant for automatic redispatch; durable supervisor reconciliation must establish whether external work began. An ambiguous delivery becomes uncertain, never an automatic resend.

The committed issuance is the linearization point: revoke/removal committed first means issuance fails; issuance committed first means the grant was already issued and may have reached the attempt. Revoke cancels pending grants atomically and records durable cancellation intent for issued grants; the supervisor closes streams/input and cancels affected work best-effort. Every later mediated tool action needs a new fresh check. There is necessarily a delivery/cancellation race after issuance: no claim that a DB revoke recalls bytes, aborts completed effects, or revokes a provider token. Provider-side revocation/rotation is required for copied credentials. A worker with raw API-key access can retain it; containment and egress remain independent release gates.

## Failure, restart and operator recovery

Missing/malformed/wrong key, missing check record, corrupt envelope/tag/nonce/AAD, unknown version, foreign owner/reference, revoked/expired connection, stale version, removed membership, database errors and uncertain commit all deny resolution. User-facing errors identify a repair category without secret content; internal logs contain fixed error codes and safe event IDs only. Do not serialize request bodies, crypto buffers, SQL parameters or native state. Credential entry must bypass model transcripts and analytics.

Restart with the same key and intact database preserves connection references; it does not revive grants, readiness or revoked bindings. Operators back up the key separately in restricted secret management and back up ciphertext/nonce ledger/receipts consistently. Document custody and test a disposable restore before release. A DB backup without the key cannot recover credentials. Losing the key requires users to reconnect, not administrator decryption or fallback. A compromised key requires incident response, provider credential rotation and a reviewed storage rekey.

At-rest encryption protects database-only disclosure. It does not protect against a compromised trusted process/operator with key access, malicious same-attempt code, rollback of the entire database to an older authorized state, or metadata leakage. Recovery from an old backup must remain dispatch-disabled until revocations and provider state are reconciled; do not silently resurrect old grants/connections.

No plaintext migration, host credential import, automatic online rekey or multi-key vault is included. Key ID and envelope version reserve explicit migration boundaries. Before changing keys, require a separate maintenance procedure: stop writes/dispatch, back up, authenticate/decrypt every retained envelope, re-encrypt with fresh nonces/new key ID, rebuild key check and nonce accounting, and handle old idempotency receipts explicitly (old request MACs cannot verify under the new key). Resume only after complete verification; never overwrite the sole key while any record depends on it. This remains a later operator task, not an implied working feature.

## Required proof and release gates

The present artifact proves a design and source/link review only. No crypto implementation, database migration, account, provider, native profile or runtime launcher was exercised by this task.

Implement a standalone disposable synthetic-key proof before accepting the crypto slice. Generate key and fake credentials in process memory; never print/write them. Capture named boolean results, runtime version and exit status only. Require round-trip for 1 and 16,384 bytes, reject zero/16,385 bytes, distinct nonces for repeat encryptions, nonce collision handling, wrong key/length/encoding, altered tag/ciphertext/nonce and each AAD field, truncated/unknown envelope, no plaintext released on authentication failure, and key-check mismatch. Restart proof must subsequently use two processes with an explicitly disposable key channel and encrypted disposable PostgreSQL records; an in-memory round-trip is not restart evidence.

Actual PostgreSQL integration must prove A/B/admin denial, removed membership, stale version, revoke/replace races in both lock order outcomes, duplicate operation matching/conflict, concurrent duplicate create, unknown acknowledgment reconciliation, key-check bootstrap conflict, missing/wrong key after restart, expiry and serialized/log output redaction. Capture safe receipts and cleanup under the active attempt directory. No fixture result replaces HTTP/browser validation of a later user-facing setup surface or actual isolated credential delivery/recovery.

Required next gates: bounded crypto/schema/service implementation assignments; generated migration review and disposable database proof; dispatch integration with RFC-008/010; native state proofs in RFC-012–018 and RFC-074–078; privacy/recovery aggregation in RFC-065/066/068. Accepted007b/c storage contracts may supply RFC-008's prerequisite without inventing a grant engine in007; full execution-resolution acceptance remains pending until008/010 integrates and proves it. No consequential owner product question remains in this selection. Deployment secret custody, supported native profile backends and actual recovery/rekey operations are explicit operational decisions before their respective release paths.
