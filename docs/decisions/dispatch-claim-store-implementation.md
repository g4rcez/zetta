# Private fixture claim-store implementation boundary

Status: proposed010c3b0, design only. Governing decision: [accepted claim-store design](dispatch-claim-store.md). This document fixes implementation seams and assignments; it does not authorize a worker, route, transport or schema change. Source review and root assignment precede each slice.

## Existing source and required gates

[dispatch-launch-codec.ts](../../apps/server/src/modules/runtime/dispatch-launch-codec.ts) already exports canonicalDispatchLaunchSpec/decodeDispatchLaunchSpec with exact historical ten-element bytes. [dispatch-claim-rows.ts](../../apps/server/src/modules/runtime/dispatch-claim-rows.ts) exports readDispatchClaim(raw,current,policy), with current typed from readRunRows; it checks scalar linkage, historical lease/deadline, supported fixture promises, canonical spec, policy/image and both digests. Neither parser authenticates a producer or grants permission.

[runs.ts](../../apps/server/src/modules/runtime/runs.ts) provides applyRunTransition(tx,owner,token,fact), whose caller must already hold membership and the earlier locks. [run-state.ts](../../apps/server/src/modules/runtime/run-state.ts) now contains cancelled_before_admission. Identity/token equality precedes terminal replay; new transitions require CAS, time monotonicity and available int32 revision. Initial owner cancel followed by no-admission cancellation takes two run revisions. This pure accepted extension is not the later locked absence/service proof.

[runs schema](../../packages/db/src/schema/runs.ts) and current producer code contain the nullable legacy tuple and server-stamped fixture/v1 activation revision. Actual current provenance lineage was reported blocked at normal setup85600 and is being diagnosed independently. [005g6 role design](membership-runtime-role.md) is source reviewed, not an actual deployment permission proof. Identity activation/lifecycle and lock-order receipts do not substitute for these separate gates. The source implementation can be reviewed while gates finish, but actual claim proofs require an accepted combined18-table lineage, and durable execution eligibility requires actual retention/role and activation/provenance controls. No source feature flag pretends those conditions are met.

[dispatch schema](../../packages/db/src/schema/dispatch.ts) has one capacity mutex, claims and grants. Its [custom guards](../../packages/db/dispatch-test-migrations/20261022191701_dispatch_guards/migration.sql) forbid deletion/truncation, require revision+1 for real updates, freeze released rows and retain cancellation/cleanup identities. [run custom guards](../../packages/db/run-test-migrations/20261022180711_runs_constraints/migration.sql) reacquire parent run before attempt writes and deferred existence checks. Preserve every existing migration and primitive unchanged.

## Exact composition and API

All new files live in apps/server/src/modules/runtime. Factories accept a trusted `Pick<Database,"transaction">` from composition, not caller transactions or database selectors. Trusted database implementation and deployment policy are TCB; these APIs do not defend against replacing the database driver itself. Every factory reparses/copies/freezes trustedPolicy using createFixtureLaunchPolicy; no environment, I/O or implicit bootstrap during construction.

| Entry | Closed input | Success |
| --- | --- | --- |
| bootstrapFixtureCapacity(db,trustedPolicy) | normalized policy only, separate trusted operator call | frozen `{installationId,policyVersion,globalLimit:2,actorLimit:1,createdAtMs,result:"created"|"existing"}` |
| createFixtureClaimStore(db,trustedPolicy) | trusted composition only | frozen methods below; no initialization query |
| reserveFixture | `{runId,attemptId,claimOperationId}` UUIDs only | ClaimStatus with result reserved for new commit, existing for repair |
| getOwned | issued ActiveActor and `{runId,attemptId}` | current ClaimStatus with result existing |
| cancelUnsubmittedOwned | issued ActiveActor and `{runId,attemptId,expectedRunRevision,expectedClaimRevision}` | coherent owner-cancelled/released ClaimStatus with result cancel_requested; unrelated terminal winner returns existing without release |

All input objects are strict/closed. Counters use existing positive int32 schemas; IDs use runUuidSchema. No caller-supplied owner, lease, producer, epoch, clock, generation, LaunchSpec, policy override, callback or reason is accepted. reserveFixture is reachable only from trusted private backend composition; return values never activate work. Ordinary owner methods preserve genuinely issued actor checks using requireOwned; catch AccessError and map NOT_FOUND to not_found and ACCESS_DENIED to access_denied without leaking SQL. Missing/foreign run or nested attempt returns not_found.

ClaimStatus is exactly `{runId,attemptId,generation,claimOperationId,claimRevision,runRevision,resourceState,logicalStatus,leaseExpiresAtMs,deadlineAtMs,cancelReason,cancelRequestedAtMs,releasedAtMs,result}`. UUIDs/counters/state enums come from parsed current rows; nullable times/reason preserve persisted null. It is a frozen object of scalars. No prompt, canonical payload, receipt, policy/image/account detail, authority or mayExecute field. Reuse the accepted closed error set: invalid_input, unsupported, not_found, access_denied, policy_mismatch, ineligible_producer, capacity_denied, operation_conflict, already_reserved, stale_revision, requires_reconciliation, storage_unavailable, outcome_unknown.

Known predicate errors survive unchanged. Missing/malformed stored data and failed parsers become storage_unavailable. A known configured installation/version/image mismatch is policy_mismatch. Unexpected driver/transaction failure on a mutation is outcome_unknown, including uncertain commit; owner read failure is storage_unavailable. No retry loop or alternate operation ID is created. Counter exhaustion requiring a new mutation is requires_reconciliation; exact historical replay can still succeed. Internal assertion/authority failures never become success or capacity reclamation.

## Capacity and bootstrap

bootstrap runs READ COMMITTED, inserts singleton1 using ON CONFLICT DO NOTHING, then SELECT FOR UPDATE of singleton1 and exact row decode. Compare installationId,policyVersion,globalLimit2,actorLimit1 and finite createdAt; preserve original timestamp on replay. Different stored configuration is policy_mismatch, never UPDATE. No membership, run or resource lock is acquired in this transaction. The creation result comes from INSERT RETURNING; absence followed by locked compatible row is existing. Any uncertain transaction completion returns outcome_unknown; same policy repairs safely.

Capacity has no image column. Bootstrap cannot persist or compare a policyVersion→image binding in an empty installation. Trusted composition must pin that immutable mapping and deploy a different policy identity only through separately reviewed lifecycle work. Every claim comparison checks its actual stored image/spec/recipe digests. Do not invent an extra column, claim the bootstrap proves image identity, or silently rewrite policy/version on existing rows.

Under the capacity row lock, one aggregate SQL statement counts all claims for installation with released_at IS NULL, plus FILTER(owner_user_id=owner). Cast count(*) to text; decode exactly canonical nonnegative decimal through BigInt with signed-int64 bound. Compare total<2n and owner<1n; require owner<=total. No limited snapshot, Number truncation or filtering by logical status, expiry, cleanup, pending action, cancellation or unknown outcome. Released claims remain tombstones but no longer occupy. Later release paths decrease occupancy and must never acquire capacity after membership.

## Reservation transaction and replay order

READ COMMITTED order is capacity singleton → one membership → run → current attempt → claim → grants when needed. Candidate owner lookup is nonlocking discovery, never authorization. No auth-account/installation lock is acquired after membership; current009/dispatch FKs target membership/run, so these are forward subsequences of the [accepted identity order](identity-lock-order.md). No external I/O occurs within locks.

1. Parse request before I/O. Inside the real transaction callback, nonlocking owner/run/attempt discovery denies missing IDs without granting authority; no extra db.select capability is required on the factory handle. Lock capacity row1 and validate policy/limits. Missing capacity fails storage_unavailable rather than bootstrap. Lock discovered owner membership FOR UPDATE; require active positive activationRevision. Then SELECT run by id AND owner FOR UPDATE, compare immutable discovered owner, and lock its exact current requested attempt. A different generation/attempt is not_found; never follow a foreign claim to lock its run out of order.
2. readRunRows establishes current immutable input/scalar/state correspondence. Require producerKind=fixture, producerVersion=1 and actorActivationRevision equal to current member. Null legacy or mismatch is ineligible_producer, including repair after reenrollment. Supported payload is fixture/null model/no connections/no resume, interactive or setup, maxToolCalls0, prompt UTF8<=65536 and output<=65536; retain all009 promises and reject unsupported without changing input.
3. Lock claim by exact attempt. For same claimOperationId, decode historical claim against the locked current rows and trusted policy, then return existing even after deadline, cancellation or release. No fresh expiry/capacity/queued gate runs first. Fresh membership/epoch/identity/policy validation still precedes repair. Different operation on this attempt is already_reserved. For no claim, nonlocking lookup of globally unique operation rejects foreign use as operation_conflict; do not reveal its owner or lock its rows. Capacity serializes legitimate inserts; the unique constraint remains the final arbiter. An unexpected uniqueness/driver error is not assumed to mean successful repair.
4. New reservation requires queued run and current attempt, no lease/claim/cancellation/start/stop/result/terminal facts. A running unclaimed row is requires_reconciliation; a valid already-terminal unclaimed row is unsupported. Read floor(clock_timestamp()*1000) after all waits and predicates. Validate finite epoch and checked addition of deadlineMs; do not use host time or a transaction-start timestamp. Generate one lease UUID for this transaction; expiry=deadline=now+input.deadlineMs. Construct existing008 context from exact immutable row IDs, fence=generation, recipe fixture-v1/echo, mapped budgets input65536/output from009/frame min8192,65536,output. Use parseLaunchSpec(spec,{nowEpochMs:now,authorizedDeadlineEpochMs:deadline,policyVersion:policy.policyVersion}) for fresh admission, canonicalDispatchLaunchSpec for exact stored bytes and expandFixtureRecipe for both digests. Historical repair uses readDispatchClaim, never the fresh clock parser.
5. Evaluate aggregate occupancy while capacity remains locked. Issue the private token only after all eligibility/policy/input/count predicates pass. Verify immediately before actual applyRunTransition(claimed); use current run token with null preclaim lease and current revision, planned lease/expiry and the same DB instant. Validate returned revision/state against planned projection. Verify the same private token at the claim-insert checkpoint, then insert initial revision1/not_submitted/all nullable facts NULL, createdAt=updatedAt=claimedAt. Reread current run/attempt and claim, reuse both row parsers, and construct safe DTO. Claim insertion failure rolls back the actual lease transition.
6. Invalidate scope/token before callback return or throw. Only resolve reserved DTO after actual commit. Do not prepare a resource, emit a callback, create grants, renew or free occupancy in this operation.

## Private authority and dead-scope verification

Keep the issuer and mutable bookkeeping physically inside createFixtureClaimStore in claim-store.ts. Neither a separate authority factory nor a test-only mint is exported. The factory owns a WeakSet of token objects and WeakMap token→metadata. A transaction callback creates a fresh private scope object with active=true and exact tx identity; only that callback can mint Object.freeze({}) after step5 eligibility. Metadata binds scope, tx, operation=reserve_fixture, owner, activation revision and producer, run/attempt/generation, inputSnapshot bytes, planned lease, claim operation, policy/image and canonical/digest identity. It also binds preclaim revision and expected claimed revision. Metadata contains a private checkpoint (claim_transition, claim_insert, done), advanced only after validated DB results; tokens cannot repeat either write.

The internal verifier first requires its own WeakSet membership and metadata, then exact tx/scope identity, active scope, operation, checkpoint and every immutable binding. No exported predicate can bypass this first check. Re-run it immediately before each mutation, with the exact locked/current identity for that checkpoint. Any additional await before a future mutation requires a new verification; no callback or network seam exists between verification and issuing that query. The tx itself comes only from the trusted db.transaction callback; reserveFixture never accepts caller-supplied transaction or rows.

A narrow pure export in claim-store-contract.ts, `matchesClaimScope(binding,expected) → boolean`, may compare reference identity, active flag, operation/checkpoint and frozen scalar/byte bindings. It neither owns a WeakSet nor accepts/returns an ExecutionAuthority, issues a token, invokes SQL, or authorizes any service method. A caller can manufacture data for this predicate and obtain true; that has no effect because actual service acceptance separately requires the unreachable factory-private token registry. Tests vary active=false, different transaction/scope objects, every scalar/input byte, operation and checkpoint. These are pure predicate controls, not authority or SQL proofs.

The real callback finally path supplies the missing lifetime control without a minting seam: while the issued token and its metadata are still present, set scope.active=false, call the same internal verifier and require rejection; then in a nested finally remove WeakSet/WeakMap entries regardless of assertion outcome. Require rejection again after deletion. Thus actual successful reservation/rollback scenarios necessarily pass the real dead-scope check, not just an external imitation. A broken check throws a fixed storage_unavailable before callback completion and prevents commit. No token/reference leaves through DTO, logging, callback, diagnostic result or exception. Pre-issuance failure has nothing to invalidate. Cross-factory acceptance is impossible through distinct private registries; pure identity controls/source inspection are distinguished from observed actual callback lifetime checks.

This token authorizes only two reservation writes within one transaction. It is not durable provenance, a queued ticket, an owner credential or future prepare/action authority. A restarted factory creates its own token only after fresh durable checks.010d must separately design action-purpose authority and authentic settlement facts.

## Owner read and atomic unsubmitted cancellation

getOwned validates genuinely issued actor, locks that owner membership then owner-scoped run/current attempt/claim, and parses current history under trusted policy. It does not enforce current activationRevision equals historical producer revision: read authority differs from execution eligibility. This lets the currently active owner inspect retained old-enrollment history, while reserve repair remains denied. Foreign/admin/forged actors cannot cross that boundary.

cancelUnsubmittedOwned takes membership→run→attempt→claim, then ordered grant rows by id FOR UPDATE. An empty grant query alone is not a range lock: exclusivity comes from the already locked parent claim and the protocol requiring every future grant/prepare writer to lock run→attempt→claim before recording its fact. Existing FK key-share also waits on FOR UPDATE of the claim. The serialized writer must revalidate cancellation/release after its wait; raw privileged inserts are TCB and can never be treated as compliant runtime operations. Include an actual race with such a compliant contender in the service proof. Any grant row, including cancelled/expired/uncertain history, precludes the initial never-admitted proof.

Require not_submitted, absent prepare/receipt/pending/cleanup/release, leased running/no_effect, no start/stop/result, exact current identity and policy. Read a fresh DB clock after locks; require it no earlier than all current relevant facts. A coherently owner-cancelled/no_effect/null-result/null-stop claim already released as not_submitted replays before CAS and preserves all timestamps/revisions. Another coherent terminal winner returns existing without changing the run/claim or releasing occupancy. Any possible submission or grant/history fact is requires_reconciliation. New mutations require both supplied revisions, sufficient counter space and coherent existing intent.

For initially absent intent, precompute pure owner cancel then cancelled_before_admission using the returned intermediate revision and same instant. Apply those exact two transitions through applyRunTransition in the same real transaction, each with the current lease/generation and expected revision. Set claim owner/time, cleanupKind=not_submitted, cleanupConfirmedAt=releasedAt=that instant, updatedAt=that instant and revision+1 in one guarded update; run finishes cancelled/no_effect, result=NULL, stopConfirmedAt=NULL. Preserve earlier coherent owner intent if already present; do not fabricate a process-stop fact. Full final row parsing must succeed before commit. Claim update failure rolls back both run transitions. No capacity lock is acquired; retained claim simply ceases occupancy after commit.

**Required cancellation-routing integration:** today's009 createRunStore.cancelOwned can write owner run intent without a claim update. Under the narrow accepted initial boundary, run-only or claim-only intent returns requires_reconciliation; do not guess timestamps or silently fill the other half. Before exposing both owner APIs together or enabling a worker, register a separate009/010 child to route claimed-run owner cancellation through one transaction-aware service that owns membership→run→attempt→claim→grants, while queued/unclaimed cancellation stays009. It must avoid nested transactions/out-of-order locks and preserve owner-request provenance. That child needs concrete actual009-cancel-then-claim-cancel and both-order contention tests. It is an explicit incomplete dependency, not completed by this proposal or deferred indefinitely. Initial proof must exercise existing009 cancel interaction and verify unchanged requires_reconciliation denial.

Removed membership denies ordinary read/cancel/reserve; later privileged safety reconciliation is a separate closed service. Membership removal integration must persist cancellation intent before its lock releases and has its own pending proof; no backend cause, stopped boolean, resource callback or caller reason is introduced here.

## Actual proof assignments and binary oracles

All scenarios use reviewed fresh18-table fixture, independent reserved clients, observed pg_blocking_pids edges, finite pauses and whole owned service disposal. Never issue concurrent transactions on one PoolClient, loosen timeouts, delete tombstones or claim private token predicate tests prove database serialization.

| Scenario | Required observable |
| --- | --- |
| Explicit bootstrap absent/exact/mismatch and two-client race | singleton1, immutable first timestamp, exact2/1 policy; mismatch leaves all rows unchanged |
| Eligibility/access | issued A/B/admin/forged and legacy/null/wrong producer/old activation/current pointer/input/policy cases; correct fixed code and zero new leases/claims |
| Same operation and competing different operations | observed gate blocking, one claim/lease and retained operation; duplicate existing, loser already_reserved; foreign global operation_conflict |
| Capacity2 global/1 owner | independent owners serialize at gate; exactly two unreleased total and one per owner; extra request remains queued |
| Tombstone occupancy | synthetic expired/terminal/unknown/cancelled-but-unreleased rows still count; actual owner never-submitted release frees exactly one; released row remains immutable |
| Clock after wait | observe capacity/member/run wait, release, prove created/claimed time and full duration derive from post-wait DB time, never transaction-start/host time |
| Atomic reservation failure | real claim-insert fixture rejection after actual claimed transition; queued/null lease/no claim after rollback |
| Lost commit acknowledgment | wrapper throws after real commit; independent client sees claim before identical-operation repair; no second lease/claim; a new factory repairs durable row without process-restart claim |
| Owner cancel success/replay/CAS | exact two run revisions/one claim revision on first absent-intent cancel; repeat preserves first times before stale CAS; failure rolls back whole state; max counters fail safely |

Future fresh-process repair is separately scoped if requested; a new factory is not a process restart. Current005g6 grants cover reenrollment/run submission only and do not grant dispatch writes: a separately reviewed confined fixture/deployment profile must cover capacity/claim/grant reads and correct lock-column privileges before claiming production readiness. Structural dispatch SQL, accepted pure codecs, this design and source-only store each have narrower evidence than the actual claim/cancellation protocol.
