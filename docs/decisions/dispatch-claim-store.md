# Fixture claim and capacity transaction foundation

Status: revised design accepted after [coordinator independent review](../reviews/dispatch-claim-design-010c3-review.md),2026-10-22. Design only; pure codec/row implementation may be separately assigned. No schema, database, worker, launcher or provider execution is authorized here. Only acceptance status changed after the reviewed freeze.

Inputs: [010a dispatch](durable-dispatch.md), [010c1 storage](dispatch-storage.md), [010c2 schema](../../tasks/010c2-implement-dispatch-schema.md), [010c2a actual structural proof](../reviews/dispatch-schema-010c2a-review.md), [010b1 pure contract](../../tasks/010b1-define-dispatch-action-contract.md), [009 runs](durable-runs.md), [007 connections](connection-secrets.md). Structural56-scenario SQL proof does not establish capacity enforcement, backend authority or genuine resource cleanup.

## Selected boundary

Implement durable trusted fixture submission and a private reservation store, with separately authorized owner reads/cancellation. It can explicitly bootstrap the fixture policy, submit/replay fixture input through009, reserve an existing queued current attempt, read current claim status and record owner cancellation of an unsubmitted reservation. It cannot prepare, bind a receipt, issue a grant, admit input, renew, release a possibly submitted resource, start a worker, execute a callback supplied by a request or call a transport. Releasing a proven never-submitted owner cancellation requires the separate009 terminal prerequisite below first. Claims remain durable occupancy facts; runs/attempts remain the queue.

009 validates fixture input and ownership but its bot/conversation/configuration fields are opaque identifiers, not real owned-resource queries. A syntactically valid stored row must not be promoted to producer evidence. Choose the minimal durable prerequisite:005 membership activation revision plus immutable009 producer kind/version/actor activation revision. Legacy untagged rows are ineligible. This allows eventual restart-safe claiming without a second process-local ticket protocol or synthetic session actor.

No fixture provenance/readiness flag enables native/public bot work. No schedules, delegated work, workflow origin, resume reference, credential binding or private resource reference is supported. Administrative status grants no cross-owner read/cancel permission. The backend reservation entry point is private trusted composition, not an owner route.

## Durable prerequisites and migration boundary

**005 activation revision:** add membership.activationRevision as a nonnull positive PostgreSQL int32. New membership starts at1. A separately reviewed migration sets every existing membership row to1 at the new boundary; this claims no earlier enrollment continuity and grants no trust to legacy runs. A removed→active transition increments exactly once under the membership lock; active→active, active→removed and removed→removed preserve the value. At2147483647, reactivation is denied, never wrapped, reset or replaced with a fresh identity value. Idempotent concurrent activation increments only for the transaction that actually changes removed to active. Bootstrap, invitation acceptance/reactivation and admin replacement must use this same rule under the reviewed005 identity order.

The schema child must enforce insertion at1 and OLD/NEW revision transitions, including maximum denial, with named guards; a trusted migration backfills before those guards become active. This monotonic counter provides exact non-resurrection without a UUID history ledger or timestamp assumptions. Old run/readiness evidence stores the historical integer and compares equality to current active membership. Do not FK the historical revision to the current revision: that would prevent legitimate activation increments.

**Membership retention:** existing runs.owner_user_id already references membership.user_id with restrictive deletion. Keep that FK and retain historical runs; future readiness evidence must likewise retain a restrictive membership-owner FK before it can authorize anything. Runtime roles must not have membership DELETE/TRUNCATE or DDL privileges; deactivation is a status transition, never delete/reinsert. Together these prevent deleting/recreating the same user membership at1 while retained run/readiness evidence exists. Any later history-retention deletion or membership-purge feature needs a separate non-resurrection design before removing those protections. Privileged database operators/migrations remain the trusted computing boundary; this counter does not defend against their deliberate rewrites or restoration of an inconsistent backup.

**Proof lineage prerequisite:** accepted baseline SQL and its hashes remain frozen. Generate a new identity activation feature migration and its guarded/custom constraints as a separate reviewed child. Before auth source accesses activationRevision, extend the verified identity proof lineage to check exact new folder/file/hash identities and apply this feature after the frozen baseline. The layered identity adapter must finish before auth construction/proofs and before007/009/dispatch helpers continue through that same lineage. Never silently repin, patch or replace old migration SQL to make the new column appear. Existing baseline migration proof stays valid for its old scope; new tests explicitly prove old-row backfill1, fresh-row1, lifecycle increments/preservation/exhaustion and restrictive retention on the combined schema. Review updated proof-helper consumers and migration ordering together, then separately authorize actual disposable execution.

**009 provenance:** add immutable nullable producerKind, producerVersion, actorActivationRevision as an all-null legacy tuple or a complete tuple. Initial closed nonnull form is producerKind=fixture, producerVersion=1, actorActivationRevision positive int32. No SQL default or migration backfill labels an old run trusted. New trusted fixture submission reads the active activation revision under its existing membership lock and inserts the tuple atomically with run/attempt; the request body never supplies provenance. Update009's immutable trigger, closed row parser and canonical consistency checks through a separately owned generated/custom migration and tests. CanonicalRunInput remains byte-compatible; provenance is immutable server-stamped metadata outside the caller's request tuple.

The accepted fixture-only009 producer is the sole writer of fixture/v1 provenance. Real bot/conversation/configuration validation belongs to020/025's future different producer contract; do not broaden this enum now to imply those exist. Database roles/privileged SQL remain a trusted storage boundary, as in existing009: schema shape cannot authenticate a malicious DB operator. No public generic producer discriminator setter is exposed.

Identical request-key replay retains the original run/provenance/activation revision and never upgrades a legacy or old-enrollment row. Owner reads/cancellation retain their own current authorization independent of execution eligibility. Reservation of missing/mismatched provenance fails `ineligible_producer`; after re-enrollment, an explicit genuinely new owner request may create a new run/key, but no automatic resubmission or replacement occurs. This is the minimal durable option: one005 field and three009 fields, versus rejected transient tickets plus a second reissuance API that would later need replacing. Both migrations and all affected005/009 paths require separate review/actual proof;010c3 cannot implement around their absence.

## Exact proposed APIs and composition

Proposed names are new contracts, not existing exports:

- `bootstrapFixtureCapacity(db, trustedPolicy)`: separate operator/composition entry point, never returned on an owner-facing store. Explicitly inserts singleton1 with limits2/1; existing exact policy is an inert success. Missing-row creation is serialized by the singleton unique key using insert-on-conflict-do-nothing then locked exact read. A mismatched row returns `policy_mismatch`, never upserts. This function runs before stores admit reservations and has no runtime route.
- `createFixtureClaimStore(db, trustedPolicy)`: synchronous factory; no startup I/O, implicit bootstrap or environment reads. Policy is a closed object accepted through008's `createFixtureLaunchPolicy` and a fixed versioned fixture budget recipe described below. Trusted policy input is server composition, not request JSON. Factory returns frozen methods only.
- Existing009 `submitOwned(actor, request)` gains trusted fixture provenance stamping in its separately assigned producer extension, with the same owner/request replay semantics. It returns its existing RunDto, not a new ticket. A public caller cannot request a producer kind/version/activation revision.
- `reserveFixture({runId, attemptId, claimOperationId}) → ClaimStatus`: private backend method on trusted composition, never an HTTP/tool method. Operation UUID is generated once before invocation and retained for unknown-commit repair. No actor object, owner string, lease, timestamp, generation, revision, image, policy or arbitrary LaunchSpec is accepted. Stored immutable provenance plus fresh locked membership/current rows establish eligibility.
- `getOwned(actor, {runId, attemptId}) → ClaimStatus`: current/known claim status only, after owner-scoped fresh membership and run/attempt validation. Unknown/foreign nested IDs return the same `not_found`. No claim means `not_found`; no implied queued-work authority.
- `cancelUnsubmittedOwned(actor, {runId, attemptId, expectedRunRevision, expectedClaimRevision}) → ClaimStatus`: owner cancellation for a coherent never-submitted claim, with atomic no-effect termination/release only after the required009 extension is accepted; otherwise this integration remains gated, not simulated. Exact repeats return current already-cancelled status before stale-CAS rejection. No setup/backend reason is accepted from the caller. Submission or pending/receipt/cleanup/release facts return `requires_reconciliation`, never fake a stop.

`ClaimStatus` is a frozen closed safe DTO: runId, attemptId, generation, claimOperationId, claimRevision, runRevision, resourceState, logicalStatus, leaseExpiresAtMs, deadlineAtMs, cancelReason, cancelRequestedAtMs, releasedAtMs, and `result=reserved|existing|cancel_requested`. It contains no canonical private input, prompt, raw LaunchSpec, transport receipt, execution token, image/account details or `mayExecute` boolean. A returned reserved row is not permission to perform I/O. The planned initial factory never consumes this DTO as authority.

Closed errors: `invalid_input`, `unsupported`, `not_found`, `access_denied`, `policy_mismatch`, `ineligible_producer`, `capacity_denied`, `operation_conflict`, `already_reserved`, `stale_revision`, `requires_reconciliation`, `storage_unavailable`, `outcome_unknown`. Preserve005-issued-actor error boundaries or map them explicitly at the service adapter without exposing raw causes. Known SQL/shape failures are not silently converted to successful replay. No raw driver error, SQL, row snapshot or private prompt is logged.

## Private transaction authority

The factory first reads candidate owner identity without locking, then locks the capacity gate and that membership before locking run/attempt. Immutable owner is reread/compared under lock; no row is authorized by the candidate read. Require membership active with a valid positive current activation revision, exact fixture/v1 producer tuple and equality to the run's actorActivationRevision. Never call005 requireOwned with a backend-constructed actor. Human owner reads/cancel still require genuinely issued ActiveActor objects.

A factory-private issuer creates `ExecutionAuthority` only inside this factory's real transaction callback after capacity/membership/run/attempt locks and all reserve predicates succeed. Use a private WeakSet plus private metadata WeakMap. Metadata binds the exact transaction identity object, active scope, operation kind reserve_fixture, stored owner/activationRevision/producer, run/attempt/generation, planned lease ID, claim operation and exact normalized input/policy identity. No exported issuance function accepts a parsed owner string, arbitrary row or caller-supplied Drizzle transaction.

The internal verifier checks membership in that issuer's WeakSet, same transaction object, active scope and exact locked identity/operation. Claim insertion/lease persistence calls it immediately before mutation. A finally block invalidates/removes the token before the transaction callback returns or throws; commit acknowledgment does not extend its lifetime. Tokens never appear in returned DTOs, caller callbacks or persisted data. A different factory, transaction or replay cannot reuse one. There is no public generic withAuthority callback just to facilitate testing.

This is reservation-purpose authority, not activation/input/grant authority.010d must separately bind a newly issued action-purpose token to exact current claim/grant/action and real provenance in its own transaction. Restart reads durable eligibility and issues a fresh transaction-local token; it never deserializes an old one. Tests cover missing/wrong/legacy/old-activation-revision provenance, forged owner actors on owner methods and DTO non-disclosure. Test the internal verifier's dead-transaction branch within its narrowly owned module without exposing an issuance seam that accepts arbitrary transactions. Review the concrete module boundary before implementation if a test-only export would otherwise be needed.

## Stored codecs and exact comparisons

Use closed Zod row parsers over Drizzle results, rejecting unknown columns when a selected projection is passed, unsafe numbers, invalid/nonfinite Date values, malformed optional pairs and state/time inconsistencies. Dates normalize to integer UTC milliseconds and normalized rows/DTOs are readonly/frozen. DB types/checks are not sufficient validation of imported/restored/corrupt data.

`readRunRows` already decodes canonical009 input, verifies scalar correspondence, current attempt linkage and pure lifecycle state. Reuse it without copying or weakening it. Claim codec validates all010c1 fields and initial/retained states, then compares attempt/run/owner/generation/lease, claim.createdAt=attempt.claimedAt, expiry within immutable deadline, installation/policy/image, and claim operation identity. No claim-side renewable lease or copied logical outcome is added. Historical read may accept expired leases as history; new reserve cannot resurrect them. Repair uses historical parse and retained canonical bytes, never a fresh-deadline LaunchSpec admission check. A configured policy/image mismatch fails closed rather than rewriting the original claim.

A new small pure `dispatch-launch-codec.ts` is required;008 currently exports `digestLaunchSpec`, `parseStoredLaunchSpec` and `parseLaunchSpec`, not a canonical text decoder. Decode exactly this fixed ten-element tuple:

```text
["zetta.launch.spec",1,
 [actorId,runId,attemptId,botId,conversationId,configurationId,routineIdOrNull,delegationIdOrNull],
 leaseId,fence,recipe,fixtureCase,policyVersion,deadlineEpochMs,
 [deadlineMs,maxInputBytes,maxOutputBytes,maxFrameBytes]]
```

Reject non-string/ill-formed UTF-8/NUL, over16384 bytes, invalid JSON, wrong tuple length/tag/version or any unknown alternative. Decode into008's existing historical parser, re-encode canonically and require byte equality. Recompute `digestLaunchSpec` and reconstruct `expandFixtureRecipe(spec, trustedPolicy).identityDigest`; compare both persisted digests, policy and image. Hash equality alone never substitutes for canonical byte equality.

Compare spec.context actor/run/attempt/bot/conversation/configuration against locked009 rows/input; routine/delegation must be absent, fence equals generation, lease equals assigned lease, deadline equals claim deadline, and recipe/case/budgets equal the selected fixture policy.009's configurationVersion remains in its immutable input;008 context has configurationId only, so check the pinned input/configurationVersion separately rather than inventing a tuple field. Generated codecs must round-trip the tuple already hashed by008; do not change008's hash format incidentally.

For the first lane select fixture-v1/echo only, model=null, connections=[], resume=null, interactive/setup origins, maxToolCalls=0. Accept existing009 deadline1..60000, but reject inputs whose promised maxOutputBytes exceeds65536 or whose prompt byte count exceeds65536. The trusted recipe sets maxInputBytes=65536, maxOutputBytes equal to the accepted input output budget, and maxFrameBytes=min(8192,maxInputBytes,maxOutputBytes), all positive. maxEvents/maxToolBytes stay pinned009 input promises, not invented008 fields. Actual wire framing/cumulative input feasibility must be checked before future input admission; no transport delivery is promised here. Preserve semantic budget mismatch as `unsupported`, never silently truncate.

Fixture bot/conversation/configuration IDs remain explicitly synthetic correlation IDs. No actual bot availability, team visibility, conversation ownership, readiness or native-account entitlement is inferred.020/025 public producers require real resource queries and trusted stored provenance before reuse of this foundation outside the isolated fixture lane.

## Explicit reserve transaction

Use READ COMMITTED and the accepted order: capacity singleton → actor membership → connections/key-check when supported (none here) → run → current attempt → claim → grants (none written). No installation/auth-account lock is acquired after membership. Initial lane has one owner membership; multi-owner bot use must wait for the separately audited005/020 order extension. Existing009 attempt triggers reacquire their parent; therefore run is always already locked before attempt writes. No lock spans filesystem, network, launcher or human interaction.

1. Parse the closed request and read candidate immutable owner without a row lock. Unknown run/attempt returns not_found. Lock capacity row1 and validate exact trusted installation/policy/limits. Missing singleton fails closed, with no lazy repair.
2. Lock the discovered owner membership and require current active status/activation revision. Select the run with that owner predicate FOR UPDATE, compare immutable owner to the discovery read, and lock exact requested current attempt. Reuse readRunRows, require fixture/v1 provenance and matching activation revision, and compare its exact normalized input/run/attempt/generation. Query/lock claim by attempt; do not acquire an unrelated run through a claim discovered later.
3. Before queued/stale/deadline/capacity predicates, handle original-operation repair. An existing same-attempt claim with the same operation and exact pinned identity returns validated current status, regardless of subsequent cancellation/expiry/release; it grants no fresh authority. A different operation on that attempt yields `already_reserved`, not new lease/claim. If the globally unique operation belongs to another attempt, return fixed `operation_conflict` without disclosing its owner. A nonlocking unique-key lookup can reject that collision; unique insertion is still the final race arbiter. Never follow and lock the foreign run out of order.
4. For absence, require the current attempt/run queued, no lease/claim, no cancel/start/stop/result/terminal facts and supported fixture input. Do not turn a running unclaimed row into a recovered reservation. Read DB `clock_timestamp()` only after locks, floor to milliseconds, derive immutable deadline=now+input.deadlineMs and initial lease expiry equal to that deadline. Generate lease UUID once inside the transaction; no renewal method in this slice.
5. In one aggregate statement count **all** claims with this installation and released_at IS NULL, total plus owner FILTER count. Parse PostgreSQL bigint count text using a closed nonnegative decimal grammar and BigInt (at most signed-int64 maximum), compare against2n/1n without Number truncation; counts above limits deny without materializing a bounded1024-row snapshot. Do not omit terminal, expired, stopped, unknown, cancelled or logically unrelated occupied claims. Capacity row serializes every insertion. Releases cannot increase occupancy and remain ungated in their later service.
6. Issue the private reserve-purpose authority; verify it; apply009's actual `claimed` transition using its current token/lease/fence and same DB instant. Insert initial claim revision1/not_submitted/all nullable facts NULL with exact immutable spec/digests/policy, then reread/parse the joined result. Lease assignment and claim insertion commit atomically. A failed insert rolls the attempt transition back; no partial running lease may escape.
7. Invalidate authority on callback exit. Return status only after successful transaction completion. Never call prepare, create a grant or emit a side-effect callback before/after commit in this method.

The singleton bootstrap's absent insert does not lock membership or run; competing bootstrap transactions converge through its unique key, then exact comparison. A mismatch fails and cannot alter frozen policy. Reservation locks the singleton before membership regardless of whether it expects to replay; read/cancel paths omit capacity entirely.

## Replay, failures and restart

Same claimOperationId is a repair identity, not a retry command. On a transaction/commit error whose outcome is not established, return `outcome_unknown`. Trusted caller retries the identical run/attempt/claim-operation request. If the reservation committed, return its current status and retained lease; if it did not and current queued state still permits reservation, the retry may atomically reserve once. Different operation IDs cannot evade the attempt PK or spent history. Neither replay result nor an `existing` status calls prepare or refreshes expiry.

After process restart the private backend can reread the persisted run/attempt/provenance and repair the same claim operation, subject to current membership/activation revision/policy checks. It does not need an old session or a process-local ticket. Same009 request replay remains available to the owner and returns the original run; it does not stamp a new activation revision or alter producer metadata. A different current attempt/generation conflicts; future retries require separately reviewed provenance. No native/public readiness is inferred from successful fixture repair.

Known capacity/policy/access/CAS failures return their closed reasons and do not change either run/attempt or claim. Unexpected parser/driver failures suppress values and fail closed. If the original committed row is corrupt, replay fails `storage_unavailable`; do not manufacture the old safe response, clear a claim or reclaim occupied capacity. A post-real-commit exception proof must show independent-client readback before same-operation repair; it is a lost-ack boundary injection, not a claim of real TCP failure.

## Cancellation and retained occupancy

For `cancelUnsubmittedOwned`, lock active owner membership → run → attempt → claim, validate exact identities and expected revisions, and require resourceState=not_submitted, prepare/receipt/pending/cleanup/release absent, no started/stop/result facts and effect=no_effect. Apply the existing009 owner `cancel` fact, then record claim cancelReason=owner/cancelRequestedAt from the same DB instant and increment claim revision atomically. If already coherently owner-cancelled, return current status without changing retained timestamps. A mismatched half-record is corruption, not permission to fill in a guessed time. Competing terminal state wins and returns its validated current status without rewriting history.

**Required separate009 no-effect terminal extension:** current009 cancel records intent for a claimed running attempt; it cannot terminalize that attempt as no-effect. Add a closed trusted backend fact `cancelled_before_admission` with atMs. Its pure transition permits only a leased running/no_effect state with no startedAt/result/stop fact, preserves any existing owner cancellation time, and produces cancelled/no_effect, finishedAt=atMs, result=NULL, stopConfirmedAt unchanged NULL. It does not invent an actual stopped-process observation. Pure parsing must continue accepting owner-request provenance separately; no fake completed result or crash/lost fact.

The trusted service invoking that fact must first lock membership→run→attempt→claim→all grants and prove exact current identity, prepare_intent_at/receipt/pending absent, resourceState=not_submitted, no grant rows/admission, and no resource/action operation could have started under the commit-before-prepare protocol. This is a transaction-backed absence/history proof, not a caller boolean. The initial owner cancel may then apply owner `cancel`, apply `cancelled_before_admission`, record claim owner reason/time, cleanupKind=not_submitted/cleanupConfirmedAt and releasedAt in the SAME transaction with one retained claim revision advance and valid run transition revisions. No capacity lock is needed because this only decreases occupancy. Exact replay validates the already coherent terminal/released result and preserves timestamps.

Until that009 extension and its actual service proof are accepted, cancel remains intent-only and capacity stays occupied. The implementation must not secretly substitute another terminal fact. The extension can reuse existing schema's cancelled/no_effect/null-result shape; inspect full009 parser/projection/history tests before assuming no schema change. Backend reason owner/deadline/revocation/shutdown/recovery is persisted in dispatch_claims, which already has the closed fields. The new pure fact need not forge009 cancellationReason or cancelRequestedAt for a backend cause: those existing009 fields remain specifically owner-request provenance. A separately reviewed private safety operation can later record a backend reason and no-effect terminal outcome without pretending a human requested it. Effect-bearing/backend interruption semantics still belong to010d and are not solved by this fact.

Removed owners are denied ordinary reservation/read/replay. Later safety reconciliation may lock removed membership and cancel only already-owned facts without issuing execution authority. There is no general caller-set settled/terminal/cleanup flag. Genuine removed-resource settlement requires an accepted authenticated008 fact issuer; a receipt UUID alone is not one. No initial store method releases a prepared, pending, unknown or possibly submitted resource.

Removal/activation revision integration must persist cancellation intent before releasing the membership lock and make removed→active reactivation increment the activation revision exactly once; old queued runs and confirmations remain ineligible. Actual proof must exercise removal/reactivation before and after reserve with retained provenance. These are required prerequisites for durable background eligibility, not indefinitely deferred assumptions; no worker is enabled by this design alone.

4. **010c3c actual store proof:** guarded adapter reuse, bounded entry/cases/races and root-owned fixed launcher delta. Source freeze/review/target authorization precede DB execution. 5. **Later010d:** separately assign effect-bearing cancellation, real launcher-fact/action-authority issuers and private reconciliation before grants/prepare/worker composition. No incidental completion of those contracts inside claim-store tests.

Actual proof matrix: activation migration backfill1 with legacy runs still untrusted; new membership1; removed→active increments exactly once under concurrent retries; active→active/removal preserve; MAX denies reactivation; membership deletion/reinsertion blocked while evidence remains; exact frozen-baseline-plus-feature proof lineage; explicit capacity bootstrap exact replay/mismatch/race; A/B owner-method isolation, forged actor and legacy/foreign/old-activation-revision producer denial; same run/attempt/op contention produces one claim and one lease; different op on same attempt never replaces it; global2/per-owner1 with different owners and independent clients; capacity full with terminal/expired/unknown claims remains full; forced claim insert failure rolls back leased attempt; current-pointer/owner/input/config/model/budget/policy/digest corruption fails; fresh-clock duration after observed lock wait; owner cancel/replay retains first timestamps; before terminal-extension integration it retains occupied count, afterward actual never-submitted proof releases exactly once; removal wins before reserve denies, reserve wins before removal commits at most one retained claim then later reads/requests deny. Temporary states for occupancy proofs are explicitly synthetic persisted fixtures, not actual resource observations.

For unknown commit, wrap the actual completed transaction then throw, confirm persisted claim through another reserved client, and retry identical op without a second lease/claim; precommit failure must leave queued/no claim. New factory plus durable provenance and identical claim operation repairs the same row;009 request replay retains its original activation revision. True fresh-process replay gets a separate guarded process slice if included; new factory alone is not restart proof. Inspect returned DTOs for no authority/canonical private fields. No test should mistake a safely denied dead transaction for a real committed capacity proof.

Evidence must bind source hashes and each scenario's actual binary observable. No service correctness is established by this design, by pure Draft.newAdmission or by the accepted structural schema proof. Root acceptance and bounded assignments remain required.
