# Durable dispatch, capacity and grants

Status: accepted bounded design after independent CLEAR/APPROVE,2026-10-22. RFC-008 operational launcher is not accepted; RFC-009 owned store is in progress. This acceptance authorizes no migration, claim loop, secret resolver, route or external execution. Source foundations proceed only through explicit bounded assignments; transaction-backed authority issuance remains a separate source/proof gate.

## Reused contracts and selected foundation

PostgreSQL `runs`/`run_attempts` remain the sole runnable queue. Reuse [durable run identity/input/state](durable-runs.md), [connection ownership and issuance](connection-secrets.md), [supervisor transport/containment](runtime-supervisor.md), and accepted008b/c LaunchSpec/journal source. Launcher journals are resource ledgers; they never select work or issue DB leases. No Redis, second queue, event-store framework or independent connection grant engine.

Initial executable integration is a secret-free fixture recipe only, with global capacity2, per-actor capacity1, fixed60second maximum attempt duration and no native/session/GUI bindings. These are trusted fixture policy constants, not request fields. Fixture success proves neither native readiness nor that the Linux/systemd launcher is provisioned. Native credentials require the separately reviewed extension below and actual containment/egress/protocol proof.

Observed current boundaries:005 issues ActiveActor through a module-private WeakSet after authentication; requireOwned rejects structural substitutes.007 metadata store keeps crypto private and has no plaintext resolver.009b2 parses canonical input/lifecycle but grants no authority.008c drafts must be durably written before effects and never replay unknown operations. These constraints are retained, not bypassed by dispatcher wiring.

## Authority: human requests versus backend work

Owner read/cancel/submit retain a freshly issued ActiveActor plus fresh membership FOR UPDATE in the operation transaction. Admin has no private-content bypass. Claiming durable work after restart cannot call requireOwned with `{userId,isAdmin}` or cache an old session actor.

Propose a separate private `ExecutionAuthority` issuance contract owned by the trusted dispatcher/identity integration, not a new kind of public ActiveActor. A factory closed over the trusted DB and finite fixture policy creates an unexported issuer and a module-private WeakSet of transaction-scoped tokens. The issuer takes an already locked run/attempt row loaded by that factory, verifies provenance from the accepted009 submission path, exact current attempt, supported origin, canonical snapshot/resource bindings and freshly locked active membership, then records `{ownerUserId,runId,attemptId,generation,leaseId,actionId,transactionIdentity}` internally. Consumers only receive an opaque readonly token and a verifier; they cannot mint by user ID, serialize it or retain it after the transaction callback ends. All credential/run checks still use the locked row identities. This is a proposed real source contract requiring independent tests, not a TypeScript brand asserted onto a caller object.

Only interactive/setup runs created by the accepted009 fixture producer are eligible initially. Schedules remain unsupported: no scheduled authority issuer exists. A future routine producer must derive owner from a locked active routine, prove its immutable version/configuration/readiness and persist that provenance before issuing the same bounded execution authority; no scheduler-provided owner field is trusted. Removal denies new claims, renewals, grants and tools even for previously queued work. Re-enrollment must not revive old queued work: removal cancels queued runs and marks active claims for cancellation before membership release; persistent queued-work eligibility after reenrollment must also use a membership activation epoch/provenance extension before scheduled/long-lived queue support. This extension is a migration/identity review gate, not an assumption about current timestamps being a robust epoch.

Safety reconciliation is a separate backend capability: it may read exact owned claim/journal facts and persist stop/cancel/cleanup after removal, without requiring the departed actor to authenticate. It cannot decrypt, admit input, renew for execution, claim another attempt or return private content to an admin. A removed membership row is still locked when present; reconciliation is not an active-member authorization bypass for effects.

## Proposed storage delta

Reuse existing attempt generation as immutable fence and existing lease ID/expiry/claimed timestamps; never create a second attempt lease. UUIDs are server generated; bounded counters use int32, times valid UTC milliseconds. SQL names below are proposals requiring a single migration writer. No schema is changed here.

| Record | Minimal fields and invariant |
| --- | --- |
| `dispatch_capacity` | singleton `id=1`, trusted `policyVersion`, `globalLimit=2`, `actorLimit=1`; row serves only as transactional admission mutex, no drifting counter. Missing/mismatched singleton fails closed. Explicit install initialization, never lazy first-request creation. |
| `dispatch_claims` | `attemptId` PK, `runId`, `ownerUserId`, immutable generation/lease identity, `claimOperationId` unique, `launcherInstallationId`, `policyVersion`, immutable complete secret-free LaunchSpec canonical text and identity digest, absolute `deadlineAt`; nullable `receiptId`, `prepareIntentAt`, `releasedAt`; `resourceState=not_submitted|prepare_pending|prepared|active|stopping|unknown|cleaned`; fixed `cancelReason` nullable; immutable createdAt and mutable revision/updatedAt. Composite attempt/run/owner FK. Lease duplication columns are validated against attempt under lock, not an independent renewable lease. Receipt binds once and cannot be replaced. |
| `dispatch_grants` | UUID `id`, composite claim/attempt/run/owner identity, immutable `actionId`, `kind=activate|input`, positive `sequence`, canonical descriptor/digest, nullable paired connectionId+credentialVersion, `state=pending|issued|cancelled|expired|uncertain`, `expiresAt`, createdAt, issuedAt/cancelledAt nullable; `deliveryOutcome=not_attempted|acknowledged|unknown`; unique `(attemptId,actionId)` and `(attemptId,kind,sequence)`. Composite credential ownership/version FK when present; tombstones retained. No plaintext/ciphertext/native files. |

Claims are ownership/occupancy facts, not another queue. Only queued current attempts in runs/attempts are candidates. Persist prepare intent before the first prepare call; an unknown create/prepare remains occupied even with no receipt. Count **every claim where releasedAt IS NULL**, per installation globally and per actor, including running attempts, terminal attempts with unconfirmed cleanup, unknown creates/starts and expired leases. A logical terminal state or timeout never frees capacity. Conservative release requires terminal logical outcome plus authoritative resource cleanup/no-pending-operation proof; external-effect uncertainty may remain and still bars retry of that logical work. Profile exclusivity will have its own stricter later proof, not inferred from capacity release.

Use one grant row per action, including credential-free activation/input, as the durable admission identity. Tool-invocation grants are not implemented in this foundation; host-tool execution stays unsupported until its own bounded admission extension. The first credential-bearing extension supports at most one pinned API-key connection per action; multi-key activation bundles remain unsupported pending a bounded atomic-bundle design. A run may reference up to32 connections, but each selected tool action must identify exactly the authorized pinned connection it uses. No arbitrary credential map or implicit latest-version fallback. Credential-free actions require both connection columns null. Secret-free fixture input is bounded and reconstructed from private009 canonical input; grant descriptors hold its identity/sequence/byte count, never its bytes.

Grant `issued` means admitted once, not successful delivery or external completion. Acknowledgment is a separate fact and never resets state to pending. `uncertain` forbids reissue. A semantic action ID cannot be replaced merely to escape a failed/expired/unknown grant. Closed row parsers and DB constraints must cover status/null/time combinations and immutable binding columns. Append-only tombstones survive restart; retention is deferred011/025.

## Complete lock graph

Runtime order: **capacity gate → membership → sorted connection rows → connection key-check singleton (when needed) → sorted runs → sorted attempts → sorted claims → sorted grants**. Claims sort by attemptId (their primary key); all other sets sort by their stable primary key. Each operation takes only a forward subsequence. Connection key-check is placed here because007 mutation already locks membership→connection→key-check; no grant path may take key-check after a grant and then request a connection. Read candidate IDs without row locks; acquire in order and re-read all predicates. Every claim receipt/resourceState/revision/cancellation/release mutation locks that claim after its run and attempt and before any grant; claim CAS is not a replacement for this order. No locks remain held across network, launcher, harness or human interaction.

The capacity gate is needed only for an increase in occupancy (claim insertion), not release. All insertions acquire it; releases cannot create over-admission, so ungated release may cause only a conservative stale-count denial. Policy changes, if later allowed, must acquire gate before anything else. A transaction already holding membership/run/connection/attempt/claim/grant must never acquire capacity. No counters are decremented asynchronously.

After acquiring the gate in READ COMMITTED, use one aggregate statement over claims with releasedAt IS NULL to count global and candidate-owner occupancy from the same statement snapshot. Do not FOR UPDATE the counted rows before their membership/run/attempt locks; the gate serializes every occupancy increase instead. An uncommitted concurrent release stays counted; a committed release can be omitted only after its authoritative cleanup transaction commits. Both cases preserve an upper bound on occupied resources. Set releasedAt once under membership→run→attempt→claim→grant as needed; never clear it, delete an unreleased claim, transfer its owner/installation or otherwise increase occupancy outside gated insertion. Release is monotonic and duplicate release inert. Claim insertion and attempt lease assignment commit together while the gate remains held. Unknown commit is still occupied if it committed, and repair reads cannot increase occupancy. This is a count of durable facts, not an asynchronous counter.

| Operation | Locked subsequence and linearization |
| --- | --- |
| Submit | issued actor → membership → run/current attempt insertion; unique owner/request key and canonical comparison. No capacity reservation until claim; no connections after run. |
| Claim | gate → membership → required connections sorted (none for fixture) → key-check if needed → run → attempt → claim if already present; count unreleased claims under gate, revalidate candidate/current generation/input/cancellation, assign lease once and insert absent claim atomically. Run/attempt lock and unique attemptId serialize absence. Commit is reservation. |
| Prepare/activate/input admission | membership → sorted connections if credential action → key-check → run → attempt → claim → grant. Confirm claim active/unreleased, owner/current generation/lease, deadlines, cancellation and previous operation settlement. Commit intent/grant before call. Activation admission atomically records009 admitted/uncertain before sending, rather than waiting for a start acknowledgment. |
| Owner cancel | membership → run → attempt → claim if present → grants; persist cancellation before any stop call, cancel pending and record intent for issued actions. Queued unclaimed cancellation has no claim. No connection lookup needed. Terminal-first remains terminal. |
| Renew | membership → run → attempt → claim; exact claim identity and known healthy resource, no cancellation/uncertainty, time not expired. Extend only leaseExpiresAt <= immutable absolute deadline and update claim revision atomically; no new lease, generation, input or grant. No resurrecting expired leases. |
| Replace/revoke connection | existing membership → connection → key-check; then affected grants sorted. Cancel pending grants, mark issued actions for cancellation in same transaction. Do not subsequently acquire run, attempt or claim locks. Worker consumes these grant facts in a separate membership→run→attempt→claim→grant transaction, re-reading the locked grant before updating the claim/run. |
| Membership removal | preserve existing identity administrative lock prelude; lock affected membership before runtime rows, then sorted runs→attempts→claims→grants. Cancel queued work and active admission atomically with removal. No capacity gate or later connection lock. |
| Stop/cleanup/reconciliation and prepare/action fact ingestion | membership row even if removed → run → attempt → claim → grant as needed; exact claim/resource evidence, no secret resolution. Commit receipt/resourceState/revision, terminal/stop facts and release occupancy only after required proof. No new capacity acquisition. |

Identity administrative prelude remains **installation singleton → required admin authorization membership (where existing endpoint uses it) → auth users → subject memberships**, with the existing sorted multi-user rules. Administrative methods never acquire capacity or connection key-check after runtime locks; workers never acquire installation/auth-user locks after membership. This preserves the existing partial order rather than reversing membership removal to fit a worker. Existing source paths (including enrollment/removal and operator replacement) must be audited together before implementation: any path requiring more than one membership must use its accepted identity order, and may not retain runtime locks while acquiring another membership. No batch claims across owners in one transaction. If integration reveals a reverse edge, stop and correct the shared order before enabling worker admission.

Claim query uses READ COMMITTED, locked capacity row and candidate recheck. A nonlocking bounded candidate scan ordered by createdAt/id supplies hints; claim one hinted run at a time after membership/connection locks. Optional `FOR UPDATE SKIP LOCKED` applies only at the already-correct run/attempt stage, never to choose a run before membership. Gate serialization ensures two workers cannot both admit against the same stale count. Two workers racing one attempt serialize on run/attempt and the unique claim. A fixed per-pass candidate limit64 avoids an unbounded transaction; idle/full/unsupported is an explicit result, not a busy retry loop.

## Private API and transaction boundaries

Proposed composition-only interfaces, no public URL or request-selected transport:

```ts
type ClaimToken = Readonly<{
  runId: string; attemptId: string; generation: number; leaseId: string;
  claimOperationId: string; claimRevision: number;
}>;
claimNext(): Promise<{ kind: "idle" | "capacity" } | { kind: "claimed"; claim: ClaimToken }>;
recordPrepareIntent(claim: ClaimToken): Promise<PreparedCommand>;
recordPrepareFact(claim: ClaimToken, fact: VerifiedPrepareFact): Promise<ClaimToken>;
admitAction(claim: ClaimToken, action: ClosedAction): Promise<AdmittedCommand>;
recordActionFact(claim: ClaimToken, fact: VerifiedActionFact): Promise<void>;
renewClaim(claim: ClaimToken): Promise<ClaimToken>;
reconcileClaim(claim: ClaimToken, fact: VerifiedResourceFact): Promise<void>;
```

Names above describe future ports. A token's shape grants no authority: methods re-read locked rows, verify the private worker capability/ExecutionAuthority, and compare full identity/revision. `ClosedAction` is a discriminated union: activate has immutable activationId and descriptor; input has inputId, next sequence, byte count and EOF. Tool invocation descriptors and effects require a later reviewed extension, not a generic action payload. No arbitrary URL/path/env/SQL/argv. `Verified*Fact` is accepted only from the trusted launcher adapter validating journal policy/digests/receipt/attempt/lease/fence and exact operation identity. It is not parsed directly from caller booleans such as noEffects or stopped.

Claim operation ID is generated before its DB transaction and retained for acknowledgement-loss repair. Unknown claim commit means **no prepare call**: re-read by that same operation ID, current membership and claim identity. If committed, recovery owns a reservation, not automatic permission to launch; revalidate into a fresh prepare admission or cancel it. Only a known committed prepare intent on the current live invocation may submit prepare once. Restart never treats an existing prepare_pending as an instruction to resend. Same rule applies to activation and input effects. Duplicate/replayed admission returns only durable status, never a second executable command; the once-delivery command is a private in-memory value produced only by the invocation that confirms the new commit.

Pure grant construction binds exact fixed-position tuples containing version/domain, actor/run/attempt/generation/lease/action identity, launcher installation/policy/receipt, kind/sequence, pinned connection/version or null, absolute expiry, and the closed action descriptor. Run snapshot uses009's exact canonical text comparison. LaunchSpec uses008 digest and trusted image/recipe identity. Digests are internal integrity/equality aids, not bearer tokens or substitutes for owner queries; changed same-ID payload conflicts. All identity-bearing fields participate. Input grant includes a private digest of exact bytes plus count/EOF so the same input ID cannot be reused with changed content; digest is never logged or public. Full tuple/encoding needs byte-exact oracle tests before schema approval.

Select this exact action encoding for review: UTF-8 `JSON.stringify(["zetta.dispatch.action",1,ownerUserId,runId,attemptId,generation,leaseId,actionId,launcherInstallationId,policyVersion,receiptId,kind,sequence,connectionIdOrNull,credentialVersionOrNull,expiresAtMs,descriptor])`. Activation descriptor is `["activate",activationId,launchIdentityDigest]`, with sequence1 and actionId=activationId. Input descriptor is `["input",inputId,inputSequence,byteLength,eof,sha256OfExactInputBytes]`, actionId=inputId and sequence=inputSequence; the unique constraint includes kind. Arrays have fixed length, every ID is bounded/canonical, digests are64lowercase hex, optional connection/version are both null for fixtures. Input sequence/count/EOF obey008 limits; expiry is no later than30seconds from admission or absolute attempt deadline. Canonical text is bounded to16KiB and exact-reencoded on read. Hash with SHA256 only after canonical validation; stored canonical equality remains authoritative. No arbitrary descriptor object is accepted.

The fixture currently allows009 maxOutputBytes up to1MiB while008 caps64KiB; dispatch must reject an unsupported policy intersection (or use an explicitly chosen producer budget within both), never silently truncate a promised budget. Likewise derive absolute deadline once from DB time+authorized remaining budget; expiry never slides across restart. Input text+framing must fit008's64KiB aggregate; unsupported encoding overhead denies before prepare. Stored input is private DB text, absent from launcher journal/grant logs.

## Credential issue and once-only delivery

The007 metadata store remains unchanged until a separately reviewed private integration adds bounded issue-and-deliver. Do not expose crypto.open or an HTTP/model plaintext resolver. Wire the secret-owning closure to exactly one trusted transport at construction; caller input cannot provide a callback/endpoint. It accepts an ExecutionAuthority for the current transaction, not an arbitrary owner ID.

For a future single-key action: lock in the global order; validate current active membership, connection owner/state/current pinned version/expiry, key-check health, run/current attempt/claim/receipt/action binding and grant deadline. Decrypt only within this bounded scope; keep an owned buffer transiently. Commit grant issued **before** any byte leaves the process. After confirmed commit, the same live invocation calls its bound transport once, then wipes its buffer in finally. Transport must retain/copy bytes only for the bounded authenticated delivery and must acknowledge disposal; no argv, durable journal or general environment map. In-memory retention cannot be claimed stronger than the actual transport implementation proves.

Unknown commit: wipe, return outcome_unknown, do not deliver; re-read may show issued but never remint or resend from that receipt. Known commit plus crash-before-send loses availability safely: reconciliation records no trusted delivery outcome and still never decrypts that grant again. Unknown send/ack: mark uncertain where possible, cancel admission and reconcile exact launcher state. Failure to persist uncertainty is not permission to retry; durable issued already blocks it. Credentials expire at min(issue time+30s,attempt deadline); expired pending grants cannot be promoted. No duplicate action grant under a new ID to bypass uncertainty.

Revoke/replace/removal before issuance wins the corresponding locked checks. After committed issuance, persist cancellation and close mediated input/tools; copied credentials/effects cannot be recalled. The short race between committed issuance and delivery remains explicit: the sender rechecks available local cancellation but cannot promise atomicity with later revoke without holding a DB lock across IO (forbidden). The grant's durable issuance is the authority linearization point. Provider-side revocation is separate.

No fixture launch carries credentials. Current008 LaunchSpec/activation protocol has no approved credential payload. Native API-key delivery, including the transport disposal contract and pinned binding producer, remains blocked until its008/007 extension and actual proof are accepted.

## Recovery, cancellation and operational gaps

On startup, scan existing unreleased claims for reconciliation before claiming more work; still count all of them. Acquire only one repair at a time with DB CAS, never execute pending actions merely because another worker died. Immutable attempt lease identity does not become a new worker ownership lease; repair operations are idempotent queries/stop intents and all transitions use claim revision CAS. Concurrent repair workers cannot authorize new input or repeat external effects.

Align the pending [008d persistence design](launch-journal-persistence.md) with the coordinator-selected per-receipt runner lock plus short installation allocation/scan lock. Each live runner owns only its receipt's lifetime writer lock; a busy or stalled receipt must not monopolize installation-wide journal writes or block another attempt's stop/deadline. The installation lock covers bounded allocation/deduplication or inventory snapshot only, is released before waiting for any runner/receipt lock, and never spans Docker/systemd/network operations. Recovery snapshots candidate receipt identities under the short lock, releases it, then reconciles each exact receipt through its owning runner or verified unowned receipt lock. It cannot adopt a busy receipt or infer absence from inability to lock it. Existing launcher control/runner ownership carries commands; this adds no broker, queue or second dispatch authority. PostgreSQL transactions finish before any launcher/journal lock acquisition, and no launcher-held file lock spans a callback acquiring DB locks. This is an interface alignment requirement for008d's correction, not a claim that its filesystem backend is implemented or already accepted.

| Persisted fact | Permitted next step |
| --- | --- |
| Reservation, prepareIntentAt null, no action admitted | Fresh authorization may begin prepare once; cancellation can prove not submitted from DB protocol and release after logical terminal. |
| prepare intent committed, missing receipt or unknown response | Keep capacity; no prepare resend. Reconcile exact attempt/lease/policy against trusted launcher inventory. Absence in one query is insufficient. |
| Prepared receipt, activation not admitted | Fresh action admission only if live, authorized and unexpired; after restart prefer cancel/reconcile, never infer permission from prepared alone. |
| Issued activation/input/tool with response loss | No resend, no new grant/attempt; cancel and persist interrupted/uncertain, or cancelled/uncertain if owner intent committed first. |
| Logical terminal, resource stop/removal pending | Keep capacity and exclusive resource quarantine. Terminal result remains source-bound; no success from exit0. |
| Exact stopped/removed facts, outstanding operation settled | Record stopConfirmed separately; release capacity only when logical terminal and cleanup confirmed. Effect uncertainty is retained until separately reconciled. |
| Lease expired, host unavailable or identity mismatch | Fence admission, retain claim/quarantine, request exact-resource cancellation when possible. No replacement attempt against unresolved resources. |

An operational gap is explicit:008's proposed GET status requires a receipt, but a lost prepare response may leave DB with only attempt/lease identity. Before deployment the trusted launcher adapter needs an authenticated **read-only exact-attempt journal lookup/reconciliation port**, or equivalent trusted inventory handshake, returning validated ownership/operation settlement facts. No HTTP endpoint is invented or claimed to exist here. Until that contract and negative proofs exist, missing-receipt cases stay unknown/occupied and cannot progress automatically.

Owner cancel commits first and prevents later admission/completion success; completion already committed stays terminal. Use009 normalized terminal identity, preserving original finish/revision on matching replay. Backend revocation/deadline/shutdown/recovery reasons require a separately reviewed closed extension to current009 owner_requested-only cancellation contract; do not fake owner intent. Shutdown stops new claim admission locally, persists cancellation for owned live claims, drains bounded stop/cleanup and leaves unresolved claims durable. The independent launcher deadline remains required for worker/host failure; an application timer is not that proof.

Explicit retry remains absent: after proven stopped/settled resources and reconciled effects, a future owner-intent API may append a new attempt/generation preserving old tombstones. No automatic external replay. Backup restore leaves dispatch disabled until revocations, launcher inventory and outstanding actions are reconciled; old DB snapshots are not valid evidence of never-issued work.

## Errors, proof and bounded children

Owner-facing errors retain fixed codes (`not_found`, `unsupported`, `capacity`, `stale_attempt`, `stale_revision`, `transition_conflict`, `outcome_unknown`, `unavailable`) without SQL/cause/input/key/URL/journal content. Foreign IDs match missing IDs. Private operator evidence may include safe generated operation IDs, fixed phase/error code and counts only. RunDto never includes grants/leases/connection bindings/private snapshot;011 owns later event transport.

Proposed children, each independently assigned after review; at most five source files plus focused tests/generated migrations:

1. **010b pure authority/action/capacity contracts:** execution-authority issuance/verifier, dispatch-contract, dispatch-state, focused tests; no claims, IO or crypto wiring. Prove structural forgery/reused token/dead transaction rejection, canonical all-field substitution, state transitions and capacity counting with unknown/terminal cases. Identity issuance contract must be reviewed before accepting this slice.
2. **010c schema and claim storage:** one schema file, barrel, claims service, candidate helper and feature migration config (<=5); single-writer generated migration/custom constraints and dedicated approved PG tests. No external launcher. Prove two workers/one attempt, global/per-actor limits with two owners, expiry/terminal-unknown capacity, claim unknown-commit repair and no reverse locks.
3. **010d private action/grant integration:** grant service, bounded trusted transport adapter, cancellation coordinator and focused tests (<=5). Coordinate separate changes to existing007 revoke/replace and identity removal, serialized rather than expanding one worker. Implement only secret-free fixture actions here; the private connection-issuance extension described above gets a separate <=5-file assignment after protocol approval. Prove pending/issued/unknown transitions and issuance ordering with synthetic disposable credentials only.
4. **010e worker/reconciliation integration:** worker, launcher adapter, reconciliation, composition entry and focused worker tests (<=5), only after008 operational transport/journal and009 store acceptance. Multiworker DB plus actual isolated fixture proof; no native-readiness claim.

Fault matrix must inject response loss before/after every DB commit and prepare/activate/input call; worker crash before/after intent/issued state; revoked/removed/expired membership or key before and after issuance; both cancellation/completion orders; renewal/removal race; two actors bursting at limits; old lease/generation/receipt replacement; missing-receipt lookup; stuck create/daemon; deadline/shutdown; DB rollback restore and partial cleanup. Observe lock blocking with independent connections (not sleeps), compare exact SQLSTATE/constraint outcomes and final occupancy/tombstones, ensure buffers wiped on every credential failure path, and show no second call at the transport boundary. Actual launcher tests must prove process-tree stop, quarantine and host-restart behavior; unit drafts cannot substitute.

No new product-policy decision is required for the initial fixture limits or conservative failure behavior. Remaining genuine access/integration gates are private execution-authority issuance (including later membership epoch/scheduled provenance), identity removal transaction wiring, one-key credential transport, and missing-receipt reconciliation. Operational blockers are provisioned008 launcher/deadline/egress, accepted009 store and later native/GUI producers. Review this proposal before assigning source; parent010 remains incomplete.
