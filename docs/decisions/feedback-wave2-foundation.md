# Wave 2 foundation: schema and contracts

Built once, before three teams start in parallel, for `plans/feedback.md` Phases 2 (self-hosted models), 4 (voice mode, speech out) and 5 (mobile push). It holds the one migration (`feedback_wave2`), the shared constants, and read-only accessors. It has no route, no screen, no service worker and no engine code: those belong to the teams. If a team needs a column that is not here, it asks for it here instead of adding a second migration.

## Speech out (T9)

Columns on `installation_settings`:

- `speech_provider` text, `off | browser | openai | compatible | elevenlabs` (`SPEECH_PROVIDERS`), default `browser`.
- `speech_base_url` (used by `compatible` only; dropped for the others by `installation.update`), `speech_model`, `speech_voice`, `speech_language`: text, default empty, which means the provider's default. Limits 512 / 100 / 100 / 35 (`SPEECH_LIMITS`, also a CHECK). Model and voice match `SPEECH_NAME_PATTERN`.
- `speech_connection_id` uuid, no foreign key (like `transcribe_connection_id`): which connection holds the key. Never returned by any API.

The key is a sealed connection of provider `speech` (`SPEECH_KEY_CONNECTION_PROVIDER`), saved with the transport purpose `installation.speech-key` (`SPEECH_KEY_PURPOSE`), owned by the administrator who saves it. The operator's fallback is `ZETTA_SPEECH_API_KEY` (`SPEECH_KEY_ENV`, in `.env.schema`), used only when no connection is recorded. Read it with `speechReader.settings()`, `.keyState()` (`none | set | operator | unavailable`) and `.secret()` (a buffer the caller zeroes).

**Default `browser`, not `off`.** `browser` needs no key, address or server work, and nothing speaks until a person presses "Listen" or starts voice mode, so no text leaves the page by itself. With `off` the first visible result of Phase 4 (the Listen button) would stay hidden until an administrator found a setting. One caveat to tell the administrator in the settings copy: the browser's own voices may be network voices of the browser vendor. `off` hides the Listen button and voice mode's spoken answers.

`speech_voice` applies to `openai`, `compatible` and `elevenlabs`. A `browser` voice differs per device, so T9 keeps that choice on the device, not here.

Deliberately left to T9: the `PATCH /api/installation` fields and their address check (the existing `checkBaseUrl` rule for the speech-to-text address is the pattern), the sealed-key route (`PUT/DELETE /api/connections/speech-key`, like `transcribe-key`), the test button, the provider default models, the audio format, and its Chief/MCP tools (`bot-parity.md`). `installation.update` already validates and stores the five text fields and refuses `compatible` without an address.

## Mobile push (T10)

- `user_preference.push_mode`: `all | mentions_and_approvals | off` (`PUSH_MODES`), default `mentions_and_approvals`. It is in the `Preferences` type, `GET`/`PATCH /api/preferences` and the web `Preferences` type already. `pushModesFor(db, userIds)` reads many people at once (default for a person with no row). `pushAllows(mode, eventClass)` is the rule: `all` lets everything pass, `mentions_and_approvals` lets `mention` and `approval` pass, `off` nothing. The sender maps each trigger point to an event class: `mention` = somebody wrote the person's name; `approval` = something waits for their yes or no (a proposal, a permission request, a bot's question); `other` = every other card or message.
- Table `push_subscription`: `id` uuid v7, `user_id` (foreign key to `user`, cascade), `endpoint` (unique), `p256dh`, `auth`, `user_agent` (default empty, 200 at most), `created_at`, `last_used_at`, `failed_at` (null; set when the push service answers 404 or 410, then the sender skips and prunes it). Index on `user_id`. Limits in `PUSH_LIMITS` (also a CHECK).
- **Secrets.** `endpoint`, `p256dh` and `auth` are the secrets of the subscription: whoever has them can push to that device. They stay in the row. No API returns them: a list shows only `id`, `user_agent`, `created_at`, `last_used_at`. Nothing logs them.
- **Subscribing.** `checkPushSubscription` (pure) checks https, no user name, a real host name (no IP address, no local name), base64url keys and the limits. The server must also resolve the host and refuse a private address before the first send, and it does so even when `ZETTA_ALLOW_PRIVATE_NETWORK=1`: a push service is always public (otherwise any member could aim the server at its own network). Upsert on `endpoint`: a device that is re-subscribed by another person moves to that person and clears `failed_at`, so a shared phone does not keep pushing the previous person's cards. At most `PUSH_LIMITS.perUser` per person; the oldest goes first.
- **VAPID keys.** `installation_settings.push_public_key` (text, null until generated; public by design, so `GET /api/installation` returns it) and `push_connection_id` (never returned). The private key is a sealed connection of provider `push` (`PUSH_KEY_CONNECTION_PROVIDER`), purpose `installation.push-key` (`PUSH_KEY_PURPOSE`), owned by an administrator; the server generates the pair at first use, not the browser, so nothing travels sealed for it. Store the private scalar (`d`, 43 base64url characters) as the secret; the public key is the uncompressed P-256 point in base64url, 87 characters (`isVapidPublicKey`).
- **Both roles.** `pushReader.publicKey()` and `.privateKey()` read from the database in every `ZETTA_ROLE`. An `api` and a `worker` share `ZETTA_CONNECTION_KEY`, so both open the key. The sender (a worker) has no signed-in administrator, so the reader goes through the connection's owner as a background actor, like the speech-to-text key.
- **Generate once.** Two processes can both find no key. Create the sealed connection, then call `claimPushKeys(db, { publicKey, connectionId })`: one statement, `... where push_public_key is null`, so exactly one wins, and it writes only the two push columns. On `claimed: false` revoke the connection just made and use `current`. Do not use `installation.update` for this: it rewrites the whole row.
- **Never regenerate silently.** A new pair breaks every existing subscription (the browsers subscribed to the old public key). If the owning administrator leaves, `keyState()` reads `unavailable` and pushes stop; show the administrators that, and let one of them create a new pair on purpose, telling people to subscribe again.

Deliberately left to T10: the routes, the service worker, the sender and its library, the VAPID subject (use the public URL when there is one; no e-mail in the repository), where each trigger point maps to an event class, retry and prune rules, the Chief/MCP tools.

## A model on the person's own server (T8)

A per-user connection of provider `compatible` (`COMPATIBLE_PROVIDER`). It is a real `connection` row, so a bot can bind it through `bot.requiredConnections` and `bot_connection` with no new column.

- **Address and model name are not secret**, so they are `connection.config` (new, `jsonb`, default `{}`, a CHECK that it is an object of at most 2 KB). The shape is `CompatibleConfig = { baseUrl, model }`. `config` is written and read by `connections/compatible.ts` (`writeCompatibleConfig`, `readCompatibleConfig`), not by the credential store: the store's strict metadata and its request receipts do not carry it, which keeps that security-reviewed code unchanged. The cost: creating the connection and writing its config are two steps. A `compatible` connection without a valid config reads as `config_invalid`; T8 should revoke the connection if the second step fails. `connections.list` does not return `config`: T8 serves it through its own read.
- **The key is optional, the secret is not.** A connection always holds a sealed secret (the store refuses an empty one). With no key (Ollama's default), the server saves the placeholder `COMPATIBLE_NO_KEY`; `compatibleKey(secret)` gives `null` for it, and the engine setup then sends no credential. A key is sealed in the browser with purpose `COMPATIBLE_KEY_PURPOSE` (`connection.create:compatible`) and a body of only `{ secret }`; the address and model travel beside it in plain text.
- **Provider lists.** `compatible`, `speech` and `push` are in the server `PROVIDERS` (the store only accepts listed providers). `speech` and `push` are managed: never listed and never creatable through `POST /api/connections`. `compatible` is listed (so a person can revoke it in Accounts) but not creatable there, because it needs an address and a model; its own route creates it. The web `Provider` type and `PROVIDER_NAME` know `compatible` ("A model on my own server"); it is not in the create dropdown (`PROVIDERS` of `chat-client.ts`) for the same reason. `PROVIDER_ENV` has no entry: `envFor` treats it as a missing key until T8 handles it.
- **The address rule** is `checkModelAddress(raw, { allowLocal })` in `packages/core/src/model-server.ts`, pure and tested. It always refuses: a scheme other than `http` and `https`, a user name or password, a query or fragment, more than 512 characters, and any cloud metadata or reserved address (169.254.0.0/16 including 169.254.169.254, `fd00:ec2::254`, 100.100.100.200, `metadata.google.internal`, `metadata`, link-local, unspecified, multicast, reserved ranges), including their IPv4-mapped, NAT64 and 6to4 forms and the decimal, hex and octal spellings (the URL parser normalizes them first). Loopback (`localhost`, 127.0.0.0/8, `::1`) and the local network (10/8, 172.16/12, 192.168/16, 100.64/10 so a Tailscale address works, unique-local IPv6, one-word names such as `ollama`, `.local`, `.lan`, `.internal`) are allowed only with `allowLocal`. `http` is allowed only to a local address; a public host needs `https`, because the key and the chat travel to it.
- **Who may use a local address.** `allowLocalModelServer({ isAdmin, operatorAllowsPrivate })`: the owner of the server (an administrator), or anyone when the operator set `ZETTA_ALLOW_PRIVATE_NETWORK=1`. A member of someone else's server must not be able to point it at the server's own network. This differs from the speech-to-text rule, which lets only the operator switch decide, because a self-hosted model is normally on localhost or the LAN. Please confirm it.
- **A host name is not an address.** For a host name (`hostKind: "name"`), resolve it and pass every resolved address to `resolvedAddressIssue(ips, { allowLocal })`, before the first call and again on every call. `readCompatibleConfig` re-applies the rule on every read, because who may use a local address can change after the save, and it reads only the person's own active connections.

Deliberately left to T8: the routes and their Chief/MCP tools, the engine's provider config in the per-user engine home, the real-turn "Test connection", the owner-visible error detail, and the Docker case: in a harness container `127.0.0.1` is the container, not the host, so an address on the host needs the container's name for it (the rule does not rewrite addresses).

## What the API must never return

`transcribe_connection_id`, `speech_connection_id`, `push_connection_id` (stripped by `withLayaModel` through `SEALED_KEY_FIELDS`, with a test), any key or secret, a push subscription's `endpoint`, `p256dh` or `auth`, and `connection.config` of someone else's connection. The public VAPID key is the one exception, by design.

## Checks

The migration is additive and loses nothing: every new column has a default or is null, and `feedback-wave2.migration.test.ts` runs it on a database shaped like the one before it (old rows keep their values and get the defaults, the checks hold, the subscription table cascades with its user). It was not applied to the developer's database.
