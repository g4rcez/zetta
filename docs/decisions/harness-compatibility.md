# Six-harness protocol evidence

Status: candidate transports accepted by the coordinator for implementation planning, 2026-10-22. This is the bounded [012a](../../tasks/012a-record-harness-protocols.md) handoff. **No harness is accepted as operationally compatible.** RFC-002 and RFC-006 remain prerequisites; this document neither completes RFC-012 nor authorizes adapters, installation, login, provider calls or secret migration.

## Motivation

Zetta must carry one initiating actor through chat, delegation, memory and configuration tools across six different native harnesses. Printing a response proves neither a host-tool round trip nor private session ownership. The required research outcome is an actionable transport choice with explicit evidence gaps.

## Constraints and options

All launches belong inside the [execution boundary](execution-isolation.md), with a private native home and an exclusive actor+harness session lease. Native CLI permissions do not replace that boundary. Never inherit the application server's environment, host credential stores, native daemons or discovered configuration.

| Option | Cost / trade-off | Decision |
| --- | --- | --- |
| Parse terminal text from all six | Loses IDs, tool results and terminal errors | Reject |
| Replace each harness with its model SDK | Changes the required product behavior | Reject |
| Use each pinned harness's structured control interface | Six parsers; preserves native behavior and exposes missing capabilities | Recommend |

The coordinator accepted this adapter direction for planning; implementation remains pending RFC-006's accepted normalized contract. Where a native host callback exists, use it. Where only MCP is evidenced, use a narrowly scoped local MCP bridge owned by the attempt. This bridge implements Zetta delegation/memory/configuration callbacks; it is distinct from external app sessions in RFC-043.

## Pi 1.4.0

**Command/control:** `pi --mode rpc --session-dir <actor-session-dir> --no-extensions --no-skills --no-prompt-templates --no-context-files --no-mcp --no-approve -e <trusted-zetta-extension>`. These flags are present in installed help. Explicit `-e` still loads with discovery disabled. Supply approved model/provider and instructions explicitly; selectively materialize approved skills instead of discovering the host. `--no-session` selects ephemeral operation; persistent operation uses an owned exact `--session <path|id>` or `--session-id <id>`. Never select `--continue`/a picker across unfiltered native history.

**Wire/events:** LF-delimited JSON objects on stdin/stdout; stderr is diagnostic only. Send `{"id":"prompt-1","type":"prompt","message":"..."}`. Correlate `response` by `id`; `success:true` means admission, with `disposition:started|queued|handled`. `handled` need not start a run. Text arrives as `message_update.assistantMessageEvent` (`text_delta`, `contentIndex`, `delta`); `message_end.message` is authoritative. Tools emit `tool_execution_start/update/end` with `toolCallId`; end includes `result` and `isError`. Command failure is `response.success:false`; provider failures/aborts appear in completed assistant messages. **Wait for `agent_settled`, not `agent_end`**, and inspect abort/provider outcome. Split only LF, accepting CRLF; Unicode U+2028/U+2029 inside JSON strings must survive.

**Host bridge:** installed `extensions.md` defines `pi.registerTool()`, schema validation, `execute` result content and abort signals. A trusted explicit extension can forward a registered Zetta operation over the attempt-owned channel and return the bounded result to the agent. RPC tool execution events are observations, not an API for replacing arbitrary tool results. Extension code has the same privileges as Pi; it receives only attempt authority, never app secrets. Native MCP is also present in this Pi version; the initial candidate uses an extension to keep the local callback surface explicit.

**State/auth/models:** `PI_CODING_AGENT_DIR` relocates the default `~/.pi/agent`; this contains `auth.json`, `settings.json`, `models.json`, `mcp.json` and resource directories. `--session-dir` overrides session lookup/storage. Actor home and all referenced resource paths must be private too. API-key environment and native OAuth are supported, but no existing credentials were read/copied and no login relocation was tested. Model discovery exists as `--list-models [search]` or RPC `get_available_models`; execute it only in the intended actor context with separately approved provider discovery. A returned catalog does not prove entitlement.

**Cancellation/deadline:** clear pending queues with `clear_queue`, then `abort`; installed docs warn `abort` alone allows queued messages to continue. Also stop outstanding bash/retry work through `abort_bash`/`abort_retry` when applicable. Close stdin for orderly runtime disposal. The supervisor still owns a finite deadline and entire process-tree escalation; successful RPC abort is not containment proof.

## Codex 0.163.0

Initialize the stdio connection with `initialize` and client metadata, await its response, then send `initialized`; start/resume with `thread/start` / `thread/resume`, followed by `turn/start`. The installed generator defines `InitializeCapabilities.experimentalApi`, `requestAttestation` and optional notification filtering; dynamic tools require the experimental capability. Pin generated types for this binary rather than assuming future documentation is identical. [Official lifecycle and experimental tool contract](https://developers.openai.com/codex/app-server).

**Wire/events/bridge:** the installed generated `ThreadStartParams.ts` has `dynamicTools`; a function spec is `{type:"function",name,description,inputSchema}`. `ServerRequest.ts` routes `item/tool/call` with `{threadId,turnId,callId,namespace,tool,arguments}`. Reply to the request ID with `{contentItems,success}`. This is the preferred host bridge for Zetta tools; actor/run authority comes from the connection binding, not model-supplied arguments. Text: `item/agentMessage/delta`. Lifecycle: `item/started`, `item/completed`, `turn/completed`; turn statuses are `completed|interrupted|failed|inProgress`. Observe `error` and the completed turn's outcome; do not promote an intermediate completed item to run success.

**State/auth/instructions/models:** actor-owned `CODEX_HOME` holds native configuration/history; use exact stored `threadId` with an actor lease, never a global latest session. `ThreadStartParams` supports `baseInstructions`, `developerInstructions`, `cwd`, configuration and `ephemeral`. Installed methods include `skills/list` and `hooks/list`; those are discovery surfaces, not authority to load host resources. `model/list` is the evidenced catalog request, unexecuted. Authentication supports account login/API keys; cached login can use `CODEX_HOME/auth.json` or an OS credential store. Select an approved actor-owned storage channel and prove no host keyring fallback. `cli_auth_credentials_store` offers file/keyring/auto/ephemeral, but no storage migration is approved here. [Official authentication documentation](https://developers.openai.com/codex/auth).

**Cancellation/deadline:** send `turn/interrupt` with the exact `{threadId,turnId}`, then observe the terminal turn. The supervisor owns deadline/process-tree termination and pending dynamic-tool cancellation. Never use the host app-server daemon or its proxy for another actor. Provider login, catalog, resume, tools and cancellation remain source-supported, untested.

## OMP 18.6.1

**Command/control:** native help confirms `omp --mode rpc --no-ui --no-extensions --no-skills --no-rules --no-title --no-lsp --no-pty --profile <actor-profile> --session-dir <actor-session-dir> --max-time <duration>`. Use `--cwd <owned-workspace>` and explicit instructions. `--no-tools` disables built-ins; host tools still require their own exact allowlist verification. `--resume <id-prefix|path>` exists; resolve only an actor-bound full path, never a picker or `--continue` over shared storage. Hooks/extensions use explicit `--hook`/`-e` when needed.

**Native bridge/wire:** v18.6.1 defines `set_host_tools` with `name`, `description`, JSON-schema `parameters`; requests are `host_tool_call {id,toolCallId,toolName,arguments}`. Answer `host_tool_result {id,result,isError?}`; partial updates use `host_tool_update`. `host_tool_cancel {id,targetId}` cancels a pending callback. Commands include `prompt`, `abort`, `abort_retry`, `abort_bash`, `get_available_models`. Responses carry `command`, `success`, optional `data/error`; message events carry `messageId`. [Versioned RPC types](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/modes/rpc/rpc-types.ts).

Agent events include `message_update.assistantMessageEvent` and `message_end`; tool execution emits `tool_execution_start/update/end` with `toolCallId`, arguments, partial/final result and `isError`. [Versioned agent event types](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/agent/src/types.ts).

**Terminal/framing:** accepted prompts have correlated `prompt_result`, with `status:completed|aborted|error` and `sessionSettled`; an acceptance response alone is insufficient. When `sessionSettled:false`, wait for `session_settled` before releasing attempt ownership: background work can still wake the session. [Prompt result implementation](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/modes/rpc/rpc-prompt-results.ts). Negotiate protocol 2 before work and implement bounded `rpc_chunk` reassembly; v1 may shrink oversized frames. The upstream limits are 1 MiB physical frames and 64 MiB reassembled payloads; Zetta may impose stricter negotiated run budgets, but must reject overflow explicitly. [Frame implementation](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/modes/rpc/rpc-frame.ts).

**Private state/auth/models:** a profile scopes auth/sessions/settings/caches, but is insufficient as an OS boundary. Source paths include profile agent directory, `agent.db` for settings/auth, `history.db`, `models.db`, sessions and base-root session-owner leases. Isolate the **entire** HOME/root plus `PI_CODING_AGENT_DIR`; Linux XDG routing also exists. [Versioned directory helpers](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/utils/src/dirs.ts). OMP can discover `.claude`, `.codex` and `.gemini` resources; only approved materialized paths may exist in the sandbox. [Config discovery](https://github.com/can1357/oh-my-pi/blob/v18.6.1/packages/coding-agent/src/config.ts). Native `login`, provider API-key inputs and auth-broker/gateway commands exist in help; no host broker may be reused. API-key/OAuth storage relocation, model entitlement and login renewal need an approved isolated proof. Native `models` and RPC catalog discovery were not executed.

**Cancellation/deadline:** use correlated `abort`, cancel pending host callbacks, and stop retry/bash work when present; enforce native `--max-time` plus the outer supervisor deadline. Queues/background wakeups and subagents need version-matched settlement tests. Do not assume Pi's `agent_settled` or queue commands apply to OMP.

## Actor binding, egress and conformance gates

The adapter maps native callback IDs to one server-derived actor/run/attempt. A callback's tool name, arguments, native session ID or delegated bot cannot choose an actor. Validate schema and bounds, reauthorize each operation, reject foreign resources and reused invocation IDs, and return one bounded result/error under the same invocation. On cancel/revocation, deny new callbacks, close the channel and reconcile uncertain external effects; never blindly replay them after restart. External MCP integrations do not inherit the local bridge's authority.

For **every harness**, prompts, instructions, retrieved memory, files and tool output included in context can leave for the chosen model provider. OAuth/login and catalog discovery can contact account endpoints; MCP may contact additional services; hooks/extensions can perform their own network I/O. Pi/OMP are multi-provider, Codex uses its selected account/provider, Claude supports Anthropic/third-party providers, OpenCode uses configured integrations, and Cursor uses Cursor's service/model routing. The account binding, approved endpoint list, retention policy, telemetry/update/catalog traffic and enforceable egress policy must be recorded per selected setup. No research receipt proves provider restrictions, entitlement or data residency. The RFC-002 no-network proof does not permit real provider egress.

Before any row becomes operationally compatible, its adapter worker must record:

1. Pinned executable/package provenance and version-matched protocol/schema; no automatic upgrade during a lease.
2. A no-account startup in the isolated image with fake host/foreign-actor canaries, closed ambient environment and no host daemon/keyring/resource fallback. Prove positive controls and actor-owned writes.
3. An approved real synthetic conversation: ordered text, tool request/result/error, exactly one normalized terminal outcome; malformed/unknown/oversized/partial frames fail with bounded safe diagnostics. Include Unicode framing and duplicate/dropped events.
4. Zetta delegation, memory read/write and configuration proposal round trips with immutable actor/run/attempt binding, foreign-resource/replay rejection, cancellation during a callback and no leaked credentials. A file-writing demo does not prove these behaviors.
5. Exact actor-owned login/renewal, model selection/discovery and session resume after restart; deny foreign IDs and stale/revoked bindings. Native authentication alone does not establish bot readiness.
6. Deadline, graceful cancel, escalation, orphan cleanup, pending queues/background work, output backpressure and unaffected second actor. Recover from stream disconnect without duplicate external action.
7. Approved provider/tool egress and a successful explicitly acknowledged onboarding conversation for the tested actor/bot/configuration/account setup.

## Amendment 2026-10-23: adapter strategy actually shipped (RFC-012–018)

The protocol candidates above (RPC, app-server, stream-json + MCP) were **not** adopted for v1. All six harnesses use one adapter, `apps/server/src/modules/chat/harness.ts`: a one-shot, non-interactive CLI call per turn (`claude -p`, `codex exec`, `pi -p`, `omp -p`, `opencode run`, `cursor-agent -p`), prompt as a single argv element (no shell), empty temporary cwd, allow-listed environment, process-group kill on timeout/cancel/overflow, output cap, per-user + global concurrency limits, typed errors (`not_installed`, `auth_required`, `timeout`, `busy`, `cancelled`, `failed`) and optional per-user `HOME`/`XDG_*` (`ZETTA_HARNESS_HOME_ROOT`). Host tools are a text protocol (`zetta:*` fenced blocks, `chat/tools.ts`) rather than a native tool bridge, so there are no invocation IDs to forge; every tool effect is validated and executed by Zetta as the requesting user.

Live verification status: **Claude Code (haiku) verified end to end** (adapter smoke, UI chat, tool-protocol test). Codex, Pi, OMP, OpenCode: installed on the dev machine but **not exercised** (no quota/account approval). Cursor: `cursor-agent` is not installed, so it is reported `not_installed`. `GET /api/harnesses` shows the real per-user status; a harness only becomes "ready" after a successful run by that user.
