# Identity and resource lock-order normalization proposal

Status: per-account design accepted after [independent005f1 review](../reviews/identity-lock-order-005f1-review.md),2026-10-22. Later [005f2 reproduced the current defect](../reviews/identity-lock-order-005f2-review.md);005f3 implemented the correction and [005f4 actual positive/session controls passed](../reviews/identity-lock-order-005f4-review.md). No schema change was part of this correction. Future020 services still own their actual implementation/proof. The design body below records the source-derived proposal; linked later receipts establish completed behavior.

## Observed source and risks

`identity/enrollment.ts` lockIdentity currently acquires installation singleton, active admin membership, then actor auth user. acceptInvitation then acquires subject membership, even when it will reject an already active subject. `identity/admin-lifecycle.ts` replacement instead acquires installation, sorted auth users, then sorted memberships. Future020 operations need actor and bot-owner memberships in a single consistent order. With B sorting before admin A,020 can hold B while seeking A and enrollment can hold A while seeking B. This is a source-derived potential cycle; no actual020 service exists yet.

There is also a current implicit-lock risk:007 connection creation holds its owner's membership and then inserts a connection referencing auth user. Its FK takes a key-share lock on that auth row.005 replacement holds auth rows FOR UPDATE before seeking membership. The two paths can therefore form an opposing wait. This is an inferred current-code risk requiring actual reproduction, not a claimed deadlock receipt.

## Proposed minimal correction

Administrative identity operations retain installation singleton first. Acquire all needed auth user rows, sorted by canonical user ID, **FOR UPDATE**; then acquire all needed membership rows in the same sorted order, **FOR UPDATE**; only afterward invitation/session/audit mutations. Enrollment's account set includes the installation admin and authenticated actor, deduplicated; invitation issuance also prelocks intendedUserId when present because its invitation/audit FKs reference that account. Only actually required memberships are locked. Validate current installation/admin/member/account facts under those locks before consuming or issuing anything. Missing rows still deny safely; absent membership insertion remains serialized by the already locked auth identity and installation scope. No authority derives from caller IDs or a lock token.

For007 resource operations, explicitly acquire the actor auth user **FOR KEY SHARE before membership**, then retain the current membership FOR UPDATE and later resource/key-check order. Future020 similarly takes the complete sorted actor/owner auth account set FOR KEY SHARE before any membership. It never upgrades account locks after membership. The [PostgreSQL18 row-lock matrix](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS) and installed Drizzle lock strengths support these modes. Prelocking eliminates the later implicit auth-FK wait opposing admin replacement; independent resource calls retain compatible shared account access. Existing009 owner FKs target membership/run rather than auth user, so those paths may remain a forward subsequence without an extra account lock.

The initially proposed NO KEY UPDATE-only change is rejected: its compatibility with session FK KEY SHARE could let an uncommitted session insertion escape replacement's DELETE snapshot before replacement commits. Retaining current admin-lifecycle FOR UPDATE preserves its existing drain of in-flight session FK holders and session invalidation semantics. No global session-table fence, auth hook, session generation or weaker account lock is selected. This per-account correction adds one007 query instead of briefly blocking every user's session writes.

Ordinary runtime/resource operations do not acquire installation/auth-account locks after membership, except already-prelocked implicit FK references. Any explicit auth-account update/delete remains before membership in a reviewed identity transaction. The combined forward order is applicable capacity/administrative installation prelude, sorted auth accounts with the appropriate shared/exclusive strength, sorted memberships, then connection/bot/binding/setup/run rows.020 never requests another account/member afterward. Identity removal/release must not acquire capacity afterward.005's future removal/cancellation integration retains its own closed provenance and atomicity requirements.

## Required bounded proof before source acceptance

First create a guarded dedicated PostgreSQL reproduction without changing production behavior. Use independent reserved clients and observed pg_blocking_pids, no sleeps as lock evidence. Exercise actual007 creation versus actual005 replacement with controlled transaction pauses; prove the inferred opposing waits or explicitly record an inconclusive oracle. Retain safe phase/code evidence and roll back/reap/close clients with exact owned service teardown. For future020 membership order, a clearly labeled direct-SQL opposing-order control may demonstrate the cycle; it is not proof of a nonexistent020 service.

Then implement the smallest reviewed changes in enrollment.ts and connections/store.ts with their focused tests; admin-lifecycle retains its existing account lock strength and session behavior. Keep API/results, invitation privacy, session invalidation, credential transactions and actor issuance unchanged. Re-run real bootstrap/replacement/invite/accept/removal-where-supported cases, account-change versus enrollment, both identity/resource orderings, session-drain control and a sorted multi-member positive control. Require observed blocking, coherent committed state, no deadlock and no additional effect. Audit Better Auth/account/session implicit FKs and the existing installation active-membership FK before claiming the whole order is safe.

Membership activation epochs are a separate required schema/identity gate. This lock correction neither invents an epoch nor makes old queued work or readiness eligible after re-enrollment. No migration, public bot service, dispatcher or native integration is authorized by writing this proposal.
