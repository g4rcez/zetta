# Protected launcher journal persistence

Status: proposed for independent review and coordinator acceptance, 2026-10-22. Design only; no filesystem backend, lock helper, service or Linux capability has been implemented or demonstrated by this task.

Parent: [runtime supervisor](runtime-supervisor.md). Foundation: accepted [008c resource records/transitions](../../tasks/008c-define-resource-journal-transitions.md). Implementation gate: [008d](../../tasks/008d-persist-resource-journal.md).

## Decision

Use Bun's node:fs promises API for a private, bounded, canonical JSON record per receipt, and an installed, pinned Linux util-linux flock executable for locks on permanent inodes. A short installation lock serializes allocation and inventory. Each fixed attempt runner holds its own receipt lock for its lifetime and serializes that record's transitions/commits. Bun opens each lock itself and passes the descriptor as the helper's stdin; the helper acquires it and exits while Bun retains its descriptor. There is no extra broker process, PID-file takeover, second index, queue, database or mandatory external receipt anchor.

The selected production target remains linux-systemd-v1. This proposal selects a persistent local ext4 journal filesystem on that Linux host; network filesystems, shared folders, overlay roots and tmpfs are outside this profile. Provisioning must identify the actual filesystem and storage durability assumptions. Existing macOS Bun and Docker Desktop/Colima connectivity do not supply this Linux filesystem/control plane. An unsupported platform, missing primitive or unproved descriptor behavior returns capability_unavailable before admission. Source compatibility or a successful macOS filesystem test cannot turn this gate green.

All protocol choices below are proposed engineering decisions. The linked kernel/API behavior is source-backed; successful operation on a pinned deployment remains a required empirical proof.

## Protected layout and authority

The operator provisions a fixed absolute installation root, for example /var/lib/zetta/launcher-journal. This path is trusted installation configuration, never LaunchSpec, HTTP or model input. Every ancestor is a real directory owned by root or the dedicated trusted launcher UID and not writable by group/other. The root is owned by the launcher UID with mode0700. Neither the application service nor an attempt shares that UID or access to this root. Host root and launcher code are in the trusted computing base.

| Entry | Exact requirements |
| --- | --- |
| Root .admission.lock | Preprovisioned empty regular file, launcher UID, mode0600, nlink=1; permanent inode for bounded allocation/inventory critical sections. |
| receipt UUID directory | Canonical lowercase UUID from createLaunchJournal, exclusive mkdir mode0700, launcher UID, same filesystem as root. No caller-selected suffix or path. |
| Receipt .writer.lock | Exclusively created empty regular file during allocation, launcher UID, mode0600, nlink=1; file and directory synced before handoff. Permanent inode for that receipt. Neither lock is ever unlinked, renamed, replaced or truncated, including shutdown/recovery. |
| record.json | Regular file, launcher UID, mode0600, nlink=1; bounded canonical version1 LaunchJournal. |
| record.next | Sole fixed staging name inside that receipt directory; exclusive creation, mode0600, regular, nlink=1. It is never a recovery authority. |

Validate ancestor components with lstat before use, then open root/receipt directories with O_DIRECTORY | O_NOFOLLOW, and files with O_NOFOLLOW. Use O_NONBLOCK when opening an existing file so a substituted FIFO cannot block before fstat rejects it. Check descriptor fstat against the expected type, exact permission bits including absence of special bits, owner, nlink for regular files, device and inode; compare with the named entry after opening. Require lock descriptor numbers to be at least3. Refuse a missing existing lock, foreign ownership, links, changed inode, unsupported modes or unexpected entry; do not silently chmod, chown, adopt or repair it. Only the allocator may create a new receipt's lock, once, before its initial record.

O_NOFOLLOW protects the final component only. Protected, nonreplaceable ancestors are therefore part of this design's security boundary. Rechecking lstat/fstat detects accidental or out-of-contract replacement; it is not a race-proof substitute for directory-relative syscalls against a malicious launcher UID. Supporting a hostile same-UID writer would require a different boundary and separately reviewed native/openat2 implementation. [Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

Hashes validate record consistency and recipe identity. Protected ownership supplies authenticity. A coherent rewrite by trusted host root is outside the threat model. Startup discovers receipts from this root itself, including an intent whose application receipt response was lost.

## Cross-process lock and descriptor lifetime

The fixed acquisition sequence is:

1. Validate the protected root and the applicable permanent lock; open it O_RDWR | O_NOFOLLOW | O_NONBLOCK without O_CREAT/O_TRUNC. Retain the FileHandle strongly for the critical section or receipt-owner lifetime.
2. Spawn the operator-installed, pinned /usr/bin/flock with exactly ["-x", "-n", "-E", "75", "0"]. Pass stdin: lockHandle.fd; stdout/stderr: "ignore"; explicit fixed environment LANG=C, LC_ALL=C. There is no shell, filename operand, command operand, --fcntl, --unlock or caller argument.
3. Await definite normal exit0 and recheck the lock's named inode/owner/mode. Exit75 means journal_locked. Any other exit, signal, spawn failure or five-second acquisition deadline means capability_unavailable; no scan, write or effect is admitted. Track and terminate/reap the exact helper on a deadline. Until it has definitely exited, keep the store failed and retain the parent descriptor; do not retry with another helper.
4. Keep the descriptor open through the owner's reads, writes, outstanding I/O and shutdown draining. No other subprocess receives it. Ordinary child spawning must demonstrably close unrelated descriptors on exec. Close the parent handle only after the helper and pending filesystem work have settled; never issue an explicit LOCK_UN.

Linux flock locks belong to the open file description. Duplicated descriptors share the lock; final close releases it, while explicit unlock through a duplicate also releases it. Independent opens are different descriptions. This makes Bun's numeric-stdin behavior, rather than merely its TypeScript signature, material. [Linux flock(2)](https://www.man7.org/linux/man-pages/man2/flock.2.html)

Verified source fact: util-linux v2.41.3 descriptor form parses the supplied FD, calls flock, sets success status and skips the command branch. That normal path returns without LOCK_UN. Unlock is selected only by the explicit unlock option. The registered exit handler handles stdout/stderr, not the lock on stdin. [flock.c](https://github.com/util-linux/util-linux/blob/v2.41.3/sys-utils/flock.c#L311), [success return](https://github.com/util-linux/util-linux/blob/v2.41.3/sys-utils/flock.c#L395), [closestream.h](https://github.com/util-linux/util-linux/blob/v2.41.3/include/closestream.h#L65)

Bun documents numeric stdin descriptors, but current online documentation is newer than the locally observed Bun1.3.14. It is not proof that this installed runtime duplicates the same open file description or closes unrelated descriptors. Pin and record the Linux Bun and util-linux binary versions/hashes, then pass the lock tests below. No fallback to FFI, shell lock directories or PID-age guessing is admitted. Bun currently documents FFI as experimental; it adds an unnecessary native ABI surface here. [Bun spawn](https://bun.com/docs/runtime/child-process#input-stream), [Bun FFI](https://bun.com/docs/runtime/ffi)

Inference to verify: after the short helper has exited, killing the sole Bun owner releases the lock if no ordinary child inherited its descriptor. Killing the owner while the acquisition helper is still alive can leave that helper holding the duplicate until it exits; this blocks a successor safely. It never authorizes unlinking the lock. The future host service must account for that exact child during process-tree shutdown. Lock release provides writer exclusion, not an attempt deadline or proof that a Docker operation stopped.

## Process ownership and handoff

The control service owns allocation/inventory, each already-selected fixed systemd runner owns one active receipt, and its ExecStopPost helper owns that receipt only during post-exit reconciliation. Every process uses the same lock primitive; no independent journal broker is introduced. The sole allowed nesting is installation lock then receipt lock. Receipt writers never acquire the installation lock, including acknowledgement, cancellation and cleanup. Acquisition is nonblocking; no process waits for a receipt while holding the installation lock.

Allocation holds .admission.lock, checks bounded inventory/idempotency, creates the receipt directory and permanent lock, then acquires that new receipt lock. It commits the initial inert intent and syncs its namespace. It releases receipt then installation lock before asking the host service to start the fixed unit. No global lock remains held across unit startup, control IPC or daemon work. The runner must acquire its receipt lock, reload the latest record, validate ownership and recheck deadline/cancellation/fresh authorization before admitting any effect; the initial record alone grants no start permission.

During a live runner's lifetime, control sends activation/input/cancel through the future fixed authenticated runner command channel. Control does not write around its owner lock. The application retains cancellation/dispatch intent in its existing DB authority and treats lost runner-command delivery as unresolved;008d adds no DB queue or command transport. In the handoff gap, a cancellation handler may claim the idle receipt, durably cancel, and release it. A late runner then reads that cancellation and refuses effects. If the lock is busy, control retains/reconciles the command through the runner channel; it never steals ownership. Detailed transport and command delivery proof remains a separate integration gate.

Control-service death leaves independent runners holding their own locks and maintaining their deadlines/facts. Restarted control inventories those busy receipts without taking over. ExecStopPost may claim a receipt only after the runner and its relevant children have definitely exited, then reload and reconcile exact pending operations. Busy means quarantine/defer, never unlink or PID-age takeover. A free receipt lock alone proves neither that a delayed unit cannot start nor that an external mutation settled: a recovery claimant closes admission durably before reconciliation; a later unit must reload and obey it. Pending daemon outcomes remain uncertain until exact backend facts settle them. No cleanup helper may erase a live staging file or infer settlement from lock availability.

## Record boundary and bounds

Use the accepted parseLaunchJournal(raw, { policy, receiptId }) for direct lookup and the directory UUID as expected receipt during startup scanning. This parser already checks the closed version, stored spec shape, immutable tuple/digests and legal state. Historical expiry remains valid storage data; only fresh parseLaunchSpec admission grants a future launch.

Persist exactly UTF-8 JSON.stringify(parsedRecord) plus one newline, with the schema parser's field order; no pretty printing, BOM, alternate envelopes or application payloads. Pin this serializer as the version1 disk format. On read, bound allocation to16KiB+1, reject bytes beyond16KiB, fatal-decode UTF-8, reject a BOM, JSON-parse, run the strict journal parser, then require exact equality with canonical reserialization. This intentionally rejects duplicate keys, extra whitespace/content, alternate numeric/escape encodings and unknown fields without another generic JSON parser. Changing canonical field order requires an explicitly reviewed disk-format migration.

Read through a verified descriptor, never an unchecked readFile(path). Reject nonregular files, size0, size>16KiB, early EOF or trailing bytes. Read at most the cap plus one sentinel byte, then recheck descriptor and named entry. Under the receipt lock, changing metadata/identity is invalid. During unlocked read-only inventory, a concurrent atomic replacement means inventory_busy; retry once within the overall budget, then deny new admission if it remains unstable. Serialization is bounded before opening a staging file; accepted schema string/collection limits bound the object itself. Add a maximum-length legal record test to demonstrate it fits16KiB.

Inventory holds the installation lock and uses incremental directory iteration, not unbounded readdir. Stop at1024 receipt directories and read one record at a time. For each receipt, try its lock: if acquired, validate stable layout/record and release; if busy, boundedly read a canonical record snapshot solely for immutable identity/idempotency. A live owner's record.next is expected during commit and is not corruption. Busy snapshots never grant effects or cleanup authority; instability, unreadable content or missing initial record denies new admission without adopting/deleting anything. Diagnose stale staging/corruption only after owning the receipt. At capacity, deny new receipts while allowing independently locked existing receipts to reconcile. No garbage collection in008d: tombstones/unresolved records consume this cap until a reviewed RFC010 retention protocol exists. Keep at most32 queued calls per owner; reject excess with journal_busy. Events contain no input bytes. This is bounded serialization, not durable scheduling or a persistent index.

## Commit protocol

Each receipt owner maintains its current validated record internally. An apply call uses transitionJournal on that current record; callers cannot replace a whole snapshot. Exact inert replay produces no new effect. Before each mutation, reread/compare the complete canonical current record and recheck its permanent lock identity. Operation sequence alone is insufficient as a revision: cancellation and acknowledgement can change state without incrementing it.

For a new receipt, createLaunchJournal rechecks fresh admission. Under the installation lock, inventory searches installation/attempt identity: an identical existing spec/recipe returns that receipt without a new intent/effect; a changed descriptor conflicts. Duplicate attempt identities already present are corruption, not a choice between records. Existing terminal or uncertain records cannot be bypassed by generating another receipt. Exclusively create the new directory; EEXIST is conflict, never adoption. Open/verify that directory, create/sync its permanent lock, sync its directory and sync the installation-root directory before handoff. A crash-created incomplete directory is retained for repair.

For each actual record change, including initial intent, pending operation, cancellation and backend fact:

1. Validate the full proposed record against trusted policy/receipt and serialize within the byte cap. There must be no preexisting record.next. For replacement, verify the old record and its single link; for initial insertion, record.json must be absent.
2. Open record.next with O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW and mode0600. Verify its descriptor identity, owner and single link. Loop writes until every byte is written; zero progress or a short write followed by error fails the commit.
3. Await FileHandle.sync() on the staging file; close it and observe close success. Rename record.next to record.json within the same verified receipt directory. Never truncate/overwrite the current record in place.
4. Await sync() on the receipt directory handle. For initial insertion the previously completed root-directory sync also remains required. All filesystem operations are awaited sequentially.
5. Reopen and validate record.json through the bounded read path; require exact intended bytes. Recheck protected path/lock identities. Only now update the owner's current snapshot and resolve a committed result. A later close error also fails the operation; use explicit handle lifetimes, not forgotten finalizers.

FileHandle.sync requests a storage flush; file sync alone does not persist the containing directory entry. Rename provides atomic replacement, while directory sync supplies the namespace durability barrier. Readback detects incorrect content; it does not substitute for either sync. [Node FileHandle.sync](https://nodejs.org/api/fs.html#filehandlesync), [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html), [Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)

Any error after mutation begins is journal_durability_unknown: poison this store instance, close admission, retain exact receipt/staging names and fixed diagnostic stage, and do not automatically retry, delete, promote or roll back files. An otherwise visible valid record cannot turn a failed sync into success. Validation failure before mutation is journal_invalid; capacity/lock conflicts have their distinct fixed codes. Never expose raw paths, file contents or OS error text to application logs.

A five-second operation budget bounds admission/replies, not a blocked kernel fsync. If the timer wins, report unknown and poison the owner, but keep its lock and references until outstanding I/O actually settles. Do not use Promise.race followed by releasing the lock or starting another write. A later successful completion cannot revive that instance or authorize an effect. Process termination by the separately trusted host service is a future operational concern; it must not be represented as a successful storage commit.

The only authority returned here is that specific bytes passed the storage protocol. Future backend code must serialize transition, durable commit and one-time effect submission under the same receipt owner, rechecking cancellation/deadline immediately before submission. It must persist facts before replying. A delayed committed draft must not be executed after a competing cancel or owner shutdown.008d provides no Docker call, effect callback, activation API or scheduling mechanism and cannot prove that later integration. A storage-only return must not be advertised as a durable runnable-work token.

## Restart and ambiguous state

Acquire the installation lock for bounded inventory, honoring busy per-receipt owners as above; release it before recovery work. Never reconstruct a missing record from application state, a staging file or a container name. Once a receipt is exclusively claimed, missing/corrupt/noncanonical records, incomplete directories, leftover record.next or foreign entries are retained with a fixed recovery-required report and deny new installation admission. Independently owned valid receipts can still persist deadlines/cancellation/cleanup without the installation lock.008d provides no automatic repair/delete command; operator repair needs a later reviewed procedure with the same receipt lock (and installation lock first if changing layout). This conservative availability cost keeps partial writes from becoming authority.

A valid record without staging can be loaded for inspection, including an expired one. A busy live owner's pending operation is left to that owner; inventory does not mutate it. After ownership/death handoff to a recovery claimant, loaded pending operations are unresolved, never resubmitted. Before backend reconciliation, that claimant commits the accepted unknown event for a pending operation and cancel(reason=recovery) for other nonterminal resources as applicable. Reading a prepared/running record never activates or resumes it. Matching late backend facts can settle exact ownership for stop/removal; absence alone cannot clear uncertainty. No reconciliation fact is synthesized from filesystem presence.

An acknowledged external effect whose fact commit failed may leave either the preceding pending record or the new fact record after restart. Both remain inert and subject to cancellation/reconciliation. A lost application receipt response does not orphan discovery: the root scan finds its record. A lost commit response does not authorize another create/start/input. Keep terminal tombstones and cleanup facts; record disappearance is never proof of resource removal or logical run success.

## Required implementation and platform proofs

All rows below are future required tests, not executed evidence. Use only synthetic journals and an in-memory effect counter; no Docker, provider, credential or application DB. Test processes exchange explicit bounded ready/cut-point messages, not timing sleeps. Every process has a finite harness deadline, exact PID ownership, output cap and retained cleanup result. SIGKILL tests prove process-crash behavior; they do not simulate power loss or prove hardware write caches honor flushes.

| ID | Exact scenario and required binary observable |
| --- | --- |
| L1 | Owner opens permanent inode, helper exits0, independent process gets75 while parent retains its FD. Closing an unrelated independent FD preserves exclusion. After owner closes its retained FD, contender gets0. This rejects a helper that reopens rather than duplicates the same description. |
| L2 | After acquisition helper exits, ordinary Bun child stays alive; kill owner with SIGKILL and await its exit. Contender gets0 while ordinary child still lives. Separate deliberate-inheritance control passes the FD to a child: contender stays75 until that child closes/exits. |
| L3 | Numeric-stdin mixed with stdout/stderr ignore: child reads a byte from a dedicated synthetic descriptor and parent's unpositioned read sees the next byte. Parent FD remains valid after helper exit. Use a disposable probe file, never write to .writer.lock. |
| L4 | Two owners of the same receipt: exactly one ready, other journal_locked with no files/effects. Distinct receipt owners progress concurrently. Kill helper before acquisition acknowledgement: never ready, exact helper settles, no retry/adoption. Missing binary/pin/platform deny capability. |
| F1 | Existing/new valid record completes file sync, rename, directory sync, readback and survives fresh-process reopen with identical tuple and bytes. An observer sees old or new complete canonical record, never a partial one. |
| F2 | Inject partial write, zero write, ENOSPC/write failure, file-sync EIO, close failure, rename failure, directory-sync EIO and readback mismatch separately. Each returns fixed failure, effect counter0, owner poisoned, second mutation refused. Include an error reported after the underlying write/sync actually completed. |
| F3 | Hold an I/O promise past its budget, then resolve it. Caller sees unknown; lock remains exclusive until settlement/shutdown; no second write/effect and no late success. An unsupported directory-sync primitive denies readiness. |
| P1 | Root/ancestor/receipt/file symlink, hardlinked regular file, foreign UID, permissive or special mode, lock inode replacement, FIFO, oversized file, invalid UTF-8, BOM, duplicate key, unknown version, changed immutable tuple and unexpected entry all fail before effects; unrelated target bytes remain unchanged. |
| P2 | Maximum legal record fits; byte cap+1 and receipt1025 fail boundedly. At exactly1024 records existing transitions remain possible while a new receipt is denied. Queue call33 gets busy; queued operations cannot overwrite a cancellation using stale snapshots. |
| R1 | Fresh scan finds an intent after application receipt response loss. Repeating identical prepare returns its receipt without a second record/effect; changed descriptor conflicts. Expired records load without fresh admission. Pending create/start/input/stop/remove never replay, including lost fact-commit acknowledgement. Terminal tombstones refuse restart. |
| R2 | Every crash cut below yields either a complete old/new record or retained recovery-required condition. Live-owner staging during inventory is busy/expected, not corruption; after owner death it is retained and blocks admission. Control death does not block runner writes. Cleanup cannot claim until runner/children exit; busy never steals. Cancel in the allocation/unit-start gap is reloaded by the late unit, yielding no effect. No stage promotion, uncertain retry or absence-based cleanup claim. |

Crash cuts for both insertion and replacement: C0 before mkdir/staging; C1 after new-directory mkdir before root sync; C2 after root sync before staging; C3 during partial staging write; C4 after staging file sync before rename (include close boundary); C5 after rename before receipt-directory sync; C6 after directory sync before readback; C7 after readback before committed reply; C8 after committed reply and one synthetic effect but before fact commit/reply. At C0..C7 the submitting process has not issued that proposed effect. At C8 the counter is exactly1; restart still emits no replay. Capture surviving names, canonical validation result, readiness denial/allowance and synthetic effect count for each cut. Permission faults and syscall seams complement real SIGKILL children; neither is a substitute for the other.

## Next bounded implementation

After this proposal is accepted, allow only these five new product/test paths:

1. apps/server/src/modules/runtime/journal-files.ts — private filesystem/lock primitives, bounded codec and atomic commit; fixed error codes.
2. apps/server/src/modules/runtime/journal-store.ts — bounded installation inventory/allocation and serialized per-receipt ownership, current-state transitions, poisoned/shutdown state.
3. apps/server/src/modules/runtime/journal-files.test.ts — actual temporary-file tests and narrow write-fault seams.
4. apps/server/src/modules/runtime/journal-store.test.ts — multi-process/cut-point orchestration and semantic recovery tests.
5. scripts/fixtures/journal-writer-child.ts — fixed synthetic child modes and bounded test protocol, no arbitrary command/path service.

Reuse accepted008c types/functions without changing their state semantics. Each module stays below250 nonblank/noncomment lines; if the cohesive implementation cannot fit this five-path boundary, stop for a concrete scope review rather than compressing code or adding a framework. Unique evidence and the task document are additional artifacts. Export a trusted openJournalStore installation boundary with bounded inventory, createIntent and claimReceipt operations. createIntent returns only an inert receipt after releasing both locks; claimReceipt returns a serialized owner with readonly current state, internal-event apply and close. Inventory is explicitly observational and confers no ownership. Keep raw file-write helpers internal; no arbitrary caller snapshots or application-selected filesystem paths.

Provisioning blockers: a separately authorized Linux host/VM; persistent private local ext4 storage and dedicated UID separation; pinned Linux Bun and util-linux executable with verified ownership/version/hash; descriptor inheritance and directory-sync proof on those exact binaries; finite child-process test control and storage failure seams. Building/starting/provisioning these is outside this design assignment. Later launcher integration additionally needs the already specified systemd runner/helper, Docker controls and authenticated control transport. Full RFC008 and RFC010 remain incomplete; connection grants and native/browser broker channels are unchanged. No new credential or GUI channel is introduced here.
