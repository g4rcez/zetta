# Membership activation revision

Status: revised005g1 design accepted after [coordinator review](../reviews/membership-activation-005g1-review.md),2026-10-22. Design only. Implements the prerequisite selected in [dispatch claim store](dispatch-claim-store.md), coordinated with [identity lock order](identity-lock-order.md). No schema, migration, lifecycle service or deployed permission change has occurred.

## Current source and boundary

[Membership](../../packages/db/src/schema/identity.ts:6) has one persistent user-keyed row, active/removed status and timestamps; no enrollment generation. Its auth-user FK restricts deletion/update. The installation pointer references the active member composite key, so removing the current admin is already prohibited. [Runs](../../packages/db/src/schema/runs.ts:13) retain a restrictive owner FK to membership. Neither a current active status nor a freshly issued actor proves uninterrupted membership since a queued run or readiness confirmation was recorded.

The only production membership insert/reactivation sites found are [enrollment.acceptInvitation](../../apps/server/src/modules/identity/enrollment.ts:127) and [admin-lifecycle.activateMembership](../../apps/server/src/modules/identity/admin-lifecycle.ts:50). The latter serves existing-account bootstrap and replacement, including credential operators that delegate after provisioning. Signup creates no membership. [Access](../../apps/server/src/modules/identity/access.ts:17) reads active state and issues process-local actors; it does not stamp durable provenance. Admin replacement keeps the previous admin an active ordinary member and deletes both affected users' sessions; replacing the role is not removing membership.

There is no production membership removal service in the inspected scope. Connection/run race proofs and [identity browser support](../../apps/server/src/test-support/identity-browser-server.ts:72) issue synthetic direct SQL removals. Those fixtures cannot stand in for future atomic removal/cancellation/schedule suspension. New revision support must not claim that missing lifecycle operation exists.

## Exact stored contract

Add `membership.activationRevision` mapped to `activation_revision integer NOT NULL DEFAULT 1`; named check `membership_activation_revision_check` requires1..2147483647. A single server-owned monotonic integer suffices; no random epoch or historical UUID uniqueness ledger. It is internal provenance, never a caller-set enrollment input or public role/permission.

Migration backfills **all existing rows**, active and removed, to1 at one controlled boundary. This is a new baseline with no claim about earlier activation history. Later009 producer metadata remains NULL on legacy runs, so boundary backfill cannot make old work eligible. Future020 readiness likewise has no inferred confirmation at revision1.

A BEFORE INSERT OR UPDATE row trigger `membership_activation_revision_guard` executes a bounded schema-qualified function `public.membership_guard_activation_revision()` with fixed SQLSTATE23514 and closed constraint identifiers:

- INSERT requires revision1 (`membership_activation_initial`); any initial status must still satisfy existing status/removal checks. The default keeps existing fresh-row fixture inserts compatible. It does not authorize membership creation.
- UPDATE cannot change user_id (`membership_activation_identity_immutable`). Retaining the existing identity key prevents moving activation history to another account.
- OLD removed → NEW active requires OLD revision below2147483647 and NEW revision exactly OLD+1 (`membership_activation_transition`). Test MAX before arithmetic to avoid integer overflow; exhaustion uses `membership_activation_exhausted`. Any status corruption still fails existing status checks.
- All other valid transitions, including active→active, active→removed and removed→removed, require NEW revision=OLD (`membership_activation_transition`). Omitted increment, decrement, reset and arbitrary jump fail. The trigger validates the service's explicit value; it does not silently repair a caller's wrong value.

No trigger reads another table, acquires an unrelated lock, changes joined_at, issues authority, terminalizes runs or resumes work. No SECURITY DEFINER, dynamic SQL, new global lock or custom setting. Existing timestamp/status/admin constraints remain unchanged. Ordinary timestamp/no-op updates at MAX are valid; only a new activation is denied. A failed activation rolls back invitation consumption, audit and pointer/session changes in its transaction.

## Lifecycle wiring and lock integration

Implement after005f2 reproduction and the separately reviewed005f correction are stable. Do not restore enrollment's current inverse ordering while adding the revision. Administrative operations retain installation first, then complete sorted auth accounts FOR UPDATE, then complete sorted memberships FOR UPDATE, then invitation/session/audit changes. Connection resource auth prelocking remains005f's responsibility. Activation guards only compare OLD/NEW and introduce no new cross-table order.

`enrollment.acceptInvitation` selects status and activationRevision under the existing target membership lock. Active remains a denial without consuming an invitation. Missing row inserts revision1. Removed row at MAX denies before consuming; otherwise the conflict update sets the locked next revision, with removed-status and expected-revision predicates. The row trigger is the final invariant. Consume, activate and audit remain one transaction with opaque existing failure behavior. Same consumed token never increments again; two valid invitations racing for the removed account result in one activation and only its invitation consumed.

`admin-lifecycle.lockMembership` selects status and revision; `activateMembership` returns unchanged for already-active, inserts1 for absent, and applies the same checked increment for removed. Bootstrap uniqueness collision rolls back a tentative activation. Replacement to an active member preserves revision; replacement to removed increments once; previous admin stays active with unchanged revision. Exhausted target denies the whole replacement without pointer, audit or session deletion. No credential-operator API change: a prior separately committed provisioned account can still remain unenrolled if activation fails, as documented today.

Future removal must lock in accepted005f order, preserve activationRevision and joinedAt, set removed timestamps, and persist required resource cancellation/suspension before releasing the membership lock. It must not request capacity after membership. Current admin removal still requires separately valid pointer transition. This future integration is a required gate before dispatch/bot durable eligibility, not delivered by005g schema support. Proof-only direct removal updates preserve revision automatically because they omit the column.

Do not add activationRevision to ActiveActor as reusable authority. Future009 trusted submission and010 reservation read it fresh under membership lock;009 stamps immutable actorActivationRevision and closed producerKind/version. Original request replay retains the stored stamp. Removed→active changes the locked revision, so retained old queued work/readiness fails exact equality even though the account is active again. Owner history reads remain separate from execution eligibility. Future020 confirmation binds actor and owner activation revisions where required by its accepted ownership/query design.

## Retention and runtime permissions

A revision may not reset through membership deletion/reinsertion while dependent evidence exists. Existing runs.owner_user_id RESTRICT FK retains membership while any run remains; future readiness/binding evidence must use a restrictive membership owner FK before those features can claim this guarantee. No CASCADE or deletion of evidence to permit reactivation. A stamp alone without a retaining FK is insufficient.

Deployment must use a non-owner, non-superuser runtime role with no membership DELETE/TRUNCATE, schema CREATE, table ownership/ALTER, trigger-disable ability or role escalation; grant only required SELECT/INSERT/UPDATE (and no UPDATE user_id). Migration/operator ownership is separate and trusted. REVOKE alone is insufficient if PUBLIC or inherited roles grant access; inspect effective privileges and role memberships. Existing proof runner owns its disposable database and is not evidence of runtime least privilege. A separate scoped role proof must create a fixed non-owner test role, exercise actual allowed activation, and prove DELETE/TRUNCATE/DDL denied; it cannot merely inspect SQL strings. Durable dispatch/readiness execution eligibility stays gated until that actual role confinement and retaining-FK proof is accepted. This design introduces no blanket deletion trigger that breaks existing owner-only fixture cleanup. Privileged operators remain TCB and can destroy/reset history; restoring evidence and membership requires a consistent reviewed backup, never an automatic reset.
