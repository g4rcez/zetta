# RFC-005f1 identity lock-order review

Verdict: **CLEAR the amended per-account prelock design for coordinator acceptance and bounded reproduction-source assignment.** Reviewed2026-10-22 against [identity-lock-order](../decisions/identity-lock-order.md), including its explicit rejection of NO KEY UPDATE-only and its optional intended-user prelock. This review is not production acceptance or a live deadlock result. No production/test code, schema or database was changed or executed.

## Verified source facts

- enrollment.ts:61–72 locks installation, active-admin membership, then actor account FOR UPDATE; acceptInvitation:138–142 subsequently locks subject membership before checking already-active status. A sorted B→A team operation can oppose admin-first A→B enrollment when B sorts first. This is a source-derived schedule;020 service does not exist.
- admin-lifecycle.ts:116–121 takes installation, lexically sorted account FOR UPDATE and sorted memberships FOR UPDATE. Replacement activates the target, updates the singleton, deletes both affected users' sessions at130 and audits in one transaction. Existing-account operator runs that actual service; private credential operator provisioning commits a separate account creation before invoking lifecycle.
- connections/store.ts:18–21,73 locks actor membership before insertion; schema/connections.ts:50 references auth user. The resulting auth FK KEY SHARE can oppose replacement's user FOR UPDATE while replacement waits for that membership. Installed Drizzle supports `no key update` in pg-core/query-builders/select.types.d.ts:64 and emits the exact strength in dialect.js:209–217. No guessed API is needed.
- runs.ts:53–61 takes fresh membership before run/attempt. Its own owner references membership, and its existing attempt triggers reacquire the already-held run. It does not introduce an explicit account/installation lock after runtime rows. This audit does not enable a producer or change that source.
- identity schema's installation pointer references membership(user_id,status), with active status required. The correction must keep installation first for identity writers and hold both old/new membership rows before pointer replacement. Rechecking active-admin authorization under those locks remains mandatory. Ordinary row locks on membership do not themselves update the FK; future status-changing removal needs its own audit and cannot remove the pointed-to sole admin.

## Required finding: account-lock compatibility also changes the session fence

`FOR NO KEY UPDATE` remains incompatible with another account UPDATE/DELETE, so a stored email read cannot race an account email update once its row lock is held. It is compatible with KEY SHARE, which solves the007 insertion edge. That compatibility also permits session insertion: schema/auth.ts:29–31 gives session.user_id an auth-user FK. Better Auth1.7.7 internal-adapter.mjs:247–319 creates sessions through createWithHooks→adapter.create; neither it nor current auth configuration adds membership/session-generation coordination.

Current FOR UPDATE drains an already-in-flight session FK holder before replacement reaches DELETE. Under the proposed weaker lock alone, a session transaction can insert, stay uncommitted while replacement's DELETE statement takes its snapshot, then commit before replacement commits. DELETE cannot see that row, leaving a pre-commit session token alive. An insertion arriving after the old exclusive account fence is held instead waits until replacement commits; that is a later signin, which remains allowed. These cases must not be conflated.

[The operator contract](../operations/identity-admin.md) promises deletion of both users' stored sessions in the replacement transaction, while explicitly distinguishing SQL rows from effective cookie/cache revocation. Existing004 evidence covers fixed affected sessions and rollback, not this overlap. The source-derived overlap is therefore an unverified regression risk in the proposed change, not a claim that the current production implementation has already failed a live session test. Fresh membership/admin lookup prevents a stale admin boolean from being trusted, but it does not satisfy the separate session-invalidation promise.

PostgreSQL documents both FOR UPDATE versus KEY SHARE incompatibility and NO KEY UPDATE compatibility. [PostgreSQL18 lock modes](https://www.postgresql.org/docs/18/explicit-locking.html)

## Revised minimal correction

Keep admin-lifecycle.ts unchanged: installation, all sorted auth accounts **FOR UPDATE**, then all sorted memberships **FOR UPDATE**, with current session deletion and audit in the same transaction. Normalize enrollment to that order. Change only007's local member helper to acquire its issued actor's auth user **FOR KEY SHARE before membership FOR UPDATE**. Deny a missing auth account through the existing opaque access error. Continue the fresh active-membership check, issued-actor check and exact-owner predicates; the prelock confers no authority.

The complete order is capacity when required → installation for administrative identity changes → all needed auth accounts sorted → all needed memberships sorted → existing resource order. Use the same lexical comparator as existing admin replacement, deduplicate IDs, and finish the entire account stage before any membership lock. A future020 actor/owner operation must take both auth rows KEY SHARE first, then both memberships UPDATE. It must not lock account B after locking member A, upgrade a KEY SHARE lock after membership, or perform an account/profile mutation in its resource transaction.

For007-first, replacement now waits on the already-held user KEY SHARE before it can hold membership;007 completes its FK insertion without needing a conflicting new lock. For replacement-first,007 waits on the account before taking membership. The session FK fence remains the existing FOR UPDATE, avoiding the NO KEY UPDATE regression. This adds one short query per007 transaction (including list through the shared helper) and retains contention for the affected account; it introduces no installation/global session-write lock for ordinary resource work. No new global session-table fence, auth hook or epoch is needed for this correction.
