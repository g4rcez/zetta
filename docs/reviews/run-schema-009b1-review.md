## Findings and limits

- **Low, integration condition — privileged TRUNCATE is outside the invariant.** `packages/db/run-test-migrations/20261022180711_runs_constraints/migration.sql:69` and`:72` register only row INSERT/UPDATE/DELETE triggers. `TRUNCATE public.run_attempts` is therefore not covered, and no reverse FK prevents that operation. Do not grant runtime TRUNCATE/DDL/trigger-disable authority; if that authority is intended, add and prove a separately reviewed guard before asserting unconditional current-attempt existence. This does not block the accepted ordinary-DML foundation. PostgreSQL explicitly requires a separate TRUNCATE privilege and does not fire DELETE triggers for it. [PostgreSQL18 TRUNCATE](https://www.postgresql.org/docs/18/sql-truncate.html)
- **Low, documented service boundary — table checks are not the full semantic validator.** `packages/db/src/schema/runs.ts:79` permits terminal combinations such as succeeded/no_effect or interrupted/known;`:44` and`:91` enforce timestamp ordering rather than finite JavaScript epoch range. Canonical tuple content, maxEvents-relative result sequence and cross-row run/current-attempt projection are also intentionally service responsibilities.009c must reject these corrupt/unsupported rows with fixed errors and never release capacity or dispatch from raw SQL rows. The task handoff states this division; it is not an unreported claim of full state-machine enforcement.

## Constraint and ownership audit

Run immutable tuple covers ID, owner, logical key, origin, all bot/conversation/config/version references, input version/text and createdAt. Attempt immutable tuple covers ID/run/owner/generation/createdAt; assigned lease identity cannot be removed/replaced and assigned expiry cannot move backward. Restrictive membership/run composite FKs and owner/key uniqueness prevent foreign-parent association and global idempotency collisions. No cascade, bot/conversation FK cycle, grant table or second queue was introduced. Membership existence is not active membership:005 provenance and fresh membership locks remain mandatory service checks.

Counters use bounded integers; IDs use UUID types or explicit C-collated ASCII grammar. Snapshot text is96KiB and JSON-array shaped, preserving exact parameter bytes; service canonicalization remains necessary. Result fields are all-null or a complete version1 record, <=64KiB text, closed nullable error and sequence0..1000. SQL null branches explicitly require populated required result fields; no apparent UNKNOWN bypass was found for partial result/lease combinations. Queued forbids lifecycle facts; running requires complete lease triple and no result/finish; known effects are terminal-only. Stop is independently allowed while running; terminal does not imply resource absence. Time inequalities cover creation/claim/start where present.

## Deferred trigger reasoning, not concurrency proof

At custom SQL`:58`, deferred evaluation reads and locks the current run;`:61` locks the matching current-generation attempt FOR KEY SHARE. Both run mutations and attempt insert/update/delete schedule checks; attempt update/delete also takes the parent lock at`:36`. Identity movement is forbidden before it could orphan the old parent. A run removed together with its attempts has no remaining obligation. No immediate WHEN or stale event-generation lookup is used.

Inference for READ COMMITTED: the shared parent lock orders pointer changes against attempt deletion; rechecking the locked current pointer and key-sharing the referenced tuple should prevent a successful orphan commit. Under REPEATABLE READ, the matching attempt lock matters even when the parent was only locked, not changed: a tuple deleted since the transaction snapshot must not be accepted as an unlocked historical row. PostgreSQL documents snapshot-specific locking behavior and errors for changed locked rows. [Isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [row locks](https://www.postgresql.org/docs/18/explicit-locking.html)

Direct attempt-first DML can lock an attempt before its BEFORE trigger acquires the parent, opposing run-first service order. Deadlock/serialization abort is an allowed safe result, not a claim of nonblocking behavior. Production must retain membership→run→attempt order (and the accepted connection/grant extension), map DB failures conservatively and never auto-replay external work.

Required live acceptance: both directions of current-pointer versus target-delete race at RC and RR, same-transaction insert+attempt and pointer changes, current-attempt deletion without run update, immediate SET CONSTRAINTS, immutable/lease edits, partial result/lease/null negatives, owner substitutions and rollback/cleanup. Independent connections must show no committed orphan; deadlock/serialization failures must be captured. Current offline passing tests do not prove these scenarios. Parent009 remains incomplete.
