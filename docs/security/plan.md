# Security review and hardening plan

Date: 2026-10-29. Scope: `apps/server`, `apps/web`, `apps/desktop`, `packages/*`, Docker, CI.
Method: four read-only code audits (auth/HTTP boundary, integrations/secrets/SSRF, exec/LLM tools/bot database, web/desktop/supply chain). Each finding below was read in code. Items marked _plausible_ depend on runtime behavior that was not run.

Update 2026-11-06: the bot database plugin was removed (bots keep what they need in memory). Mentions of it below, including C10, are history.

Status values: **Fixed** (this change), **Decision** (needs an owner decision: it changes auth, a public contract, or product behavior), **Planned** (safe to do, larger than this change), **Accepted** (known, documented, low risk).

## Threat model summary

- Trust boundaries: browser to API (cookie + `Origin` check), LLM output to tools, third-party text (mail, chat, web pages, MCP) to the prompt, server to the network (MCP/IMAP/WAHA/Bitwarden URLs), bot code in the host or a container, the Docker network.
- Assets: stored connection secrets (AES-GCM), session cookies, per-user data, VM/browser sessions, the host.
- Main residual risk: **a prompt-injected bot that has code, browser, or write tools.** Several items below reduce the blast radius; the host-mode items (C1) are the largest.

### Plugin scope: private by default, shareable with the team by the owner

Every plugin is private to the user who installed it. A plugin that declares **team tools** can be shared: the owner presses "Share with team" in Studio > Plugins (with a confirmation) and picks "stop" to take it back at any time. Going back to private removes every teammate's binding at once.

- A teammate sees it in a bot's plugin list as "Shared by <name>" and binds their own bot to it. The call runs through the owner's account (limits, allowlist and send switch are the owner's), and only the plugin's team tools work, enforced on every call, not only in the prompt.
- If the teammate installed the same plugin themselves, their own install is used.
- Shareable today: WhatsApp (team tools: `status`, `send_message`; teammates cannot read the number's chats) and Telegram (`status`, `list_chats`, `read_messages`, `get_chat`, `send_message`). Gmail, Drive, Calendar, Reddit, X, password managers and the bot database are personal and refuse sharing (`NOT_SHAREABLE`).
- Stored as `mcp_server.sharing` (`private` | `team`, default `private`); migration `plugin-team-sharing` is additive.
- Not covered: inbound routes of a shared plugin still belong to the owner, so teammates' bots do not receive the owner's incoming messages.

### Operator settings added

| Variable                  | Effect                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |

| `ZETTA_COOKIE_SAMESITE`   | `lax` or `strict` for web-only installs. Default `none`.                                               |
| `ZETTA_MCP_MEMBER_STDIO`  | `1` lets members use local MCP servers.                                                                |

## Accepted / noted

- `docker/browser/Dockerfile` runs Chromium with `--no-sandbox`; the container drops capabilities and publishes only on `127.0.0.1`. Matters only on multi-user hosts.
- Desktop (Electrobun, [desktop-app](../decisions/desktop-app.md)): the only page with an IPC channel is the bundled launcher (`views://launcher`: list, add, open and remove servers; no file, shell or network access beyond asking an address for `/api/meta`). Server windows run sandboxed with no IPC and no bridge, open other sites in the system browser (http, https and mailto only) and block every other scheme. There is no updater. Re-audit when the native bridge (phase 2), deep links (phase 3) or the companion (phase 5) land: each adds a way for a remote page to reach the app.

## Checked and found sound

CORS allow-list with credentials; `Origin` check on every non-GET route; first-account and invitation flow (hashed 256-bit tokens, atomic consume); owner scoping across teams/tasks/agenda/inbound/discussions/memory/knowledge/search/artifacts; all SQL parameterized (no `sql.raw`); connection encryption (AES-256-GCM, AAD binding, nonce ledger); OAuth state/PKCE; `assertPublicUrl` block list; credential fill (value never returned to the model); VNC ticket and origin check; container flags (cap-drop, no-new-privileges, no `docker.sock`, loopback publishing); bot database roles and identifier quoting; XSS in the web app (single `dangerouslySetInnerHTML`, on a bundled SVG).

## Verification

- Type check: `apps/server` (apart from `runtime/dispatch-schema-transitions.ts`, which this work did not touch), `apps/web` and `packages/auth` compile.
- Server suite against a scratch migrated database (created for this review and dropped afterwards; your dev and test databases were not used): all pass. Five tests were failing before this work for reasons outside it, and each is fixed here: the `app.ts` import test accepts any `modules/*/routes` import; the Google plugin test supplies the OAuth client the plugin now requires; artifact byte ranges answer the range asked (Bun returned the whole tail of a sliced file; answers are now capped at 8 MiB); the test cleanup deletes artifacts before users; the room-loop test waits for the step count and no longer expects fixture bots to receive tool instructions.
