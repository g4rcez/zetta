# Security review and hardening plan

Date: 2026-10-29. Scope: `apps/server`, `apps/web`, `apps/desktop`, `packages/*`, Docker, CI.
Method: four read-only code audits (auth/HTTP boundary, integrations/secrets/SSRF, exec/LLM tools/bot database, web/desktop/supply chain). Each finding below was read in code. Items marked _plausible_ depend on runtime behavior.

Update 2026-11-06: the bot database plugin was removed (bots keep what they need in memory). Mentions of it below, including C10, are history.

Status values: **Fixed** (this change), **Decision** (needs an owner decision: it changes auth, a public contract, or product behavior), **Planned** (safe to do, larger than this change), **Accepted** (known, documented, low risk).

## Threat model summary

- Trust boundaries: browser to API (cookie + `Origin` check), LLM output to tools, third-party text (mail, chat, web pages, MCP) to the prompt, server to the network (MCP/IMAP/WAHA/Bitwarden URLs), bot code in the host or a container, the Docker network.
- Assets: stored connection secrets (AES-GCM), session cookies, per-user data, VM/browser sessions, the host.
- Main residual risk: **a prompt-injected bot that has code, browser, or write tools.** Several items below reduce the blast radius; the host-mode items (C1) are the largest.

### Plugin scope: private by default, shareable with the team by the owner

Every plugin is private to the user who installed it. A plugin that declares **team tools** can be shared: the owner presses "Share with team" in Studio > Plugins (with a confirmation) and picks "stop" to take it back at any time. Going back to private removes every teammate's binding at once.

- A teammate sees it in a bot's plugin list as "Shared by <name>" and binds their own bot to it. The call runs through the owner's account (limits, allowlist and send switch are the owner's), and only the plugin's team tools work, enforced on every call, not only in the prompt.
- If the teammate installed the same plugin themselves, their own install is used.
- Shareable today: WhatsApp (team tools: `status`, `send_message`; teammates cannot read the number's chats) and Telegram (`status`, `list_chats`, `read_messages`, `get_chat`, `send_message`). Gmail, Drive, Calendar, Reddit, X, password managers and the bot database are personal and refuse sharing (`NOT_SHAREABLE`).
- Stored as `mcp_server.sharing` (`private` | `team`, default `private`); migration `plugin-team-sharing` is additive.
- Not covered: inbound routes of a shared plugin still belong to the owner, so teammates' bots do not receive the owner's incoming messages.

## Mail sent by a bot

Added 2026-11-22 (row C7). The tools `mail_reply` and `mail_send` of the built-in `mailbox` plugin have the tool effect `send`: a kind of write that can never be taken back, treated as a write by every test that asks "is this a read?". They send plain text, To only (at most 5 recipients, no Cc, Bcc or files), at most 3 per turn and 5 a minute and 20 an hour per mailbox. The decision is the server's, in `chat/mail-policy.ts`, and nothing about it is a rule in the prompt.

A mail goes out at once only when **all** of these hold:

1. The turn is the person's own message in their own chat with the bot. A loop step, a routine or any turn Zetta started is never a send.
2. Their own words ask for mail to be sent (`asksToSendMail`, English, Portuguese and Spanish, on their message only and never on mail text, tool results or the bot's words). A question about mail, a draft, a hold ("don't send yet") and an answer meant for them ("tell me", "reply here") are not requests.
3. The recipients are ones they pointed at. A reply goes to the author of a message of the conversation open beside the chat (ids the server resolved and checked, never one the bot chose), from the answered message's Reply-To or From (a Reply-To that is not the sender's own address is a card). A new mail goes only to addresses written in their message or to correspondents of that open conversation.
4. The only outside content the turn read is that open conversation. The chat service records, call by call, whether a call read anything else (another conversation, a search, a page, a file, another plugin, any other tool); a send after such a read is a card, also when the read is in the same reply, before the send. This stops a hostile mail from making the bot carry other mail back to its sender.

Everything else is a card that shows the mailbox, the exact recipients, the subject and the full text; Approve sends exactly that. The pending call is signed with a key derived from `ZETTA_CONNECTION_KEY` and the person, carries the bot and a nonce, and expires after 30 minutes; a changed, foreign, expired or replayed call sends nothing. A card of a paused plugin call (`tool_resume`) is never remembered, so "always allow" does not exist for mail. Sending off for the mailbox refuses in every case, with a sentence that only the person can turn it on. Rooms, inbound chats, outside-event turns and calls with no conversation do not have the tools, and a forced call is refused. Each send, card, approval and refusal leaves one row in the activity trail with the mailbox and the number of recipients; that trail takes closed tokens and ids only, so the address, subject and text live in the card and in the chat, not in it.

**Accepted risks.**

- When the person asks for a reply, the mail being answered can still influence the wording of that reply. It goes only to its author and the person sees the whole mail in the chat.
- A bot with code access or MCP servers can read files and pages inside its own tools without the server seeing it. This is the same trade-off `writeMode` makes for writes (row C3), so "no other outside content" means what the server saw.
- A bot that already knows something (its earlier replies in the same chat, memory) can put it in a reply the person asked for.
- When the person asks to write to someone, an injected bot can aim that mail at a correspondent of the open conversation (including the sender of a hostile mail) with text of its choice.
- The replay guard of an answered card is per process; across processes the card's own status stops a second answer.

## Accepted / noted

- `docker/browser/Dockerfile` runs Chromium with `--no-sandbox`; the container drops capabilities and publishes only on `127.0.0.1`. Matters only on multi-user hosts.
- Desktop (Electrobun, [desktop-app](../decisions/desktop-app.md)): the only page with an IPC channel is the bundled launcher (`views://launcher`: list, add, open and remove servers; no file, shell or network access beyond asking an address for `/api/meta`). Server windows run sandboxed with no IPC and no bridge, open other sites in the system browser (http, https and mailto only) and block every other scheme. There is no updater. Re-audit when the native bridge (phase 2), deep links (phase 3) or the companion (phase 5) land: each adds a way for a remote page to reach the app.
