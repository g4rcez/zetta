## Exported contract

All five Drizzle tables export through `@zetta/db/schema`; use `typeof table.$inferSelect` / `$inferInsert` for row types. All timestamps use PostgreSQL timestamptz and explicit caller values. UUID creation, canonical UUID input parsing and installed-provider membership belong to the trusted service.

- `connection`: UUID `id`, existing-user FK `ownerUserId`, `kind: "api-key"`, provider, label, state, revision, `currentCredentialVersion`, created/updated/expiry/revoked timestamps. Owner is 1–256 UTF-8 bytes. Provider uses canonical lowercase ASCII `[a-z0-9][a-z0-9_-]{0,63}`, not a URL; this is syntax only, not an installed-adapter allowlist. Label is 1–100 PostgreSQL Unicode characters and at most 400 UTF-8 bytes. Revision/version are positive signed 32-bit integers. Active requires null revokedAt; revoked requires non-null revokedAt. Owner/id index supports owner-bound ID pagination.
- `connectionCredential`: primary key `(connectionId, credentialVersion)`. Composite restrictive FK `(connectionId, ownerUserId, kind)` binds the immutable identity to its connection. Version-1 AES-256-GCM envelope has canonical bounded key ID, binary nonce/tag/ciphertext lengths 12/16/1–16,384. Envelope nonce FK includes connection/version, so one retained nonce cannot be assigned to a different credential identity.
- `connectionNonce`: lifetime primary key `(keyId, nonce)`, purpose `credential` or `key-check`, createdAt and nullable connection/version identity. Credential purpose requires non-null UUID and positive version; key-check requires both null. No outgoing FK or cascading delete: deleting ciphertext cannot delete a tombstone. Direct privileged deletes remain outside this structural guarantee.
- `connectionKeyCheck`: singleton `id = 1`, encrypted envelope, `noncePurpose: "key-check"`, `encryptionCount` in 1–1,000,000, createdAt. Its nonce FK requires a key-check ledger identity. Bootstrap inserts nonce first, then singleton with count 1, in one transaction. The service must lock this row for accounting and fail closed on missing/corrupt key-check state.
- `connectionMutationReceipt`: primary key `(ownerUserId, operationId)`, `operation: "create-api-key" | "replace-api-key" | "revoke"`, connectionId, nullable expectedRevision, exact 32-byte binary requestMac, and all original safe metadata scalar fields. Receipt `connectionId` maps to returned DTO `id`; receipt `credentialVersion` maps directly. No current-row join is needed to reconstruct the original result. Create requires null expectedRevision, revision/version 1 and active state. Replace/revoke require positive non-overflowing expectedRevision, result revision expected+1 and corresponding active/revoked state. Composite owner/kind/connection FK retains receipts with their connection. Request MAC computation and constant-time matching remain service obligations.

## Required service invariants

There is deliberately no reverse FK from `connection.currentCredentialVersion` to credential rows: an immediate FK would create an insertion cycle. The service must atomically insert connection, version, nonce and receipt; replacement inserts the next version before moving the pointer in the same transaction. Resolution must match owner, API-key kind, current requested version and the actual credential row; a missing/stale row denies resolution. There is no claim that a direct SQL writer cannot create a dangling pointer.

The service must enforce immutable owner/kind/id, installed provider allowlist, well-formed Unicode, forward-only revision/version changes, no reactivation, and exact expected revisions. Label/provider changes require a separately accepted method. It must retain old ciphertext as inaccessible, retain nonce ledger entries for key lifetime, increment encryptionCount under lock for each persisted encryption including key-check, enforce the active configured key, retry nonce collision at most three times, and never reset/decrement counts or silently bootstrap around existing state. The database bounds the stored counter but does not prove its correspondence to encryption history.

A valid same-operation replay returns the original typed receipt after fresh membership authorization and exact MAC comparison, before rejecting the now-stale revision or expiry. Readiness/resolution must separately check current connection state. No dispatch grant or decrypt callback is supplied by this schema; RFC-008/010 owns that integration.
