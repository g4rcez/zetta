# RFC-009b1: Durable run storage schema

Status: accepted offline implementation after coordinator checks and independent CLEAR review. PostgreSQL execution and concurrency proof remain required under009b1a. Parent RFC-009 remains incomplete.

## Scope and contract

Implements the accepted [durable-runs ADR](../docs/decisions/durable-runs.md). Owned product files are `packages/db/src/schema/runs.ts`, its test, the barrel export, offline `drizzle.run-test.config.ts`, and the new `run-test-migrations/` directory. The coordinator owns the legacy identity import allowlist. No existing schema/migration/helper/launcher, service, worker, grants or capacity tables were changed.

Exports `runs` and `runAttempts` through `@zetta/db/schema`; derive insert/select types from each table. SQL names are `runs` and `run_attempts`. Run, attempt, request and lease IDs are UUIDs. Existing owner/bot/conversation/configuration references use the RFC-006 1–128 ASCII identifier grammar; opaque resource IDs do not establish resource existence or authorization. Membership is the restrictive run-owner FK. Attempts bind `(runId,ownerUserId)` to the run. Owner/request, run/generation and composite result-target identities are unique. No delete cascades exist.

Configuration version, revision and generations use positive signed32-bit integers; result sequence is 0–1000. Timestamps are explicit millisecond-precision timestamptz values. `inputVersion=1` and private `inputSnapshot` text preserve exact canonical bytes; the database bounds it to96KiB and requires a JSON array. The service must validate the canonical versioned tuple, exact semantic equality, Unicode compatibility, fixture-only harness, resource provenance and budget relationships. PostgreSQL text rejects actual NUL; this is not secret detection.

Result columns are `resultVersion`, `resultText`, `resultErrorCode`, `resultLastSequence`: all-null or complete version1, text at most64KiB UTF-8, closed RFC-006 error/null and bounded sequence. They are private; service DTO/result parsers must validate correspondence to input maxEvents and terminal status/effect. Cancellation reason is nullable or fixed server-derived `owner_requested`, only on running/cancelled attempts.

Queued attempts have no lease/claim/start/finish/stop/result/cancellation facts and `no_effect`. Running requires the full lease/expiry/claimed triple, no finished/result, and `no_effect` or `uncertain`; independent `stopConfirmedAt` may be set before logical settlement. Terminal needs finishedAt and either no lease triple or the full triple. Known effects occur only on terminal attempts. Time checks follow creation/claim/start where present. Logical terminal status alone does not establish resource cleanup. RFC-010 must count all running leases and unconfirmed terminal resources; this schema supplies no claim release.

## Custom constraint migration

Installed Drizzle-kit1.0.0-rc.4 generated the table DDL unchanged at `run-test-migrations/20261022180455_runs_initial/`. Its imported membership reference does not cause auth/identity table creation. `--custom` support was verified against installed CLI help; the generator created `20261022180711_runs_constraints/`, then the authorized custom function/trigger SQL was authored there. Both retain generator-owned snapshots and `prevIds`; this kit uses those instead of a legacy journal. An initial empty custom folder generated in the same second would sort before the tables; only that empty folder was removed and regenerated later. No table DDL or historical migration was patched. Repeat generation reports no schema changes.

`runs_guard_identity` rejects changes to run ID, owner, request key, origin, bot/conversation/configuration identity/version, input version/text and createdAt. `run_attempts_guard_write` rejects attempt ID/run/owner/generation/createdAt changes, replacement or removal of assigned lease identity, and backward/removal of assigned lease expiry. Same expiry is allowed; future bounded renewal/authorization policy belongs to010. Both functions emit fixed SQLSTATE23514 constraint failures without row content.

`runs_check_current_attempt` is an initially deferred AFTER ROW constraint trigger on run INSERT/UPDATE and attempt INSERT/UPDATE/DELETE. It re-reads the current run's generation at deferred execution; no immediate WHEN or event-time pointer is used. Submission must insert the run and generation1 attempt in one transaction. The service locks membership→run→attempt. The trigger locks parent FOR UPDATE then the matching attempt FOR KEY SHARE; an attempt UPDATE/DELETE also locks its parent before proceeding. Thus pointer mutation and deletion contend on the same parent; the key-share lookup additionally prevents accepting a concurrently deleted tuple through an older isolation snapshot. A removed parent has no current-attempt obligation. Direct SQL that takes the attempt tuple before the parent can deadlock with run-first work; abort/serialization failure is acceptable, an orphan commit is not. This design requires actual READ COMMITTED and REPEATABLE READ pointer/delete race proof before acceptance. It is not claimed proven by source inspection.

No cross-row status projection trigger is added; service parsing and transitions must verify run/current-attempt consistency. Generations/revisions are bounded but their legal transition progression is a service responsibility. Immutability does not supply retention policy: privileged deletion of all attempts plus their run remains possible, and production retention is deferred011/025. Functions are local, schema-qualified, invoker-security PL/pgSQL with no dynamic SQL, networking or global settings.
