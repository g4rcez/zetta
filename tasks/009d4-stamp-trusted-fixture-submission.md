# RFC-009d4: Stamp trusted fixture submissions with activation revision

Status: source accepted after [coordinator review](../docs/reviews/run-fixture-producer-009d4-review.md), 2026-10-22. Depends on reviewed005g4 lifecycle and009d3 proof lineage. Existing009 store remains a trusted internal fixture producer, never a public bot/configuration submission boundary.

Own runtime/runs.ts and runs.test.ts (two) for initial implementation. Read active positive-int32 membership activationRevision under the existing membership FOR UPDATE in every owned transaction. New fixture submission atomically inserts producerKind fixture, producerVersion1 and that observed revision with the run/attempt. No request metadata, caller boolean, setter, global credential, alternate producer, canonical input version or DTO field is added. Preserve owner scope, lock order, fresh clock, rollback, duplicate-key races, outcome_unknown and current/result/cancel semantics.

Replay returns the original validated run for the identical canonical request without upgrading all-null legacy or an older activation stamp, even after reenrollment. Changed canonical input still conflicts. Parsing/owner history does not imply eligibility: future private dispatch compares exact stored provenance to current active revision. Caller-supplied provenance remains invalid input.

Meaningful failing-first storage-binding controls and relevant regressions, strict, diagnostics and source freeze precede review. No database, schema, proof client, existing integration proof, launcher, provider, install or Git action in this initial child. Actual legacy replay, atomic stamping, reenrollment and observed membership races require a separate reviewed integration fixture. Existing old run proof reset SQL cannot reactivate removed rows without advancing revision under the new guard; revise it only in a separately assigned proof scope or use a new fixed current-lineage proof, never disable the guard.

Frozen result: `owned` selects status and activation revision in the existing membership FOR UPDATE query, checks active membership and positive int32 revision, and passes the observed value through its private callback. Only a new run insert stamps fixture/1/revision. Original and insert-conflict replays validate and return stored rows without updating metadata. Public API, canonical input and DTOs remain unchanged.

Evidence: `local evidence`. Baseline 5 tests/34 assertions; red-first 7 pass/2 fail; focused 9 tests/240 assertions; relevant regression 60 tests/732 assertions; strict exit 0; two clean TypeScript diagnostics. SQL binding and transaction order use the installed Drizzle adapter with a synthetic query protocol, not actual database atomicity/race evidence. Foundation and old integration fixture hashes remain unchanged.
