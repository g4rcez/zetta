# RFC-010a: Design durable dispatcher authority and recovery

Status: accepted bounded design after independent CLEAR/APPROVE; no implementation or migration authorized by this document alone. Parent010 remains incomplete and global status is coordinator-owned.

Deliverable: [durable dispatch ADR](../docs/decisions/durable-dispatch.md). Read task010, accepted009 ADR/schema/pure contracts,007 connection encryption/storage ownership contract and008 supervisor/LaunchSpec/journal handoffs.009 store remains in progress and008 operational integration remains unaccepted.

The proposal selects one PostgreSQL queue and capacity mutex, claims retaining unknown-resource occupancy, single-use action grants, private transaction-scoped ExecutionAuthority instead of forged ActiveActor, full lock-order subsequences, committed-before-delivery credential admission, cancellation precedence and conservative restart. It names precise gaps: scheduled/membership-epoch authority, membership removal integration, unaccepted credential transport and missing-receipt launcher reconciliation. No endpoint, native readiness or automatic replay is invented.

Bounded010b/c/d/e slices are source proposals with<=5source files each plus focused tests/generated migrations. Each requires independent assignment and approval; shared identity/007/barrel/migration changes serialize. Proof plan covers DB races/fault injection and later actual launcher containment separately. Runtime roles must not receive privileged TRUNCATE/DDL authority.

Verification is source inspection and documentation validation only. [Evidence](../.omo/evidence/ulw/01a1643f-531d-7590-aec8-a8624a8fa202/G002-use-bun-typescript-and-the-installed/a1/durable-dispatch-010a/report.md) binds inspected sources and documents. No schema/code/routes/services/env/Git changes, DB/native/server/container operations, installation, provider calls or subagents. Review needed before any implementation.

Root-review correction: global runtime order explicitly includes claims after attempts and before grants. All admission/renew/cancel/removal/fact/reconciliation paths lock claim rows where accessed; revoke only updates grants and never takes a later claim/run lock, with worker consumption in a separate forward-order transaction. Capacity uses one snapshot aggregate under the increase-only gate, monotonic release and no counter; counted claim rows are not locked out of order. The proposal also aligns008d with per-receipt runner ownership and a short installation allocation/scan lock, without adding a broker. [Independent review](../docs/reviews/durable-dispatch-010a-review.md) is CLEAR/APPROVE for design, retaining every operational gate. Coordinator accepted this scope and separately assigned010b1 pure action/grant/capacity contracts. Transaction-backed ExecutionAuthority is excluded from that pure child until actual row/transaction provenance can be proved.
